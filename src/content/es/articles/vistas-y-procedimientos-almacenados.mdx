Una **vista** es una consulta de [SQL](/articulos/que-es-sql/) guardada con un nombre, que después se usa como si fuera una tabla. Un **procedimiento almacenado** es un programa guardado dentro de la base de datos, que se ejecuta allí, cerca de los datos. Los dos permiten poner parte de la lógica en la base de datos en lugar de en la aplicación.

## Vistas

### Qué problema resuelven

Muchas consultas se repiten, y algunas son largas: varios [JOIN](/articulos/tipos-de-join/), filtros, cálculos. Copiarlas en cada sitio que las necesita es fuente de errores: si cambia la definición de "cliente activo", hay que buscarla en veinte lugares.

### Cómo se usan

Los bloques SQL se ejecutan en orden en una base SQLite vacía. Fijamos la fecha de referencia en el 15 de octubre de 2026 para que el resultado sea reproducible.

```sql
PRAGMA foreign_keys = ON;
CREATE TABLE clientes (id INTEGER PRIMARY KEY, nombre TEXT NOT NULL);
CREATE TABLE pedidos (
	id INTEGER PRIMARY KEY,
	cliente_id INTEGER NOT NULL REFERENCES clientes (id),
	fecha TEXT NOT NULL,
	importe INTEGER NOT NULL
);
INSERT INTO clientes VALUES (1, 'Ana'), (2, 'Luis');
INSERT INTO pedidos VALUES
	(10, 1, '2026-10-10', 100), (11, 2, '2026-01-01', 50);

CREATE VIEW clientes_activos AS
SELECT c.id, c.nombre, MAX(p.fecha) AS ultimo_pedido
FROM clientes c
JOIN pedidos p ON p.cliente_id = c.id
WHERE p.fecha > date('2026-10-15', '-90 days')
GROUP BY c.id, c.nombre;

SELECT nombre FROM clientes_activos ORDER BY id;
```

Devuelve Ana. El pedido de Luis queda fuera de la ventana de noventa días. En una aplicación real, la fecha de referencia avanzaría según la definición de cliente activo.

Una vista normal **no almacena por separado el resultado**. Al consultarla, el motor resuelve su definición con los datos visibles para esa consulta. La vista no salta las reglas de [aislamiento](/articulos/niveles-de-aislamiento/): una transacción puede estar leyendo una instantánea anterior.

### Para qué sirven

- **Reutilizar**: la definición de un concepto vive en un solo sitio.
- **Simplificar**: quien consulta no necesita conocer cómo se unen las tablas.
- **Seguridad**: se puede dar acceso a una vista que muestra solo ciertas columnas o filas, sin dar acceso a la tabla completa. Un departamento ve los clientes de su región, sin ver datos sensibles.
- **Estabilidad**: si cambian las tablas de debajo, se ajusta la vista y lo que la usa sigue funcionando.

## Vistas materializadas

Si la consulta es costosa, ejecutarla en cada lectura sale caro. Una **vista materializada** **guarda el resultado**, como una tabla.

PostgreSQL ofrece vistas materializadas y una orden de refresco. SQLite no tiene esa función nativa. Para observar la diferencia entre recalcular y conservar un resultado, hacemos una copia manual en una tabla:

```sql
CREATE VIEW ventas_por_mes AS
SELECT substr(fecha, 1, 7) AS mes, SUM(importe) AS total
FROM pedidos GROUP BY substr(fecha, 1, 7);

CREATE TABLE resumen_guardado AS SELECT * FROM ventas_por_mes;
INSERT INTO pedidos VALUES (12, 1, '2026-10-15', 20);

SELECT total FROM ventas_por_mes WHERE mes = '2026-10';
SELECT total FROM resumen_guardado WHERE mes = '2026-10';
```

La vista calcula 120; la tabla conserva 100. La tabla es una demostración del resultado guardado, no una vista materializada con mantenimiento nativo. Para ponerla al día:

```sql
BEGIN;
DELETE FROM resumen_guardado;
INSERT INTO resumen_guardado SELECT * FROM ventas_por_mes;
COMMIT;
SELECT total FROM resumen_guardado WHERE mes = '2026-10';
```

Ahora devuelve 120. La transacción agrupa la sustitución para no confirmar un resumen vacío a medias.

Consultarla puede ahorrar el cálculo de la agregación, aunque leer sus filas y utilizar índices sigue teniendo un coste. A cambio, los datos reflejan el último **refresco**. Es una [caché](/articulos/que-es-una-cache/) dentro de la base de datos, con el mismo dilema: coste de lectura frente a frescura.

| | Vista | Vista materializada |
| --- | --- | --- |
| Guarda datos | No | Sí |
| Consulta | Ejecuta la definición cada vez | Lee el resultado guardado |
| Datos | Visibles según la consulta y su aislamiento | Del último refresco |
| Conviene para | Simplificar y controlar el acceso | Informes costosos que toleran cierto retraso |

## Procedimientos y funciones almacenados

Son bloques de código que se guardan y se ejecutan en el servidor de la base de datos. Se escriben en SQL o en un lenguaje propio del sistema, que añade variables, condicionales y bucles.

Imagina una operación almacenada para confirmar un pedido. La aplicación entrega el identificador una vez y el servidor realiza este recorrido:

| Paso | Decisión dentro de la operación |
| --- | --- |
| Leer el pedido | Comprobar que existe y aún se puede confirmar |
| Comprobar líneas | Rechazar un pedido vacío o con cantidades inválidas |
| Aplicar cambios | Actualizar el estado y guardar el registro de confirmación |
| Terminar | Confirmar juntos los cambios o propagar el error y anularlos |

Guardar el código en la base de datos no lo vuelve correcto automáticamente: hay que diseñar su transacción, sus comprobaciones y su comportamiento ante concurrencia. El ejemplo de [transacciones](/articulos/transacciones-y-acid/) muestra por qué una actualización que afecta a cero filas también puede ser un fallo para el negocio.

En PostgreSQL, una **función** puede usarse dentro de una consulta; un **procedimiento** se invoca con `CALL` y, en ciertos contextos permitidos, puede controlar transacciones. Las reglas cambian entre motores. SQLite no ofrece procedimientos almacenados como los de PostgreSQL.

### Disparadores

Un **disparador**, en inglés *trigger*, ejecuta acciones **automáticamente** ante un evento configurado, como insertar, modificar o borrar. Puede actuar por fila o por sentencia según el motor. PostgreSQL utiliza funciones para su cuerpo; otros motores tienen otra sintaxis.

Se usan para:

- Guardar un historial de cambios.
- Mantener actualizado un dato calculado.
- Impedir modificaciones que no cumplen una regla.

Su peligro es que son invisibles: quien lee el código de la aplicación no ve que una inserción provoca otras tres operaciones.

## Ventajas de poner lógica en la base de datos

- **Menos viajes.** Una operación de muchos pasos se hace en una llamada, sin ir y volver por la red.
- **Cerca de los datos.** Procesar millones de filas dentro de la base de datos evita transferirlas.
- **Un punto de control compartido.** Las restricciones activas se aplican a los cambios que cubren. Un procedimiento solo impone sus comprobaciones si las escrituras pasan por él o los permisos impiden evitarlas.
- **Un solo sitio** para una operación que usan varias aplicaciones.

## Inconvenientes

- **Herramientas y despliegue adicionales.** Hace falta versionar, probar y depurar el código almacenado con medios adecuados; esa dificultad depende del entorno.
- **Dependencia del sistema.** Cada base de datos tiene su propio lenguaje. Migrar significa reescribir.
- **Lógica repartida.** Parte del comportamiento está en la aplicación y parte en la base de datos, y hay que mirar las dos para entender qué pasa.
- **Escala peor.** La base de datos suele ser lo más difícil de escalar, y cargarla de cálculo la convierte antes en el cuello de botella, como explica [escalado vertical y horizontal](/articulos/escalado-vertical-y-horizontal/).

## Un criterio

- **Vistas**: úsalas con libertad para simplificar consultas y controlar el acceso.
- **Restricciones** en la base de datos para la integridad: claves foráneas, unicidad, comprobaciones.
- **Procedimientos y disparadores**: con moderación, para operaciones intensivas en datos o reglas que deben cumplirse siempre. La lógica de negocio principal suele estar mejor en la aplicación.

Sea cual sea el caso, el código de la base de datos se guarda en el [control de versiones](/articulos/control-de-versiones-con-git/), como cualquier otro.

## Elegir entre vista normal y materializada

Para el mismo informe de ventas por mes, una **vista normal** conserva la definición y obtiene el resultado al consultarla dentro de la visibilidad de la transacción. Una **materializada** conserva un resultado calculado, cuya frescura depende de su mantenimiento o actualización.

| Criterio | Normal | Materializada |
| --- | --- | --- |
| Qué persiste | La consulta | Su resultado almacenado |
| Cambio en las tablas | Se refleja según la instantánea consultada | Puede no aparecer hasta actualizar |
| Lectura costosa | El motor vuelve a resolver la consulta | Puede reutilizar resultados ya preparados |
| Escritura y mantenimiento | Sin almacenar ese resultado aparte | Necesita mantener o regenerar datos |

Si el informe se consulta muchas veces y tolera retraso, materializar puede ahorrar trabajo. Si necesita reflejar los datos visibles en cada consulta, una vista normal evita esa copia mantenida, aunque el coste dependa de índices y plan.

No describas una vista materializada como «instantánea de consultar»: leer muchos resultados o carecer de índices adecuados también cuesta. Tampoco todas las bases ofrecen mantenimiento automático o incremental. PostgreSQL y SQLite no tienen las mismas capacidades nativas; una tabla calculada manualmente en SQLite no adquiere por ello todas las garantías de una vista materializada de otro motor.

La vista normal tampoco evita el [aislamiento transaccional](/articulos/niveles-de-aislamiento/): «actual» significa lo visible según la consulta y su transacción, no necesariamente todos los cambios ocurridos en cualquier otra sesión.

### El mismo informe cinco minutos después

Imagina que a las diez el total vendido es 100 y se actualiza la vista materializada. A las diez y cinco se confirma otra venta de 20. Una consulta normal del informe, con una instantánea que incluya esa venta, calcula 120. La materializada puede seguir devolviendo 100 hasta que se refresque. Ambas pueden estar funcionando exactamente según su diseño.

Si el panel admite diez minutos de retraso, reutilizar ese total puede ahorrar muchas agregaciones. Si decide cuánto crédito queda para autorizar una operación, el retraso podría incumplir el requisito. «La consulta es lenta» no basta para decidir: hay que acordar qué antigüedad del resultado se tolera y cómo se presenta.

### Contar también el coste de mantenimiento

Refrescar también consume trabajo y puede interferir con lecturas según el motor y el mecanismo. Si se exige una actualización frecuente de un resultado enorme, el coste de mantenimiento puede anular el ahorro. La comparación debe incluir tanto las consultas como la regeneración.

## Errores comunes

- **Confundir una vista normal con una copia.** Guarda la definición, no el resultado calculado.
- **Materializar sin acordar la antigüedad tolerable.** Un total rápido pero atrasado puede ser incorrecto para la decisión que lo utiliza.
- **Suponer que llamar a un procedimiento impide toda escritura alternativa.** Sus reglas se pueden eludir si los permisos permiten actualizar las tablas directamente.

## Lo esencial

- Una vista es una consulta con nombre que se usa como una tabla, y no guarda datos.
- Una vista materializada guarda el resultado, y hay que refrescarla.
- Los procedimientos y funciones almacenados ejecutan código dentro de la base de datos.
- Los disparadores se ejecutan solos ante cambios en una tabla.
- Acercan la lógica a los datos; requieren pruebas, permisos y mantenimiento adecuados al motor.
