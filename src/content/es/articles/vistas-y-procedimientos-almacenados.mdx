Una **vista** es una consulta de [SQL](/articulos/que-es-sql/) guardada con un nombre, que después se usa como si fuera una tabla. Un **procedimiento almacenado** es un programa guardado dentro de la base de datos, que se ejecuta allí, cerca de los datos. Los dos permiten poner parte de la lógica en la base de datos en lugar de en la aplicación.

## Vistas

### Qué problema resuelven

Muchas consultas se repiten, y algunas son largas: varios [JOIN](/articulos/tipos-de-join/), filtros, cálculos. Copiarlas en cada sitio que las necesita es fuente de errores: si cambia la definición de "cliente activo", hay que buscarla en veinte lugares.

### Cómo se usan

```sql
CREATE VIEW clientes_activos AS
SELECT c.id, c.nombre, c.correo, MAX(p.fecha) AS ultimo_pedido
FROM clientes c
JOIN pedidos p ON p.cliente_id = c.id
WHERE p.fecha > CURRENT_DATE - INTERVAL '90 days'
GROUP BY c.id, c.nombre, c.correo;
```

A partir de ahí, se consulta como cualquier tabla:

```sql
SELECT nombre FROM clientes_activos WHERE ultimo_pedido > '2026-10-01';
```

Una vista normal **no guarda datos**. Cada vez que se consulta, la base de datos ejecuta la consulta de la definición. Los resultados están siempre al día.

### Para qué sirven

- **Reutilizar**: la definición de un concepto vive en un solo sitio.
- **Simplificar**: quien consulta no necesita conocer cómo se unen las tablas.
- **Seguridad**: se puede dar acceso a una vista que muestra solo ciertas columnas o filas, sin dar acceso a la tabla completa. Un departamento ve los clientes de su región, sin ver datos sensibles.
- **Estabilidad**: si cambian las tablas de debajo, se ajusta la vista y lo que la usa sigue funcionando.

## Vistas materializadas

Si la consulta es costosa, ejecutarla en cada lectura sale caro. Una **vista materializada** **guarda el resultado**, como una tabla.

```sql
CREATE MATERIALIZED VIEW ventas_por_mes AS
SELECT date_trunc('month', fecha) AS mes, SUM(importe) AS total
FROM pedidos
GROUP BY 1;

REFRESH MATERIALIZED VIEW ventas_por_mes;
```

Consultarla puede ahorrar el cálculo de la agregación, aunque leer sus filas y utilizar índices sigue teniendo un coste. A cambio, los datos reflejan el último **refresco**. Es una [caché](/articulos/que-es-una-cache/) dentro de la base de datos, con el mismo dilema: coste de lectura frente a frescura.

| | Vista | Vista materializada |
| --- | --- | --- |
| Guarda datos | No | Sí |
| Consulta | Ejecuta la definición cada vez | Lee el resultado guardado |
| Datos | Siempre actuales | Del último refresco |
| Conviene para | Simplificar y controlar el acceso | Informes costosos que toleran cierto retraso |

## Procedimientos y funciones almacenados

Son bloques de código que se guardan y se ejecutan en el servidor de la base de datos. Se escriben en SQL o en un lenguaje propio del sistema, que añade variables, condicionales y bucles.

```sql
CREATE PROCEDURE transferir(origen INT, destino INT, cantidad NUMERIC)
LANGUAGE plpgsql
AS $$
BEGIN
	UPDATE cuentas SET saldo = saldo - cantidad WHERE id = origen;
	UPDATE cuentas SET saldo = saldo + cantidad WHERE id = destino;
END;
$$;

CALL transferir(1, 2, 100);
```

Una **función** devuelve un valor y se puede usar dentro de una consulta. Un **procedimiento** se invoca por sí mismo, y puede controlar [transacciones](/articulos/transacciones-y-acid/).

### Disparadores

Un **disparador**, en inglés *trigger*, es una función que se ejecuta **automáticamente** cuando ocurre algo en una tabla: antes o después de insertar, modificar o borrar una fila.

Se usan para:

- Guardar un historial de cambios.
- Mantener actualizado un dato calculado.
- Impedir modificaciones que no cumplen una regla.

Su peligro es que son invisibles: quien lee el código de la aplicación no ve que una inserción provoca otras tres operaciones.

## Ventajas de poner lógica en la base de datos

- **Menos viajes.** Una operación de muchos pasos se hace en una llamada, sin ir y volver por la red.
- **Cerca de los datos.** Procesar millones de filas dentro de la base de datos evita transferirlas.
- **Reglas que nadie se salta.** Si la regla está en la base de datos, se cumple venga el cambio de la aplicación que venga.
- **Un solo sitio** para una operación que usan varias aplicaciones.

## Inconvenientes

- **Peor de mantener.** Más difícil de versionar, de probar y de depurar que el código de la aplicación.
- **Dependencia del sistema.** Cada base de datos tiene su propio lenguaje. Migrar significa reescribir.
- **Lógica repartida.** Parte del comportamiento está en la aplicación y parte en la base de datos, y hay que mirar las dos para entender qué pasa.
- **Escala peor.** La base de datos suele ser lo más difícil de escalar, y cargarla de cálculo la convierte antes en el cuello de botella, como explica [escalado vertical y horizontal](/articulos/escalado-vertical-y-horizontal/).

## Un criterio

- **Vistas**: úsalas con libertad para simplificar consultas y controlar el acceso.
- **Restricciones** en la base de datos para la integridad: claves foráneas, unicidad, comprobaciones.
- **Procedimientos y disparadores**: con moderación, para operaciones intensivas en datos o reglas que deben cumplirse siempre. La lógica de negocio principal suele estar mejor en la aplicación.

Sea cual sea el caso, el código de la base de datos se guarda en el [control de versiones](/articulos/control-de-versiones-con-git/), como cualquier otro.

## Elegir entre vista normal y materializada

Para el mismo informe de ventas por mes, una **vista normal** conserva la definición y obtiene el resultado al consultarla dentro de la visibilidad de la transacción. Una **materializada** conserva un resultado calculado, cuya frescura depende de su mantenimiento o actualización.

| Criterio | Normal | Materializada |
| --- | --- | --- |
| Qué persiste | La consulta | Su resultado almacenado |
| Cambio en las tablas | Se refleja según la instantánea consultada | Puede no aparecer hasta actualizar |
| Lectura costosa | El motor vuelve a resolver la consulta | Puede reutilizar resultados ya preparados |
| Escritura y mantenimiento | Sin almacenar ese resultado aparte | Necesita mantener o regenerar datos |

Si el informe se consulta muchas veces y tolera retraso, materializar puede ahorrar trabajo. Si necesita reflejar los datos visibles en cada consulta, una vista normal evita esa copia mantenida, aunque el coste dependa de índices y plan.

No describas una vista materializada como «instantánea de consultar»: leer muchos resultados o carecer de índices adecuados también cuesta. Tampoco todas las bases ofrecen mantenimiento automático o incremental. PostgreSQL y SQLite no tienen las mismas capacidades nativas; una tabla calculada manualmente en SQLite no adquiere por ello todas las garantías de una vista materializada de otro motor.

La vista normal tampoco evita el [aislamiento transaccional](/articulos/niveles-de-aislamiento/): «actual» significa lo visible según la consulta y su transacción, no necesariamente todos los cambios ocurridos en cualquier otra sesión.

## Lo esencial

- Una vista es una consulta con nombre que se usa como una tabla, y no guarda datos.
- Una vista materializada guarda el resultado, y hay que refrescarla.
- Los procedimientos y funciones almacenados ejecutan código dentro de la base de datos.
- Los disparadores se ejecutan solos ante cambios en una tabla.
- Acercan la lógica a los datos, a cambio de ser más difíciles de mantener y de llevar a otro sistema.
