La **compresión de datos** consiste en representar una información con menos [bits](/articulos/que-es-un-bit/) de los que ocupa en su forma original. Hay dos clases. La compresión **sin pérdida** permite recuperar los datos exactamente como eran. La compresión **con pérdida** descarta información y reconstruye una aproximación. En imagen y sonido suele buscar que el cambio sea poco perceptible; cuánto reduce y cuánto se nota depende del contenido y de los ajustes.

Está en todas partes: las páginas web, las fotos, la música, el vídeo y los archivos ZIP.

## Por qué se puede comprimir

Porque casi todos los datos tienen **redundancia**: repeticiones y patrones.

- En un texto, unas letras aparecen mucho más que otras, y las palabras se repiten.
- En una foto, los puntos vecinos suelen tener colores parecidos.
- En un vídeo, un fotograma se parece mucho al anterior.

Comprimir es describir los datos aprovechando esos patrones, en lugar de enumerarlo todo.

## Sin pérdida

### Contar repeticiones

La idea más simple: sustituir una serie de símbolos iguales por el símbolo y el número de veces. Este formato didáctico admite solo letras ASCII mayúsculas; así los números del recuento no se confunden con los símbolos originales:

```js
function comprimir(texto) {
	return texto.replace(/(.)\1*/g, (grupo, simbolo) => `${grupo.length}${simbolo}`);
}

console.log(comprimir("AAAAAABBBCCCCCCCC")); // "6A3B8C"
console.log(comprimir("ABCD")); // "1A1B1C1D"

function descomprimir(codigo) {
	return codigo.replace(/(\d+)([A-Z])/g, (_, cantidad, simbolo) => simbolo.repeat(Number(cantidad)));
}
console.log(descomprimir(comprimir("AAAAAABBBCCCCCCCC"))); // "AAAAAABBBCCCCCCCC"
```

Los 17 caracteres pasan a 6 y el decodificador los recupera; este presupone una salida válida del compresor. Pero el segundo caso enseña algo importante: sin repeticiones, el resultado es **más largo** que el original.

Ningún método comprime todo. Cada uno apuesta por un tipo de patrón.

### Códigos más cortos para lo frecuente

Un código de anchura fija dedica el mismo número de bits a cada símbolo; otras [codificaciones](/articulos/codificacion-de-caracteres/) ya usan anchuras variables, como UTF-8. Si en un texto la "e" aparece mil veces y la "w" dos, es un desperdicio.

La **codificación de Huffman** asigna códigos cortos a los símbolos frecuentes y largos a los raros. Es la idea del código Morse, donde la "E" es un solo punto.

Los códigos se construyen de modo que ninguno sea el comienzo de otro, para poder separarlos al leer. Por ejemplo, para cinco `A`, dos `B` y una `C`, se combinan primero los recuentos menores, 1 y 2; ese grupo de peso 3 se combina con el de peso 5. Un código resultante es:

| Símbolo | Frecuencia | Código | Bits aportados |
| --- | --- | --- | --- |
| A | 5 | 0 | 5 |
| B | 2 | 10 | 4 |
| C | 1 | 11 | 2 |

`AAAAABBC` se convierte en `00000101011`: once bits de contenido. El receptor también necesita conocer la tabla y dónde termina el mensaje. Guardar esos metadatos puede costar más que el ahorro en un ejemplo tan pequeño.

### Referencias a lo ya visto

Los métodos de la familia **LZ** buscan secuencias que ya aparecieron antes y las sustituyen por una referencia: "copia 12 caracteres de 340 posiciones atrás".

En un texto, en código o en un documento [HTML](/articulos/que-es-html/), con sus etiquetas repetidas, funciona muy bien.

### Combinados

Los formatos reales encadenan técnicas. **DEFLATE**, usado por gzip, PNG y muchos archivos ZIP, combina referencias a secuencias anteriores con códigos Huffman. ZIP es un contenedor y admite también otros métodos.

El siguiente bloque se ejecuta en **Node.js**. Comprueba tanto la reducción del caso repetitivo como la recuperación exacta de una entrada aleatoria:

```js
import { randomBytes } from "node:crypto";
import { deflateSync, inflateSync } from "node:zlib";

const repetitivo = Buffer.from("abc".repeat(1000));
const alAzar = randomBytes(3000);

console.log(repetitivo.length); // 3000
console.log(deflateSync(repetitivo).length < 100); // true
console.log(inflateSync(deflateSync(alAzar)).equals(alAzar)); // true
```

Tres mil bytes muy repetitivos quedan en menos de cien. Una entrada de bytes uniformes al azar suele reducirse poco o crecer por las cabeceras. No se promete un tamaño para cada realización: algunas secuencias aleatorias pueden coincidir con un patrón comprimible.

## El límite

No es casualidad. En 1948, Claude Shannon formuló la **entropía** de una fuente como una medida de incertidumbre media. Una fuente que repite casi siempre lo mismo ofrece más posibilidades de codificación corta que otra cuyos símbolos son uniformes e independientes.

Los límites de codificación se refieren a longitudes **medias** bajo un modelo de fuente y unas condiciones de decodificación. No fijan un tamaño mínimo universal para cada archivo individual: un resultado particular puede tener una descripción muy corta.

De aquí salen tres consecuencias prácticas:

- **No existe un compresor que reduzca cualquier archivo.** Hay `2^n` cadenas de `n` bits, pero solo `2^n - 1` cadenas más cortas, contando la vacía. No caben todas con una correspondencia que permita recuperarlas sin ambigüedad.
- **Comprimir dos veces suele aportar poco.** Un formato ya comprimido puede conservar cabeceras o patrones aprovechables por otro método, pero también puede crecer. Hay que medirlo.
- **Un cifrado adecuado suele dificultar la compresión del contenido.** En un archivo suele tener sentido comprimir antes de [cifrar](/articulos/cifrado-simetrico-y-asimetrico/). En protocolos interactivos, comprimir secretos junto a entradas controladas por un atacante puede filtrar información a través de la longitud: el orden no es una recomendación universal de seguridad.

## Con pérdida

En algunas aplicaciones de imagen, sonido y vídeo, la reducción sin pérdida no basta para el tamaño o la tasa de transmisión disponibles. Si el uso admite cambios, se puede aceptar una aproximación que **se perciba** igual, o suficientemente parecida.

La compresión con pérdida explota los límites de los sentidos.

- **La vista** distingue mejor los cambios de brillo que los de color, y percibe mal los detalles muy finos.
- **El oído** no percibe un sonido débil cuando suena a la vez otro fuerte de frecuencia parecida.

El codificador intenta dedicar menos bits a diferencias poco perceptibles; esa predicción puede fallar o dejar defectos visibles y audibles.

El [recorrido de una canción de Spotify](/articulos/como-funciona-spotify/) conecta esta elección con los datos que hay que transferir, su decodificación y la reserva que permite reproducir mientras continúa la descarga.

### En una imagen

El JPEG habitual basado en bloques y transformada sigue, a grandes rasgos, estos pasos:

1. Suele separar información de brillo y color, y puede reducir la resolución de los componentes de color.
2. Divide la imagen en bloques pequeños.
3. Transforma cada bloque para expresarlo como una mezcla de patrones, de los más suaves a los más finos.
4. **Redondea** con poca precisión los patrones finos, que el ojo apenas ve. Aquí es donde se pierde información.
5. Comprime el resultado sin pérdida.

El nivel de calidad que se elige al guardar regula cuánto se redondea.

### En vídeo

Además de comprimir cada imagen, se aprovecha que un fotograma se parece al anterior: se guarda uno completo de vez en cuando, y de los demás solo lo que **cambia**.

### La calidad es una elección

La relación entre tamaño y calidad depende de los datos, del método, del ajuste y de cómo se evalúe el resultado; no hay una proporción garantizada. Cuando se abusa, aparecen defectos reconocibles: bloques cuadrados, bordes borrosos, sonido metálico.

Y es irreversible. Decodificar y volver a codificar con pérdida puede acumular deterioro. Copiar el archivo sin recodificarlo conserva sus bits. Por eso se trabaja sobre un original sin pérdida, y se exporta al final.

## Comparación

| | Sin pérdida | Con pérdida |
| --- | --- | --- |
| Se recupera el original | Exacto | Una aproximación |
| Reducción | Depende de los patrones y del coste del formato | Depende además de la distorsión admitida |
| Se usa para | Texto, código, programas, datos | Fotos, música, vídeo |
| Ejemplos | ZIP, gzip, PNG, FLAC | JPEG, MP3, AAC, H.264 |

## Velocidad frente a tamaño

Dentro de un mismo método hay otro equilibrio: cuánto tiempo se invierte en comprimir.

Muchos compresores tienen niveles. Un nivel alto suele invertir más trabajo en buscar una representación pequeña; uno bajo prioriza la rapidez. No se garantiza que subir el nivel reduzca cualquier entrada: conviene medir tamaño y tiempo.

La elección depende del uso:

- **Se comprime una vez y se descarga millones**: puede compensar invertir más trabajo al preparar archivos estáticos.
- **Se comprime al vuelo, en cada petición**: hay que equilibrar CPU, latencia y bytes ahorrados.

Descomprimir suele ser mucho más rápido que comprimir.

## En la web

- **Texto.** Los servidores comprimen HTML, [CSS](/articulos/que-es-css/), JavaScript y [JSON](/articulos/formatos-de-datos-json-csv-xml/) antes de enviarlos, y el navegador los descomprime. Se negocia con cabeceras de [HTTP](/articulos/que-es-http/). Los formatos habituales son gzip, Brotli y Zstandard.
- **Imágenes.** Compara formato, calidad, compatibilidad y coste de decodificación sobre las imágenes reales; un formato más reciente no gana con cualquier contenido y configuración.

En texto con patrones repetidos puede mejorar el [rendimiento](/articulos/rendimiento-web-y-core-web-vitals/) al reducir los bytes transferidos, a cambio del trabajo de comprimir y descomprimir.

A menudo se evita la compresión HTTP adicional para imágenes y vídeo ya comprimidos porque el ahorro no compensa el coste; se comprueba con el contenido concreto.

## Lo esencial

- Comprimir es eliminar redundancia para representar lo mismo con menos bits.
- Sin pérdida, el original se recupera exacto; con pérdida, se acepta una aproximación según el criterio de calidad elegido.
- La entropía limita la longitud media bajo un modelo; ningún método sin pérdida acorta todas las entradas.
- Repetir la compresión puede aportar poco o aumentar el tamaño; comprimir junto a secretos requiere estudiar el protocolo.
- Siempre hay un equilibrio entre tamaño, calidad y tiempo.
