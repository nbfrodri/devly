La **concurrencia** es la capacidad de un programa para tener varias tareas en marcha durante el mismo periodo de tiempo. Un **hilo** es un flujo de ejecución dentro de un [proceso](/articulos/que-es-un-proceso/). Usar varios hilos es una forma de organizar trabajo concurrente.

## Qué problema resuelve

Un programa que hace una sola cosa cada vez se queda parado cuando esa cosa tarda. Si un navegador descargara un archivo sin poder hacer nada más, la ventana quedaría congelada hasta terminar.

Hay dos motivos para querer concurrencia:

- **No bloquearse.** Mientras una tarea espera al disco o a la red, otras pueden avanzar.
- **Aprovechar varios núcleos.** Un [procesador](/articulos/como-funciona-un-procesador/) actual tiene varios, y un programa con un solo flujo de ejecución usa uno solo.

## Concurrencia no es paralelismo

Se usan como sinónimos y no lo son.

- **Concurrencia**: varias tareas están en curso y avanzan intercalándose. Puede haber un solo núcleo, que salta de una a otra.
- **Paralelismo**: varias tareas se ejecutan literalmente en el mismo instante, por ejemplo en núcleos distintos.

Un cocinero que prepara tres platos, atendiendo cada uno mientras los otros se hacen, trabaja de forma concurrente. Tres cocineros, cada uno con su plato, trabajan en paralelo.

La concurrencia es una forma de **organizar** el programa. El paralelismo es una forma de **ejecutarlo** y requiere recursos capaces de trabajar simultáneamente. Varios núcleos son una forma de conseguirlo; también hay otros niveles, como las operaciones vectoriales y el multihilo simultáneo de algunos procesadores.

### El mismo trabajo con uno o dos núcleos

Imagina dos tareas A y B que necesitan diez milisegundos de CPU cada una, sin esperar a red o disco. Supongamos un único contexto de ejecución, sin multihilo simultáneo. Puedes alternar cinco milisegundos de A, cinco de B y repetir. Ambas progresan de forma concurrente, pero el trabajo total sigue necesitando veinte milisegundos de CPU, más el coste de alternar.

En dos núcleos puedes ejecutar A y B simultáneamente. Si son independientes y no aparecen otros costes, ambas acabarían en unos diez milisegundos. El paralelismo reduce el tiempo de ese cálculo; intercalarlo no crea capacidad adicional.

| Criterio | Concurrencia | Paralelismo |
| --- | --- | --- |
| Pregunta principal | Cómo organizar varios trabajos en curso | Cómo ejecutarlos simultáneamente |
| Recursos simultáneos de CPU | No son necesarios para intercalar | Son necesarios en el nivel que se paraleliza |
| Ventaja típica | Aprovechar esperas y mantener respuesta | Acelerar trabajo divisible |
| Coste relevante | Coordinación y [cambios de contexto](/articulos/cambio-de-contexto/) | Reparto, comunicación y sincronización |

Si A pasa diez milisegundos esperando una respuesta, el único núcleo puede aprovechar esa espera para ejecutar B. Esa mejora proviene de solapar espera y trabajo, no de hacer dos cálculos a la vez en el mismo núcleo. Para decidir, distingue primero una carga limitada por CPU de otra limitada por entrada y salida.

Añadir núcleos tampoco garantiza una aceleración proporcional: la [ley de Amdahl](/articulos/la-ley-de-amdahl/) recuerda que el trabajo secuencial sigue limitando el conjunto.

### Elegir según el trabajo

La elección también depende del objetivo. Un editor puede querer seguir respondiendo al teclado mientras espera un archivo: organizar el trabajo concurrentemente mejora la respuesta aunque no reduzca la cantidad total de cálculo. Un conversor de imágenes puede querer terminar cien transformaciones antes: repartir imágenes independientes entre núcleos ofrece paralelismo útil.

Para el conversor, crear cien hilos en un equipo con cuatro núcleos no proporciona cien cálculos simultáneos de CPU. Hay que repartir recursos, considerar memoria y evitar que el coste de coordinación supere lo ganado. Para el editor, ejecutar un cálculo largo en una función llamada asíncrona tampoco libera automáticamente el hilo de la interfaz. Primero se identifica qué trabajo espera y cuál consume CPU; después se elige cómo organizarlo.

## Qué es un hilo

Un proceso tiene al menos un hilo, el principal. Puede crear más.

Lo que distingue a los hilos de los procesos es lo que comparten:

| | Procesos distintos | Hilos del mismo proceso |
| --- | --- | --- |
| Memoria | Espacios de direcciones separados; pueden compartir regiones explícitamente | Comparten el espacio de direcciones |
| Pila de llamadas | Una por cada hilo que contiene el proceso | Cada hilo tiene la suya |
| Crearlos y cambiar entre ellos | Suele implicar más recursos y aislamiento | Compartir el espacio de direcciones puede reducir el coste |
| Si uno falla | El aislamiento limita la propagación directa | Un fallo fatal puede terminar todo el proceso |

Cada hilo tiene su propia [pila](/articulos/pilas-y-colas/) y su propio punto de ejecución. Comparten el espacio de memoria, pero eso no significa que todas las variables sean comunes: una variable local de cada llamada ocupa su propia ubicación. El lenguaje también puede ofrecer almacenamiento específico de cada hilo.

Compartir memoria permite intercambiar datos sin copiarlos entre procesos. Aun así, la visibilidad y el orden de los accesos necesitan coordinación; compartir una dirección no garantiza leer el valor esperado.

## Quién decide el orden

El planificador del [sistema operativo](/articulos/que-es-un-sistema-operativo/) reparte el tiempo de procesador entre los hilos. Puede interrumpir a uno en cualquier momento, incluso a mitad de una operación, para dar paso a otro.

El programa no controla en qué orden se intercalan. Dos ejecuciones del mismo programa pueden mezclar los pasos de forma distinta. A esto se le llama **no determinismo**, y es lo que hace difícil la programación concurrente: un error puede aparecer una vez de cada mil.

## El riesgo de compartir

Si dos hilos modifican el mismo dato sin coordinarse, el resultado depende de cómo se intercalen. Es una **condición de carrera**, y produce fallos intermitentes muy difíciles de reproducir.

La forma de evitarlo y los problemas que trae consigo, como los bloqueos mutuos, se explican en [condiciones de carrera y bloqueos](/articulos/condiciones-de-carrera-y-bloqueos/).

## Otra forma: un solo hilo que no espera

No toda la concurrencia usa varios hilos. El hilo principal de una página puede atender clics, descargas y temporizadores sin ejecutar dos callbacks simultáneamente. El navegador puede usar otros hilos internamente, y JavaScript dispone también de workers para trabajo separado.

El truco es no quedarse esperando. Cuando una operación va a tardar, como una petición de red, el programa la inicia, deja anotado qué hacer cuando termine y sigue con otra cosa. Un mecanismo llamado **bucle de eventos** va despachando las tareas pendientes a medida que están listas.

```js
function esperar(milisegundos) {
	return new Promise((resolver) => setTimeout(resolver, milisegundos));
}

async function tarea(nombre, duracion, registro) {
	registro.push(`empieza ${nombre}`);
	await esperar(duracion);
	registro.push(`termina ${nombre}`);
}

const registro = [];
await Promise.all([tarea("A", 30, registro), tarea("B", 10, registro)]);

console.log(registro.join(", ")); // "empieza A, empieza B, termina B, termina A"
```

Las dos tareas empiezan una tras otra y B termina antes, aunque se lanzó después. Mientras A espera, el único hilo atiende a B. `await` marca los puntos en los que una tarea cede el paso.

Este modelo se llama **asíncrono**, y en JavaScript se escribe con [promesas y async/await](/articulos/promesas-y-async-await/). Encaja muy bien cuando la mayor parte del tiempo se va en esperar: a la red, al disco, a una base de datos. Con él, un solo hilo atiende a miles de clientes.

No sirve para acelerar cálculos. Si una tarea ocupa el procesador sin pausas, bloquea a todas las demás, porque solo hay un hilo.

## Cuál elegir

| El trabajo consiste en | Conviene |
| --- | --- |
| Esperar: red, disco, base de datos | Modelo asíncrono |
| Calcular: procesar imágenes, comprimir, simular | Varios hilos o procesos, en paralelo |

## Un límite que conviene conocer

Añadir [núcleos](/articulos/procesadores-multinucleo/) no acelera un programa sin fin. Solo se beneficia la parte del trabajo que se puede repartir. Si la décima parte de un programa tiene que ejecutarse en orden, por muchos núcleos que añadas nunca irá más de diez veces más rápido. Esta observación se conoce como **ley de Amdahl**.

Un [semáforo](/articulos/semaforos-en-concurrencia/) coordina tareas mediante permisos y permite distinguir exclusión mutua de límites de capacidad.

## Errores comunes

- **Crear más hilos y esperar una mejora proporcional.** Los núcleos, la parte secuencial y la coordinación limitan el paralelismo útil.
- **Suponer que compartir memoria ordena los accesos.** Dos hilos pueden leer un mismo valor antiguo y sobrescribir el resultado del otro. Hace falta un mecanismo de sincronización adecuado.
- **Marcar una función como `async` para apartar un cálculo pesado.** Esa palabra no crea un hilo: el código síncrono sigue ocupando el hilo donde se ejecuta.

## Lo esencial

- La concurrencia es tener varias tareas en curso; el paralelismo, ejecutarlas en el mismo instante.
- Un hilo es un flujo de ejecución dentro de un proceso; los hilos comparten memoria.
- El planificador decide la intercalación; la sincronización permite imponer las relaciones de orden necesarias.
- El modelo asíncrono consigue concurrencia con un solo hilo, y es adecuado cuando el trabajo consiste en esperar.
