Una **caché** es un almacén temporal donde se guarda el resultado de una operación costosa para reutilizarlo en lugar de repetirla. Es una de las técnicas más usadas para hacer que un sistema responda rápido.

## La idea

Si consultas a menudo un libro de la biblioteca, acabas teniéndolo en tu mesa. La biblioteca sigue siendo el lugar "oficial", pero la copia a mano te ahorra el viaje.

Una caché se apoya en lo mismo: obtener un dato del sitio original cuesta, hay datos que se piden una y otra vez, y guardar una copia cerca sale más barato que volver a buscarlo.

## Aciertos y fallos

En una caché sencilla que carga los datos cuando faltan y tiene permiso para almacenarlos:

- Si hay una copia utilizable en la caché, es un **acierto** (*hit*): se devuelve sin repetir la operación de origen.
- Si no está, es un **fallo** (*miss*): se obtiene del origen, se guarda en la caché y se devuelve.

La proporción de aciertos mide lo útil que es una caché. Si casi todo son fallos, solo añade trabajo.

Este ejemplo guarda resultados en un [`Map`](/articulos/tablas-hash/). La función representa un cálculo costoso mediante un contador; elevar al cuadrado un número no necesita por sí solo esta optimización:

```js
const cache = new Map();
let calculos = 0;

function cuadradoLento(numero) {
	calculos = calculos + 1;
	return numero * numero;
}

function cuadrado(numero) {
	if (cache.has(numero)) {
		return cache.get(numero);
	}

	const resultado = cuadradoLento(numero);
	cache.set(numero, resultado);

	return resultado;
}

cuadrado(12);
cuadrado(12);
cuadrado(12);

console.log(cuadrado(12)); // 144
console.log(calculos); // 1
```

Cuatro llamadas y un solo cálculo. Guardar así los resultados de una función se llama **memorización**.

## Hay cachés en todas partes

La misma idea aparece en todos los niveles de un sistema:

| Dónde | Qué guarda |
| --- | --- |
| El [procesador](/articulos/como-funciona-un-procesador/) | Los datos de memoria usados hace poco |
| El sistema operativo | Partes del disco leídas recientemente |
| El navegador | Imágenes, estilos y programas de las páginas visitadas, según la [caché HTTP](/articulos/como-funciona-la-cache-http/) |
| Una [CDN](/articulos/que-es-una-cdn/) | Copias de los archivos de un sitio, repartidas por el mundo |
| La aplicación | Resultados de consultas a la base de datos o a otros servicios |
| El [DNS](/articulos/que-es-dns/) | Las direcciones IP de los nombres ya resueltos |

## El problema difícil: los datos caducan

Una caché guarda una copia, y el original puede cambiar. Entonces la copia queda **obsoleta**: la caché sirve un dato que ya no es verdad.

Decidir cuándo una copia deja de valer se llama **invalidación**, y tiene fama de ser uno de los problemas difíciles de la informática. Hay tres enfoques.

### Caducidad por tiempo

Cada dato puede tener un **tiempo de vida** (TTL). Al agotarse, deja de poder reutilizarse sin seguir la política de renovación. Según el sistema, puede eliminarse, obtenerse otra vez o conservarse mientras se comprueba si cambió. En HTTP, perder frescura no obliga por sí solo a borrar el cuerpo guardado.

Esta política obliga a elegir: un TTL largo permite más reutilización, pero también aceptar datos antiguos durante más tiempo; uno corto requiere renovaciones más frecuentes. El resultado depende de las peticiones y de cuándo cambie el original.

### Invalidación explícita

Cuando el dato original cambia, se borra o se actualiza la copia. Es preciso, pero exige que todo el código que modifica el dato se acuerde de avisar a la caché. Un olvido deja datos obsoletos sin fecha de fin.

### Nombres que cambian con el contenido

Si el nombre de un archivo incluye una huella de su contenido, como `estilos.3f9a2c.css`, cualquier cambio produce un nombre nuevo. Si se respeta la regla de no cambiar el contenido bajo ese mismo nombre, la copia puede tener una vida de frescura larga. Eso no garantiza que se conserve: el espacio es limitado y puede desalojarse. También hay que actualizar la página para que apunte al nombre nuevo.

## Cuando la caché se llena

La memoria es limitada, así que en algún momento hay que tirar algo. La regla que decide qué se elimina es la **política de desalojo**. Una política habitual es **LRU** (*least recently used*): se descarta lo que lleva más tiempo sin usarse.

```js
class CacheLRU {
	#datos = new Map();

	constructor(capacidad) {
		if (!Number.isInteger(capacidad) || capacidad < 0) {
			throw new RangeError("La capacidad debe ser un entero no negativo");
		}
		this.capacidad = capacidad;
	}

	obtener(clave) {
		if (!this.#datos.has(clave)) {
			return undefined;
		}

		const valor = this.#datos.get(clave);
		this.#datos.delete(clave);
		this.#datos.set(clave, valor);

		return valor;
	}

	guardar(clave, valor) {
		this.#datos.delete(clave);
		this.#datos.set(clave, valor);

		if (this.#datos.size > this.capacidad) {
			const masAntigua = this.#datos.keys().next().value;
			this.#datos.delete(masAntigua);
		}
	}
}

const cache = new CacheLRU(2);
cache.guardar("a", 1);
cache.guardar("b", 2);
cache.obtener("a");
cache.guardar("c", 3);

console.log(cache.obtener("a")); // 1
console.log(cache.obtener("b")); // undefined
```

Al guardar `c` no cabe todo. Como `a` se acababa de consultar, la que se descarta es `b`.

## La caché de HTTP

En la web, [HTTP](/articulos/que-es-http/) intercambia peticiones y respuestas. Sus **cabeceras** son campos de metadatos. El servidor utiliza `Cache-Control` para indicar reglas de almacenamiento y reutilización de una respuesta:

| Valor | Significado |
| --- | --- |
| `max-age=3600` | Vida de frescura de una hora, teniendo en cuenta la edad de la respuesta |
| `no-cache` | Se puede guardar, pero requiere validación satisfactoria antes de reutilizarla |
| `no-store` | Ordena a las cachés no almacenar esta petición o respuesta; no borra copias anteriores |
| `private` | Permite cachés privadas de un usuario, pero prohíbe almacenarla en cachés compartidas |

Cuando una copia deja de estar fresca y dispone de un validador, como una etiqueta `ETag`, el cliente puede preguntar si ha cambiado. Una respuesta `304 Not Modified` permite reutilizar el cuerpo guardado. Si no hay validador o la representación ha cambiado, puede hacer falta descargarla de nuevo.

## Sus riesgos

- **Datos obsoletos**, ya vistos.
- **Datos privados en una caché compartida.** Guardar la respuesta de un usuario y servírsela a otro es un fallo de seguridad grave. Lo que depende de quién pregunta no debe compartirse.
- **Avalancha al caducar.** Si una copia muy solicitada caduca, miles de peticiones pueden ir a la vez al origen para regenerarla.
- **Más complejidad.** Los errores causados por una caché son difíciles de reproducir: aparecen y desaparecen según lo que haya guardado en ese instante.

## Cuándo usarla

Una caché suele compensar cuando el dato **cuesta de obtener** y se **reutiliza mucho**. Si no se tolera desactualización, hace falta un mecanismo de coherencia o validación apropiado, con su coste. El [caso de Cloudflare](/articulos/que-hace-cloudflare/) sigue tres visitas para distinguir frescura, actualización y permanencia de una copia.

Mide el coste de obtener datos, la tasa de aciertos y la antigüedad tolerable. Una caché puede ser parte del diseño adecuado, pero también añade trabajo y reglas que mantener; no sustituye corregir una consulta innecesariamente costosa.

## Lo esencial

- Una caché guarda una copia de un resultado costoso para reutilizarla.
- Un acierto evita el trabajo; un fallo obliga a ir al origen.
- Lo difícil es la invalidación: saber cuándo la copia deja de ser válida.
- Cuando se llena, una política de desalojo como LRU decide qué eliminar, aunque la copia siga vigente.
