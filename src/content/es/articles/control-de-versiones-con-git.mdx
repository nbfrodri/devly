El **control de versiones** registra estados de unos archivos para compararlos, recuperar versiones anteriores y combinar trabajo. **Git** es un programa que lo hace: tú eliges qué contenido guardar en cada versión.

## Qué problema resuelve

Las carpetas `proyecto-final` y `proyecto-final-2` no explican qué cambió ni por qué. Git conserva versiones identificables, con autor, fecha y mensaje. Permite consultar una versión anterior sin depender de recordar qué archivo copiaste.

También permite trabajar en paralelo. Cada persona registra su trabajo y después lo combina con el de las demás. Git ayuda a reunir cambios, pero las personas siguen comprobando que el resultado tenga sentido.

## Repositorio y confirmaciones

Un **repositorio** guarda la historia y la información con la que Git la gestiona. En un proyecto local habitual, esa información vive en la carpeta oculta `.git`, junto a los archivos que editas.

Una **confirmación**, o *commit*, registra una instantánea del contenido preparado, además de autor, fecha y mensaje. No recoge automáticamente todos los archivos del disco. Los archivos que no cambian respecto de la versión anterior siguen formando parte de la instantánea.

Cada commit tiene un identificador calculado a partir de sus datos mediante una [función hash](/articulos/funciones-hash/). También enlaza a sus **padres**, los commits anteriores de los que procede: el inicial no tiene ninguno, uno habitual tiene uno y uno de fusión puede tener varios. La historia puede ramificarse; no es siempre una cadena. Los detalles se explican en [Git por dentro](/articulos/git-por-dentro/).

## Tres lugares que no hay que confundir

| Lugar | Qué contiene |
| --- | --- |
| **Directorio de trabajo** | Los archivos tal como están ahora en tu carpeta |
| **Área de preparación**, o *staging area* | La versión que estás construyendo para el próximo commit; Git la llama también **índice** |
| Repositorio | Las versiones ya confirmadas y su historia |

**Preparar** contenido significa seleccionarlo para la próxima confirmación. `git add` copia al índice el contenido que tiene el archivo en ese momento. Si lo editas después, lo preparado no se actualiza solo.

Así puedes separar tareas: preparar el arreglo de un error, confirmarlo y registrar después otro cambio con su propia explicación.

## Un recorrido desde una carpeta vacía

Necesitas Git instalado: `git --version` muestra su versión. Usa una [**terminal**](/articulos/terminal-y-shell/), una ventana para introducir órdenes, y un editor de texto. Los comandos siguientes funcionan en PowerShell y Bash con Git 2.28 o posterior.

### 1. Crear el proyecto de práctica

Abre la terminal en una carpeta de prácticas, fuera de otros proyectos, donde todavía no exista `practica-git`. Ejecuta las líneas en orden:

```bash
mkdir practica-git
cd practica-git
git init -b main
git config --local user.name "Persona de prueba"
git config --local user.email "practica@example.com"
```

`mkdir` crea la carpeta y `cd` entra en ella. `git init` crea el repositorio; `-b main` fija el nombre de la rama inicial. Las dos órdenes `config` ponen una identidad ficticia para esta práctica. `--local` limita el cambio a este repositorio: no modifica tu configuración global ni crea una cuenta en internet.

### 2. Preparar una versión y seguir editando

Con el editor, crea `notas.txt` dentro de `practica-git`, como texto UTF-8 con esta línea:

```text
Comprar pan.
```

```bash
git status --short
git add notas.txt
git status --short
```

La primera consulta muestra `?? notas.txt`: el archivo está **sin seguimiento**, todavía no elegido para el historial. La segunda muestra `A  notas.txt`: su incorporación está preparada.

Ahora sustituye la línea en el editor por `Comprar pan y leche.` y guarda. No repitas todavía `git add`:

```bash
git status --short
git diff --cached
git diff
```

El estado es `AM notas.txt`. La primera columna describe lo preparado: `A`, archivo añadido. La segunda describe el cambio posterior en la carpeta: `M`, modificado.

`git diff --cached` muestra lo preparado frente a la última confirmación; como aún no hay ninguna, muestra la incorporación de `Comprar pan.`. `git diff` compara el archivo actual con lo preparado: verás que la línea sin leche se sustituye por la línea con leche.

### 3. Confirmar y comprobar qué se guardó

```bash
git commit -m "Crea la lista de compra"
git show HEAD:notas.txt
git status --short
```

`-m` introduce el mensaje del commit. **HEAD** identifica aquí la confirmación actual. `git show HEAD:notas.txt` imprime su versión del archivo: `Comprar pan.`. En tu editor sigue apareciendo `Comprar pan y leche.`: confirmar lo preparado no borra esa edición posterior.

El estado muestra ` M notas.txt`, con la primera columna vacía. La modificación existe en tu carpeta, pero aún no está preparada para otro commit.

Ahora registra también la leche:


El estado abreviado no imprime nada: no quedan cambios pendientes. El historial muestra dos commits, el más reciente primero, con sus identificadores abreviados y mensajes. Los identificadores concretos variarán en tu práctica.

## Trabajar en otra rama

Una **rama** es un nombre que apunta a un commit y avanza cuando confirmas trabajo en ella. Permite desarrollar una tarea sin mover la rama principal. Sigue en la misma carpeta:

```bash
git switch -c mejora-lista
```

`switch -c` crea la rama y te sitúa en ella. Edita `notas.txt` para que contenga estas dos líneas:

```text
Comprar pan y leche.
Llevar bolsa.
```

```bash
git add notas.txt
git commit -m "Recuerda llevar una bolsa"
git switch main
git show HEAD:notas.txt
git merge --ff-only mejora-lista
git show HEAD:notas.txt
```

Al volver a `main`, el archivo vuelve a contener solo la compra: el recordatorio está confirmado en la otra rama. La **fusión**, o *merge*, incorpora su trabajo a la rama actual.

Aquí `main` no avanzó por separado. `--ff-only` permite un **avance rápido**, o *fast-forward*: mueve `main` hasta el commit del recordatorio, sin crear otro commit. La última consulta muestra las dos líneas. Si las ramas hubieran avanzado por separado, esa opción se detendría.

Cuando ambas ramas tienen trabajo nuevo, una fusión puede crear un commit con dos padres. Si Git no sabe reconciliar los cambios, aparece un **conflicto**: por ejemplo, dos ediciones incompatibles de una línea o borrar un archivo que la otra rama modifica. Hay que decidir el resultado, prepararlo y completar la fusión. Los conflictos de texto suelen mostrar ambas versiones en el archivo.

Una fusión sin conflictos tampoco demuestra que el programa funcione: dos cambios aceptados pueden contradecirse. Revisa el resultado y ejecuta sus comprobaciones. Las estrategias se comparan en [merge y rebase](/articulos/merge-y-rebase/).

## Compartir el trabajo

Todo el recorrido anterior funciona sin internet. Un **repositorio remoto** es otro repositorio con el que intercambias historia, normalmente alojado en un [servidor](/articulos/que-es-un-servidor/).

| Orden | Para qué sirve |
| --- | --- |
| `git clone` | Crear una copia local a partir de otro repositorio |
| `git fetch` | Traer historia y referencias del remoto sin integrarlas en tu rama actual |
| `git pull` | Traer cambios e intentar integrarlos según la configuración y las opciones elegidas |
| `git push` | Enviar commits y actualizar ramas u otras referencias en el remoto, si este lo permite |

Git es **distribuido**: puedes confirmar y consultar historia localmente. Un clon normal trae la historia disponible de las ramas del origen; también existen clones con historia recortada o con contenidos que se descargan después. No todas las copias contienen todo.

[GitHub](/articulos/git-y-github/) aloja repositorios y añade revisión y automatización. Git es el programa de control de versiones. Las [comprobaciones automáticas](/articulos/integracion-y-despliegue-continuos/) pueden verificar las propuestas antes de integrarlas.

## Errores comunes

- **Creer que guardar en el editor crea un commit.** Guardar cambia el directorio de trabajo; preparar y confirmar son pasos distintos.
- **Preparar sin revisar.** Consulta `git status` y `git diff --cached`; registra cambios con un propósito y un mensaje que lo explique.
- **Usar `.gitignore` para borrar el pasado.** Ese archivo enumera patrones de archivos que Git debe ignorar cuando aún no están bajo seguimiento. No deja de seguir archivos ya registrados ni elimina secretos de commits anteriores. Si expones una clave, hay que revocarla o sustituirla; añadir su archivo a `.gitignore` no basta.
- **Confundir un remoto con una copia de todo el ordenador.** `push` no envía ediciones sin confirmar ni archivos sin seguimiento. Git no sustituye una estrategia de copias de seguridad.

## Lo esencial

- Git registra versiones elegidas, no cada pulsación del editor.
- `git add` prepara el contenido actual; `git commit` registra lo preparado.
- Las ramas permiten separar trabajo; reunirlo exige comprobar el resultado.
- Un remoto permite compartir historia, pero no guarda automáticamente todo tu trabajo local.
