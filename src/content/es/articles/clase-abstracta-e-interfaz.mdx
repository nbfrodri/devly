Una **[interfaz](/articulos/que-es-una-interfaz/)** describe solo **qué** debe ofrecer un objeto: sus métodos y propiedades, sin código. Una **clase abstracta** es una [clase](/articulos/que-es-una-clase/) que no se puede instanciar directamente: puede incluir **parte del código**, y deja otras partes para que las completen las clases que heredan de ella.

## Interfaz

Los bloques TypeScript son variantes independientes del mismo cuadrado de lado 3. Aquí una interfaz describe su operación:

```ts
interface Figura {
	area(): number;
}

class Cuadrado implements Figura {
	constructor(private lado: number) {}
	area() { return this.lado ** 2; }
}
console.log(new Cuadrado(3).area()); // 9
```

En TypeScript, la interfaz no aporta código ejecutable. La cumple cualquier objeto con un método `area` de firma compatible, aunque no sea una instancia de clase. Esa compatibilidad de tipos no demuestra que el cálculo sea correcto. Una clase puede cumplir **varias** interfaces a la vez.

## Clase abstracta

```ts
abstract class Figura {
	abstract area(): number;

	describir() {
		return `Área: ${this.area()}`;
	}
}

class Cuadrado extends Figura {
	constructor(private lado: number) { super(); }
	area() { return this.lado ** 2; }
}
console.log(new Cuadrado(3).describir()); // "Área: 9"
```

`area` queda pendiente en la base; `describir` ya está hecho y lo hereda el cuadrado. Para calcular el área bastaba la interfaz; para compartir esta implementación de descripción, la clase abstracta ofrece una opción.

JavaScript no tiene clases abstractas, pero se puede imitar:

```js
class Figura {
	constructor() {
		if (new.target === Figura) throw new Error("Figura es abstracta");
	}

	describir() {
		return `Área: ${this.area()}`;
	}
}

class Cuadrado extends Figura {
	constructor(lado) {
		super();
		this.lado = lado;
	}

	area() {
		return this.lado ** 2;
	}
}

console.log(new Cuadrado(3).describir()); // "Área: 9"

try {
	new Figura();
} catch (error) {
	console.log(error.message); // "Figura es abstracta"
}
```

## Comparación

Esta tabla se refiere a TypeScript. Otros lenguajes permiten, por ejemplo, implementaciones predeterminadas en interfaces.

| | Interfaz | Clase abstracta |
| --- | --- | --- |
| Contiene código | No | Sí, en parte |
| Se instancia | No | No |
| Cuántas se pueden usar | Varias a la vez | Normalmente una, por herencia |
| Relación | "Se comporta como" | "Es un" |
| Estado, atributos con valor | No | Sí |
| Acoplamiento | Bajo | Mayor: se hereda su implementación |

## Cuál elegir

- **Interfaz** cuando se quiere definir un contrato que cosas muy distintas pueden cumplir. Es la opción más flexible, y la que encaja con la idea de [preferir la composición a la herencia](/articulos/herencia-y-composicion/).
- **Clase abstracta** cuando varias clases comparten de verdad una parte del código y una relación "es un" clara.

También puedes compartir código con una función que reciba la interfaz, sin heredar. La elección depende de qué comportamiento y estado necesitas compartir, no de que una opción sea siempre superior.

## Confusiones frecuentes

- **Esperar validación al ejecutar una interfaz.** TypeScript la borra al generar JavaScript. Para datos externos hacen falta comprobaciones reales.
- **Confundir `abstract` con una barrera de ejecución.** La prohibición de instanciar la clase abstracta pertenece al verificador de TypeScript; el ejemplo JavaScript implementa una comprobación distinta en su constructor.
- **Exigir herencia para cualquier contrato.** Un objeto literal con `area(): number` también puede cumplir `Figura` en TypeScript.

## Lo esencial

- Una interfaz solo define qué métodos debe tener algo, sin código.
- Una clase abstracta puede aportar parte del código y no se instancia.
- Una clase puede cumplir varias interfaces, pero heredar normalmente de una sola clase.
- Las interfaces dan más flexibilidad; las clases abstractas, código compartido.
