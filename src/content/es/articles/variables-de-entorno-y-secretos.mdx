Una **variable de entorno** es un valor con nombre que el [sistema operativo](/articulos/que-es-un-sistema-operativo/) entrega a un programa cuando lo arranca. Se usan para pasarle su **configuración** sin escribirla en el código. Un **secreto** es un dato de configuración que da acceso a algo, como una contraseña o una clave de API, y que por eso necesita una protección especial.

## Qué problema resuelven

Una aplicación necesita datos que cambian según dónde se ejecute:

- La dirección de la base de datos.
- Las claves para usar servicios externos.
- El puerto en el que escucha.
- Si está en modo de depuración.

En tu ordenador usa una base de datos local; en producción, otra. Si esos valores están escritos en el código:

- Hay que **modificar el código** para cambiar de entorno, y es fácil publicar por error la configuración de pruebas.
- Las contraseñas **quedan en el repositorio**, a la vista de cualquiera que lo tenga.

La regla, formulada en la metodología de los doce factores, es separar estrictamente la configuración del código. Una prueba sencilla: ¿podría publicarse el repositorio ahora mismo sin exponer ninguna credencial?

## Cómo funcionan

Cada [proceso](/articulos/que-es-un-proceso/) tiene un **entorno**: una lista de pares de nombre y valor. Lo hereda del proceso que lo arrancó.

En una [terminal](/articulos/terminal-y-shell/) se pueden definir justo delante de una orden:

```bash
PUERTO=8080 node servidor.js
```

Y el programa las lee. En Node.js están en `process.env`:

```js
const entorno = { PUERTO: "8080", DEPURAR: "false" };

const puerto = Number(entorno.PUERTO ?? 3000);

console.log(puerto + 1); // 8081
console.log(Boolean(entorno.DEPURAR)); // true
console.log(entorno.DEPURAR === "true"); // false
```

El ejemplo usa un objeto para imitar `process.env`, y muestra una trampa: **los valores son siempre texto**. El texto `"false"` no está vacío, así que convertido a booleano es verdadero. Los números y los booleanos hay que convertirlos de forma explícita.

Por convención, los nombres se escriben en mayúsculas con guiones bajos.

## Archivos .env

Escribir las variables a mano cada vez es incómodo. En desarrollo se guardan en un archivo llamado `.env`:

```
URL_BASE_DE_DATOS=postgres://localhost:5432/tienda
CLAVE_API_PAGOS=clave-de-pruebas
PUERTO=3000
```

Una herramienta las carga al arrancar.

Dos reglas, sin excepciones:

- **El archivo `.env` no se sube al repositorio.** Se añade a `.gitignore` el primer día.
- **Sí se sube un `.env.example`**, con los nombres y sin valores reales, para que quien llegue sepa qué necesita.

## Validar al arrancar

Una variable que falta debe detener el programa al iniciarse, con un mensaje claro, y no provocar un error extraño horas después.

```js
function leerConfiguracion(entorno) {
	const necesarias = ["URL_BASE_DE_DATOS", "CLAVE_API"];
	const faltan = necesarias.filter((nombre) => !entorno[nombre]);

	if (faltan.length > 0) {
		throw new Error(`Faltan variables: ${faltan.join(", ")}`);
	}

	return { baseDeDatos: entorno.URL_BASE_DE_DATOS };
}

try {
	leerConfiguracion({ URL_BASE_DE_DATOS: "postgres://localhost/tienda" });
} catch (error) {
	console.log(error.message); // "Faltan variables: CLAVE_API"
}
```

Es el principio de fallar pronto, del artículo sobre [manejo de errores](/articulos/manejo-de-errores-y-excepciones/).

## Secretos

No toda la configuración es igual de delicada. El puerto no importa que se sepa. La contraseña de la base de datos, sí.

Son secretos:

- Contraseñas de bases de datos.
- Claves de API de servicios externos.
- Claves para firmar [tokens](/articulos/que-es-un-jwt/) o cifrar datos.
- Certificados y claves privadas.

Quien tenga uno puede hacerse pasar por la aplicación.

### El error más común

Subir un secreto a un repositorio. Ocurre constantemente, y es grave por una razón que a menudo se pasa por alto: **[Git](/articulos/control-de-versiones-con-git/) guarda todo el historial**. Borrar el secreto en un commit posterior no lo elimina. Sigue en los commits anteriores, al alcance de cualquiera que clone el repositorio.

En los repositorios públicos hay programas automáticos que buscan claves recién subidas, y las encuentran en minutos.

Si ocurre, lo único seguro es **revocar el secreto y generar otro**. Limpiar el historial no basta: no se puede saber quién lo copió ya.

## Dónde se guardan

Fuera del repositorio, en un sistema pensado para ello.

| Dónde | Uso |
| --- | --- |
| Almacén de secretos de la plataforma de CI/CD | Lo que necesita el [pipeline](/articulos/integracion-y-despliegue-continuos/) |
| Configuración de la plataforma de alojamiento | Variables de la aplicación en producción |
| Gestor de secretos | Organizaciones con muchos servicios y equipos |

Un **gestor de secretos** guarda los valores cifrados, controla quién puede leer cada uno, anota cada acceso y permite cambiarlos sin volver a desplegar.

## Buenas prácticas

- **Mínimo privilegio.** Cada servicio accede solo a los secretos que necesita, y cada secreto da los permisos justos. Una clave de solo lectura, si basta con leer.
- **Un secreto distinto por entorno.** La clave de pruebas no abre producción.
- **Rotación.** Cambiarlos cada cierto tiempo limita el daño de una filtración que no se ha detectado.
- **Corta duración.** Las credenciales que caducan solas en minutos u horas son mejores que las permanentes.
- **Fuera de los registros.** Un error que imprime toda la configuración filtra todo. Tampoco van en las direcciones web ni en los mensajes de error. Se trata en [observabilidad](/articulos/observabilidad/).
- **Nunca en el cliente.** Todo lo que llega al navegador o a una aplicación móvil puede leerlo el usuario. Una clave incluida en el JavaScript de una página es pública. Los secretos se quedan [en el servidor](/articulos/cliente-servidor/).
- **Tampoco en las imágenes.** Quien obtenga una imagen de [Docker](/articulos/que-es-docker/) obtiene lo que contenga.

## Los límites de las variables de entorno

Para los secretos, son mejores que el código, pero no perfectas:

- Las ve cualquier proceso que tenga acceso al de la aplicación, y las heredan los procesos que esta arranque.
- Pueden acabar en un volcado de memoria o en un informe de errores.
- No dejan constancia de quién las leyó ni se rotan solas.

Por eso los sistemas más exigentes hacen que la aplicación pida el secreto al gestor cuando lo necesita, o lo reciben como un archivo en memoria.

## Lo esencial

- Las variables de entorno pasan la configuración a un programa sin escribirla en el código.
- Sus valores son siempre texto, y conviene validarlos al arrancar.
- El archivo `.env` es para desarrollo y no se sube al repositorio.
- Un secreto subido a Git sigue en el historial: hay que revocarlo.
- Los secretos se guardan en un almacén específico, con permisos mínimos y rotación.
