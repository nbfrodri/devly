**Git** es el programa de [control de versiones](/articulos/control-de-versiones-con-git/) que registra y combina cambios en archivos. **GitHub** es una plataforma que aloja repositorios de Git y añade herramientas para proponer, revisar y organizar ese trabajo.

## Dos problemas distintos

Guardar una versión de tu proyecto requiere un sistema de control de versiones. Acordar con otras personas qué versión incorporar requiere además comunicación, permisos y un proceso de revisión.

Git resuelve la primera parte y proporciona las operaciones para intercambiar historia. GitHub reúne un alojamiento para esa historia y herramientas para coordinar al equipo. Un commit puede existir en tu ordenador sin existir todavía en GitHub.

## Qué hace Git

Git gestiona el directorio de trabajo, la preparación de cambios, los commits y las ramas. Puedes registrar versiones y consultar la historia disponible localmente sin conexión.

Un **remoto** es otro repositorio con el que intercambias información. Puede estar en GitHub, en otro servidor o en una carpeta de tu ordenador. `origin` es el nombre que `git clone` le da normalmente al origen de la copia; no significa «GitHub».

Git es **distribuido**: distintos repositorios pueden conservar historia y producir commits. Un clon normal trae la historia de las ramas disponibles del origen, pero hay clones con historia recortada o con contenidos que se obtienen cuando hacen falta.

## Qué añade GitHub

Una **solicitud de cambios**, o *pull request* (**PR**), propone incorporar los cambios de una rama a otra. Permite comentar líneas, discutir decisiones y revisar comprobaciones antes de aceptar la propuesta. Abrirla no fusiona el código.

GitHub también ofrece **incidencias**, o *issues*, para registrar tareas o problemas, y flujos de automatización para ejecutar [comprobaciones y despliegues](/articulos/integracion-y-despliegue-continuos/).

Estas conversaciones y decisiones pertenecen a la plataforma. Clonar el repositorio con Git no descarga por sí solo todas sus incidencias, comentarios y revisiones. La historia del código y la historia de la colaboración están relacionadas, pero se almacenan como información diferente.

## Una colaboración sin cuentas ni conexión

Este ejemplo separa las operaciones de Git de los servicios de GitHub. Necesitas Git 2.28 o posterior y un editor de texto; los comandos funcionan en PowerShell y Bash.

Abre una terminal en una carpeta de prácticas donde no exista `practica-remotos`:

```bash
mkdir practica-remotos
cd practica-remotos
git init --bare -b main central.git
git clone central.git ana
cd ana
git config --local user.name "Ana de prueba"
git config --local user.email "ana@example.com"
```

`central.git` es un repositorio **bare**, sin carpeta de archivos para editar: recibe y conserva historia. `ana` es una copia con directorio de trabajo. El aviso de que has clonado un repositorio vacío es normal: todavía no hay commits.

Las identidades ficticias se configuran solo en esta copia. En `ana`, crea `notas.txt` con el editor y guarda esta línea como texto UTF-8:

```text
Comprar pan.
```

```bash
git add notas.txt
git commit -m "Crea la lista de compra"
git push -u origin main
```

El commit se creó en `ana`. `push` lo envía a `central.git` y actualiza allí `main`. `-u` vincula tu rama local con esa rama del remoto para futuras operaciones de seguimiento.

Crea ahora la copia de otra persona:

```bash
cd ..
git clone central.git luis
cd luis
git log --oneline
git show HEAD:notas.txt
```

Luis ve un commit con el mensaje `Crea la lista de compra` y el contenido `Comprar pan.`. Tiene los datos que Ana envió al central; no accede automáticamente a lo que Ana edite después en su carpeta.

## El mismo trabajo con GitHub

Si el remoto estuviera en GitHub, usarías su dirección y los permisos necesarios para intercambiar commits. El ciclo de guardar, preparar y confirmar seguiría ocurriendo en Git.

Un flujo habitual añade estos pasos:

1. Crear una rama para la tarea y confirmar los cambios.
2. Enviar esa rama al remoto con `push`.
3. Abrir una PR indicando la rama de destino y explicar el cambio.
4. Revisar la propuesta y sus comprobaciones; corregir lo necesario.
5. Fusionarla cuando cumpla los requisitos del repositorio.

Las diferencias entre las formas de integrar la historia se explican en [merge y rebase](/articulos/merge-y-rebase/), y el proceso humano en [revisión de código](/articulos/revision-de-codigo/). También puedes participar mediante la interfaz web de GitHub sin instalar Git en tu dispositivo: la plataforma sigue usando repositorios Git por debajo.

## Comparación

| Criterio | Git | GitHub |
| --- | --- | --- |
| Responsabilidad | Registrar e integrar versiones | Alojar repositorios y coordinar colaboración |
| Trabajo sin conexión | Commits y consulta de datos locales | Las funciones del servicio requieren acceso a él |
| Qué guarda | Objetos e historia del repositorio | Repositorios, PR, incidencias y otros datos de la plataforma |
| Cómo compartes | Operaciones como clone, fetch y push | Permisos, revisiones y flujos alrededor del repositorio |

## Cuándo necesitas cada uno

Git basta para llevar la historia de un proyecto local. Para colaborar necesitas intercambiar cambios, pero el remoto puede estar en distintos alojamientos; GitHub es una opción cuando sus herramientas encajan con el equipo.

No son alternativas equivalentes: elegir GitHub no elimina las operaciones de Git, y elegir Git no obliga a usar un alojamiento concreto.

## Confusiones frecuentes

- **Commit, push y PR como si fueran lo mismo.** El commit registra una versión; push la transmite; la PR propone integrarla.
- **Creer que push integra cualquier rama en main.** Actualiza las ramas que indique la operación y que el remoto permita; enviar una rama de trabajo no la fusiona automáticamente.
- **Suponer que clone es una copia de toda la plataforma.** Los comentarios y las incidencias necesitan sus propios mecanismos de exportación o copia.
- **Confundir un repositorio público con permiso para contribuir directamente.** Leerlo y poder enviar cambios a sus ramas son permisos distintos.

## Lo esencial

- Git registra versiones; GitHub añade alojamiento y colaboración.
- Un remoto puede ser otra carpeta, no necesariamente GitHub.
- Confirmar, enviar y proponer una integración son acciones diferentes.
- Clonar el código no copia automáticamente todos los datos de la plataforma.
