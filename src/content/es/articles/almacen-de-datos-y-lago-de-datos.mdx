Un **almacén de datos**, en inglés *data warehouse*, es una base de datos diseñada para **analizar**: reúne información de muchas fuentes, ya limpia y organizada, para responder preguntas de negocio. Un **lago de datos**, en inglés *data lake*, es un almacenamiento donde se guardan **todos los datos en bruto**, en su formato original, para procesarlos cuando haga falta.

## El punto de partida: no se analiza donde se opera

La [base de datos](/articulos/que-es-una-base-de-datos/) de una aplicación está pensada para su funcionamiento diario: muchas operaciones pequeñas y rápidas, crear un pedido, actualizar un saldo. Se llama **procesamiento transaccional**, u OLTP.

Analizar es otra cosa: pocas consultas, pero enormes. "Ventas por región y mes en los últimos cinco años, comparadas con el año anterior." Eso recorre millones de filas.

Lanzarlo contra la base de datos de producción la ralentiza para los usuarios. Además, la información está repartida: las ventas en una base, los clientes en el sistema comercial, las visitas en la analítica web. Hace falta un sitio aparte que lo reúna. Es el **procesamiento analítico**, u OLAP.

## Almacén de datos

Reúne datos de varias fuentes, los limpia, los unifica y los organiza para consultarlos. Llegan mediante [procesos ETL](/articulos/procesos-etl/).

### Esquema en estrella

La organización clásica no sigue la [normalización](/articulos/normalizacion-de-bases-de-datos/) de una base transaccional. Se diseña para que las consultas de análisis sean simples y rápidas.

- **Tabla de hechos**: los sucesos que se miden, con sus cifras. Cada venta: importe, unidades.
- **Tablas de dimensiones**: el contexto por el que se analiza. Cuándo, qué producto, qué cliente, qué tienda.

```
              Fecha
                │
Producto ── Ventas ── Tienda
                │
             Cliente
```

Las preguntas se responden uniendo los hechos con las dimensiones y agrupando: ventas por mes y por categoría de producto.

### Almacenamiento por columnas

Los almacenes guardan los datos **por columnas**, no por filas. Para sumar los importes de mil millones de ventas, solo hay que leer la columna del importe, no todo lo demás. Y una columna de valores parecidos se [comprime](/articulos/compresion-de-datos/) muy bien.

Para leer una fila entera es peor; para agregar una columna, mucho mejor.

## Lago de datos

En lugar de decidir de antemano qué guardar y cómo, se guarda **todo**: registros de servidores, eventos de la aplicación, [JSON](/articulos/formatos-de-datos-json-csv-xml/), imágenes, exportaciones de otras bases de datos. En su forma original, en un almacén de objetos barato de [la nube](/articulos/computacion-en-la-nube/).

La estructura se decide **al leer**, no al escribir. Se llama **esquema en lectura**, frente al **esquema en escritura** del almacén.

Los datos tabulares se guardan en formatos por columnas, como Parquet, que los motores de consulta leen de forma eficiente.

### El riesgo: un pantano

Guardar todo sin orden es fácil. Encontrar algo después, no. Un lago sin catálogo, sin dueños, sin saber qué significa cada archivo ni si está actualizado, se convierte en un **pantano de datos**: mucho volumen y poca utilidad.

## Comparación

| | Almacén de datos | Lago de datos |
| --- | --- | --- |
| Datos | Limpios y estructurados | En bruto, de cualquier tipo |
| Esquema | Se define al escribir | Se aplica al leer |
| Coste del almacenamiento | Más alto | Muy bajo |
| Usuarios | Analistas, informes de negocio | Ingenieros y científicos de datos |
| Fiabilidad | Alta: datos verificados | Variable |
| Flexibilidad | Baja: hay que decidir antes | Alta: se guarda todo |
| Uso típico | Cuadros de mando, informes | Exploración, [aprendizaje automático](/articulos/que-es-el-aprendizaje-automatico/) |

## Juntos

En la práctica se usan los dos. Los datos llegan primero al lago, tal cual. Desde ahí, se procesan y se cargan en el almacén lo que se va a consultar a menudo.

Las arquitecturas recientes, a veces llamadas **lakehouse**, intentan unir ambos: guardar en el almacenamiento barato del lago, con formatos de tabla que añaden transacciones, esquemas y versiones encima. Así se consulta con la fiabilidad de un almacén sin copiar los datos a otro sistema.

## Lo que cuesta

- **Calidad de datos.** Lo más difícil no es la tecnología, sino que los datos sean correctos y signifiquen lo mismo para todos. Que "cliente activo" se calcule igual en todos los informes.
- **Gobierno.** Saber quién puede ver qué, sobre todo con datos personales, sujetos al [RGPD](/articulos/rgpd-y-proteccion-de-datos/). Un lago con todo dentro es un riesgo si nadie controla el acceso.
- **Retraso.** Los datos del almacén suelen ir unas horas o un día por detrás de los de producción.

## Lo esencial

- Las bases de datos de las aplicaciones no sirven para análisis pesados: se analiza aparte.
- Un almacén de datos guarda información limpia y estructurada, organizada para consultar.
- Un lago de datos guarda todo en bruto, y la estructura se decide al leer.
- El almacén es más fiable; el lago, más barato y flexible.
- Un lago sin orden ni catálogo se vuelve inútil.
