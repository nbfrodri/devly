**ARP**, protocolo de resolución de direcciones, permite obtener la [dirección MAC](/articulos/que-es-una-direccion-mac/) asociada a una dirección IPv4 en el ámbito local. En IPv4 sobre Ethernet se utiliza para preparar la trama dirigida al siguiente destinatario: el equipo final si es local, o un router si hay que salir a otra red.

## Por qué hace falta

La tabla de rutas determina el siguiente salto mediante direcciones IP. Ethernet necesita además una MAC para construir la trama de [enlace](/articulos/capa-de-enlace/). ARP conecta esas dos decisiones sin cambiar la IP de destino del paquete.

## Cómo funciona

1. El equipo envía una **difusión local**: "¿quién tiene la IP 192.168.1.35? Dímelo a mí".
2. En este caso normal, el equipo que tiene esa IP responde al solicitante con su MAC. No está garantizado que llegue una respuesta ni que nadie responda falsamente.
3. El que preguntó **guarda** la respuesta en su **tabla ARP** durante un tiempo, para no preguntar cada vez.

La simulación siguiente usa una red conocida y respuestas inmediatas. Omite los tiempos de espera, la caducidad y las actualizaciones de la tabla real:

```js
const tablaArp = new Map();
const red = { "192.168.1.1": "aa:bb:cc:00:00:01", "192.168.1.35": "aa:bb:cc:00:00:35" };
let preguntas = 0;

function macDe(ip) {
	if (!tablaArp.has(ip)) {
		preguntas++; // difusión: "¿quién tiene esta IP?"
		if (!red[ip]) return null; // no se almacena una respuesta inexistente
		tablaArp.set(ip, red[ip]);
	}
	return tablaArp.get(ip);
}

macDe("192.168.1.35");
macDe("192.168.1.35");
console.log(macDe("192.168.1.1"), preguntas); // aa:bb:cc:00:00:01 2
console.log(macDe("192.168.1.99"), preguntas); // null 3
```

La segunda consulta a la misma IP sale de la tabla, sin preguntar a la red. En Linux, la tabla se consulta con `ip neigh`; su página de manual recuerda que la tabla de vecinos de IPv4 también se llama tabla ARP.

## Solo dentro de la red local

Los routers no reenvían estas preguntas ARP por internet. Si el destino es remoto y la ruta elegida pasa por `192.168.1.1`, se busca la MAC de ese router. La IP de destino del paquete sigue siendo la del servicio remoto; la MAC de la trama es la del siguiente salto.

Otros enlaces pueden utilizar tecnologías diferentes. Incluso en Ethernet puede bastar una entrada ya guardada, sin enviar una nueva pregunta por cada paquete. También existe proxy ARP, donde un router responde por otro destino; ARP no demuestra por sí solo dónde está conectado el dueño final de una IP.

## Su punto débil

ARP no autentica por sí mismo las asociaciones recibidas. Una respuesta falsa puede alterar la tabla y desviar o cortar tráfico: es el **envenenamiento ARP**. [HTTPS](/articulos/https-y-tls/) puede proteger el contenido y autenticar el extremo del intercambio aunque alguien observe el camino; no impide que ese intermediario bloquee la comunicación. El riesgo no es exclusivo de una wifi pública.

Si una IP cambia de interfaz y queda una asociación antigua, las tramas pueden dirigirse a una MAC equivocada hasta actualizar la entrada. Si nadie responde, no se puede completar esa entrega local mediante ARP. Ninguno de los dos síntomas demuestra por sí solo una avería del servidor remoto.

## Lo esencial

- ARP obtiene asociaciones entre IPv4 y MAC en el ámbito local.
- Una difusión solicita la asociación y la respuesta puede guardarse temporalmente.
- Para un destino remoto se resuelve la MAC del router local elegido, no la del servidor lejano.
- No tiene autenticación, lo que permite el envenenamiento ARP.
