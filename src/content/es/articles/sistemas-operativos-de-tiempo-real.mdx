Un **sistema operativo de tiempo real**, o **RTOS**, ofrece mecanismos de ejecución y planificación orientados a cumplir plazos. En un sistema de tiempo real, la corrección depende tanto del resultado como del momento en que llega. Instalar un RTOS no garantiza que cualquier conjunto de tareas llegue a tiempo.

## El tiempo forma parte del requisito

Supón un controlador que recibe periódicamente una medida y debe producir una orden. Una respuesta correcta, pero posterior al momento en que debía aplicarse, incumple el contrato.

El **plazo**, o *deadline*, indica cuándo debe estar terminado un trabajo. El **periodo** indica cada cuánto se activa una tarea periódica. No tienen por qué coincidir: una tarea que se activa cada 10 milisegundos puede tener que terminar en los primeros 3.

| Requisito | Qué significa incumplir |
| --- | --- |
| Tiempo real estricto | Incumplir el plazo es un fallo del requisito temporal |
| Tiempo real flexible | Un retraso puede reducir la calidad dentro de una tolerancia definida |

En audio, por ejemplo, perder un plazo puede causar un corte. Que un sistema sea estricto no significa que cada fallo cause una catástrofe: la gravedad pertenece a la aplicación. Tampoco todo dispositivo que controla algo necesita un RTOS; algunos utilizan otros diseños de ejecución.

## Un calendario que se puede comprobar

Usaremos un modelo de un solo procesador, dos tareas y tiempos hipotéticos:

| Tarea | Periodo | CPU que necesita como máximo | Plazo desde su activación |
| --- | --- | --- | --- |
| A, calcular una orden | 10 ms | 2 ms | 3 ms |
| B, preparar un registro | 10 ms | 4 ms | 9 ms |

Ambas se activan en 0, 10, 20… A tiene mayor prioridad. No comparten recursos que deban reservarse en exclusiva ni esperan dispositivos; primero omitimos el coste del sistema. El recorrido de cada periodo es:

1. A ejecuta de 0 a 2 y cumple su plazo de 3.
2. B ejecuta de 2 a 6 y cumple su plazo de 9.
3. De 6 a 10 queda capacidad libre.

Consumen `6 / 10 = 60 %` de CPU. Ahora añadimos una interferencia que retrasa el inicio de A: una interrupción que ocupa el procesador antes de que A pueda ejecutar. En este cálculo la agrupamos al principio y no añadimos ninguna otra interferencia.

```js
function plazos(interferencia) {
	if (!Number.isFinite(interferencia) || interferencia < 0) {
		throw new TypeError("La interferencia debe ser finita y no negativa");
	}
	const finA = interferencia + 2;
	const finB = finA + 4;
	return [finA <= 3, finB <= 9];
}

console.log(plazos(0).join(" ")); // "true true"
console.log(plazos(0.8).join(" ")); // "true true"
console.log(plazos(1.5).join(" ")); // "false true"
```

Con 0,8 ms, A termina en 2,8 y B en 6,8. Con 1,5 ms, A termina en 3,5: falla aunque el trabajo total del periodo, 7,5 ms, aún quepa en 10. **Capacidad media suficiente no demuestra que cada plazo se cumpla.**

Este código comprueba las cuentas del modelo. No mide latencias reales ni demuestra los plazos de un dispositivo. Para trasladarlo a una máquina habría que justificar los máximos de ejecución, las activaciones y todas las interferencias omitidas.

## Qué aporta el RTOS

Una política frecuente es **prioridad fija con expropiación**: entre tareas preparadas, ejecutar la de mayor prioridad y permitir que interrumpa a una inferior. FreeRTOS ofrece esa configuración y otras, con reparto por turnos entre prioridades iguales según sus opciones. Zephyr también permite tareas cooperativas y expropiativas; no hay un único algoritmo obligatorio para todos los RTOS.

«Elegir la de mayor prioridad» no significa latencia cero. Puede estar atendiendo una [interrupción](/articulos/interrupciones-y-entrada-salida/) o una sección que no puede interrumpirse todavía. Una tarea bloqueada tampoco ejecuta solo por tener alta prioridad.

El sistema proporciona temporizadores, estados de tareas y coordinación. Para obtener límites temporales útiles hay que controlar también reserva de memoria, esperas de dispositivos, cachés y tramos no interrumpibles. No toda operación de una biblioteca tiene un máximo adecuado para una tarea crítica.

## Inversión de prioridad

Imagina que una tarea de prioridad baja, L, tiene un **cerrojo** que protege un recurso. A lo necesita y queda esperando. Una tarea intermedia, M, puede adelantarse a L y retrasar todavía más a A, aunque M no utilice ese recurso. Es **inversión de prioridad**.

La **herencia de prioridad** puede elevar temporalmente a L para que avance y libere el recurso. Evita parte de la interferencia de M; no elimina el tiempo de la sección protegida, no resuelve un bloqueo mutuo ni demuestra por sí sola el plazo de A. Los protocolos y sus límites se estudian junto con [carreras y bloqueos](/articulos/condiciones-de-carrera-y-bloqueos/).

## Dónde encaja

Muchos RTOS se utilizan en un **[microcontrolador](/articulos/microcontrolador-y-microprocesador/)**, un circuito que integra procesador, memoria y periféricos para controlar dispositivos. Otros sistemas temporales son mayores y necesitan separación de procesos, red y almacenamiento.

Linux dispone de PREEMPT_RT para reducir tramos no expropiables y tratar más interrupciones mediante hilos planificables. Esa posibilidad tampoco concede una garantía universal: el hardware, los controladores, la configuración y la aplicación siguen formando parte del análisis.

## Errores comunes

- **Usar el promedio como límite.** Una medición rápida normalmente no acota el peor caso.
- **Confundir prioridad con disponibilidad.** Una tarea puede esperar un recurso que tiene otra.
- **Prometer plazos por el nombre del núcleo.** Deben justificarse para el sistema y la carga concretos.

## Lo esencial

- En tiempo real, el resultado debe llegar dentro de un plazo definido.
- El RTOS aporta mecanismos; la garantía depende del diseño completo.
- Hay que contar ejecución, esperas e interferencias, no solo uso medio de CPU.
- La herencia de prioridad reduce ciertos retrasos, pero no sustituye el análisis temporal.
