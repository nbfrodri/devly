Una **base de datos vectorial** es un sistema que guarda **vectores**, listas de números que representan el significado de un texto, una imagen u otro dato, y que responde con rapidez a una pregunta concreta: ¿cuáles de los vectores guardados se parecen más a este?

Esos vectores son [embeddings](/articulos/embeddings/). Las bases vectoriales son la pieza de búsqueda de muchas aplicaciones con [modelos de lenguaje](/articulos/modelos-de-lenguaje/).

## Qué problema resuelve

Muchas consultas tradicionales buscan coincidencias exactas o por rangos: el usuario con este identificador, los pedidos de marzo. Un [índice](/articulos/indices-de-bases-de-datos/) de árbol B aprovecha un orden por claves; hay otros tipos de índices y consultas.

La búsqueda por significado es otra cosa. Para "cómo devuelvo un pedido" hay que encontrar un texto que diga "política de reembolsos", sin ninguna palabra en común. Se convierten ambos en vectores y se busca el más cercano.

Ordenar por una coordenada no basta para localizar los vecinos en muchas dimensiones. Se pueden ordenar los vectores de varias maneras, pero eso no convierte un árbol B corriente en una solución eficaz para cualquier búsqueda de proximidad.

## La forma directa

Comparamos la consulta con todos los vectores y conservamos los mejores. El ejemplo utiliza vectores no nulos de dos coordenadas finitas y un número positivo de resultados; son valores inventados para mostrar la geometría, no embeddings obtenidos de un modelo.

```js
function coseno(a, b) {
	const producto = a.reduce((suma, x, i) => suma + x * b[i], 0);
	return producto / (Math.hypot(...a) * Math.hypot(...b));
}

const vectores = [
	{ id: "gato", vector: [0.9, 0.1] },
	{ id: "perro", vector: [0.8, 0.3] },
	{ id: "coche", vector: [0.1, 0.9] },
];

function masCercanos(consulta, cuantos) {
	return vectores
		.map((v) => ({ id: v.id, parecido: coseno(consulta, v.vector) }))
		.toSorted((a, b) => b.parecido - a.parecido)
		.slice(0, cuantos)
		.map((v) => v.id);
}

console.log(masCercanos([1, 0.2], 2).join(" ")); // "gato perro"
```

Es una búsqueda **exacta** respecto a la similitud calculada: examina todos los vectores. Eso no demuestra que los resultados sean relevantes para una persona; la aritmética también tiene precisión finita. Aquí gato obtiene una similitud aproximada de 0,996 y perro de 0,987, por eso quedan en ese orden.

Con N vectores de d dimensiones, calcular las similitudes cuesta O(N·d). Este ejemplo además ordena N resultados, con un coste habitual O(N log N); existen formas de seleccionar solo los mejores sin ordenarlos todos. A gran escala ese trabajo puede superar el presupuesto de tiempo.

## La idea: aproximar

Muchos sistemas ofrecen tanto búsqueda exacta como **aproximada** de vecinos más cercanos. La aproximada utiliza índices para explorar menos candidatos, con el riesgo de omitir alguno de los vecinos reales.

Aceptar esa omisión depende del uso. Para algunos sistemas de recomendación puede compensar; para otros requisitos hay que aumentar la exhaustividad o utilizar búsqueda exacta. Se mide sobre consultas representativas.

La calidad se mide con la **exhaustividad**: qué proporción de los verdaderos vecinos más cercanos se ha encontrado. Un 95 % significa que, de los 10 mejores reales, la búsqueda devuelve de media 9,5.

## Cómo se construyen los índices

### Un grafo navegable

El método más extendido, llamado HNSW, organiza los vectores en un [grafo](/articulos/grafos/): cada vector se conecta con algunos de sus vecinos cercanos.

La búsqueda empieza en las capas superiores con saltos hacia puntos más cercanos. En la capa inferior explora un conjunto de candidatos y mantiene vecinos prometedores; no es simplemente una única cadena de saltos que termina en el primer mínimo local.

Para no dar miles de pasos pequeños, hay varias capas. Las superiores tienen pocos vectores y conexiones largas, que cruzan el espacio de un salto. Las inferiores, todos los vectores y conexiones cortas. Se empieza arriba, se llega deprisa a la zona adecuada y se baja para afinar.

Se parece a orientarse en un viaje: primero autopista, luego carretera, al final calles.

- **A favor:** rápido y con buena exhaustividad.
- **En contra:** ocupa mucha memoria y tarda en construirse.

### Agrupar

Otro método divide los vectores en grupos de vectores parecidos. Al buscar, se localizan los grupos más cercanos a la consulta y solo se miran esos.

- **A favor:** menos memoria, construcción más rápida.
- **En contra:** si el vecino buscado quedó en un grupo que no se revisa, se pierde.

### Comprimir

Con 1536 componentes de 32 bits, un vector ocupa 6144 bytes (6 KiB). Cien millones ocupan 614,4 GB decimales solo en componentes, antes de sumar índices, identificadores y metadatos. La **cuantización** los guarda con menos precisión, o resumidos. Se pierde algo de exactitud y se gana mucho espacio.

## El compromiso

Todos los índices tienen parámetros que mueven el mismo equilibrio:

| Si se quiere más | Se paga con |
| --- | --- |
| Exhaustividad | Consultas más lentas o más memoria |
| Velocidad | Menos exhaustividad |
| Ahorro de memoria | Menos exhaustividad o menos velocidad |

No hay un ajuste universal. Se prueba con datos y consultas reales.

## Cómo se mide el parecido

| Medida | Qué compara |
| --- | --- |
| Similitud del coseno | La dirección de los vectores, sin importar su longitud |
| Producto escalar | Dirección y longitud |
| Distancia euclídea | La separación en línea recta |

Hay que usar la medida con la que se entrenó el modelo de embeddings. Su documentación lo indica.

Los vectores de consulta y documentos deben pertenecer a un **espacio compatible**. Tener la misma dimensión no basta. Lo habitual es usar la misma versión y configuración de embeddings, o codificadores distintos entrenados para compartir espacio. Una migración a un espacio incompatible exige recalcular los vectores que se quieran comparar.

## Filtros

Casi nunca se busca en todo. Se busca "documentos parecidos a este, **de este cliente**, **de este año**". Cada vector lleva asociados unos **metadatos**, y la consulta combina parecido y filtro.

Hacerlo bien es difícil:

- Filtrar **después** de buscar puede dejar sin resultados: los diez más parecidos eran todos de otro cliente.
- Filtrar **antes** puede inutilizar el índice.

Cómo resuelve esto cada sistema es una de las diferencias reales entre ellos. Si hay documentos con permisos distintos, la autorización debe aplicarse en el servidor y cubrir los candidatos devueltos. Un filtro enviado libremente por el cliente no constituye por sí solo una barrera de acceso.

## Opciones

- **Bases vectoriales dedicadas.** Diseñadas para esto, pensadas para volúmenes muy grandes.
- **Extensiones de bases existentes.** `pgvector` añade vectores a [PostgreSQL](/articulos/que-es-postgresql/). Los vectores viven junto al resto de los datos, con transacciones, [JOIN](/articulos/tipos-de-join/) y permisos.
- **Bibliotecas**, que construyen el índice en memoria dentro de tu programa.
- **Buscadores de texto** que han añadido vectores.

## ¿Hace falta una?

A menudo, no.

- **Con un conjunto pequeño**, mide primero una búsqueda exacta: puede satisfacer el requisito sin mantener otro índice.
- **Si ya se usa PostgreSQL**, evalúa `pgvector` con tus dimensiones, filtros, carga y objetivos de latencia. No hay un umbral universal por número de vectores.
- **Una base dedicada** compensa con volúmenes muy grandes o exigencias de rendimiento altas.

Añadir un sistema significa mantener dos copias de los datos al día. Es un coste real.

## Sus límites

- **La búsqueda por significado no encuentra bien lo exacto**: códigos, nombres propios, siglas. Por eso se combina con la búsqueda por palabras, como explica el artículo sobre [RAG](/articulos/generacion-aumentada-por-recuperacion/).
- **Depende del modelo de embeddings.** La base encuentra los vectores cercanos; que "cercano" signifique "relevante" es cosa del modelo.
- **Las actualizaciones cuestan.** Insertar y borrar en algunos índices es lento o los degrada.
- **Resultados que varían** un poco, al ser aproximados.

## Errores comunes

- **Confundir vecino geométrico y respuesta pertinente.** Una buena exhaustividad del índice no corrige embeddings inadecuados.
- **Mezclar espacios porque tienen igual dimensión.** Las coordenadas pueden representar cosas diferentes y producir distancias sin utilidad.
- **Medir solo consultas sin filtros.** Los permisos y metadatos pueden cambiar tanto el coste como los resultados disponibles.

## Lo esencial

- Una base de datos vectorial guarda embeddings y busca los más parecidos a uno dado.
- La búsqueda exacta y la aproximada tienen costes y garantías diferentes; se eligen según la carga y la calidad requerida.
- Los índices, como los grafos navegables, miran solo una pequeña parte de los datos.
- Hay un equilibrio entre exhaustividad, velocidad y memoria.
- Con pocos vectores, o con PostgreSQL ya en uso, puede no hacer falta un sistema aparte.
