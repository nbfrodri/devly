Un **compilador** traduce código a otra representación, como código máquina o bytecode. Un **intérprete** ejecuta las operaciones descritas por una representación del programa, como un árbol sintáctico o bytecode. La diferencia es qué hace cada etapa; una herramienta puede combinar ambas, incluso compilar mientras el programa se está ejecutando.

## El problema de fondo

Un [procesador](/articulos/como-funciona-un-procesador/) solo entiende **código máquina**: instrucciones muy simples escritas en binario, distintas para cada familia de procesadores.

Las personas programamos en lenguajes de alto nivel, con variables, funciones y nombres legibles. Algo tiene que salvar la distancia entre lo que escribimos, el **[código fuente](/articulos/que-es-el-codigo-fuente/)**, y lo que la máquina ejecuta. Compilar e interpretar son las dos estrategias básicas.

## Una analogía

Tienes un libro escrito en un idioma que tu público no entiende.

- **Preparar una traducción** que se podrá leer después. Se parece a compilar por adelantado.
- **Contratar a un intérprete** que comunique su contenido durante la lectura. Se parece a ejecutar mediante un intérprete.

La analogía explica la separación entre preparar una representación y usarla. No demuestra cuál será más rápido ni obliga a traducir todo el libro de una vez.

## El compilador

En una cadena de compilación **por adelantado**, el código fuente se traduce y se enlaza para producir un [binario](/articulos/que-es-un-binario/). Puede ejecutarse sin el compilador ni el fuente, aunque quizá necesite bibliotecas y un entorno de ejecución compatibles. No todos los compiladores producen directamente un ejecutable: también pueden generar archivos objeto, bytecode u otro lenguaje.

Las implementaciones habituales de C, C++, Rust y Go usan compilación por adelantado a código nativo.

**Ventajas:**

- **Ejecución nativa.** Evita interpretar cada operación. Las optimizaciones pueden reducir trabajo, pero el rendimiento depende del programa y de la implementación.
- **Comprobaciones previas.** Puede detectar errores de sintaxis y, según el lenguaje y las comprobaciones implementadas, de tipos. No descubre todos los fallos.
- **Se distribuye sin el código fuente.**

**Inconvenientes:**

- **Hay un paso previo.** Tras cada cambio hay que compilar antes de probar.
- **El ejecutable tiene un destino.** Necesita instrucciones e interfaces compatibles. Para otro destino puede hacer falta recompilar o usar una capa de traducción; compartir «64 bits» no basta.

## El intérprete

Un intérprete ejecuta el programa a partir de una representación que entiende. Puede recibir texto ya analizado, un árbol o bytecode; no necesariamente vuelve a leer el fuente línea por línea. Hace falta el intérprete compatible, pero el fuente original puede no ser necesario si se distribuye la representación intermedia.

**Ventajas:**

- **Ciclo de trabajo breve.** La herramienta puede analizar y ejecutar sin que el usuario gestione una compilación separada. Ese análisis también consume tiempo.
- **Portabilidad del programa.** Se puede reutilizar en entornos con un intérprete compatible, siempre que también lo sean sus bibliotecas, archivos y dependencias del sistema.
- **Interactividad.** Permite ejecutar una línea, ver el resultado y seguir.

**Inconvenientes:**

- **Coste de interpretación.** Despachar operaciones añade trabajo, aunque una operación puede llamar a una biblioteca nativa muy rápida.
- **Errores durante la ejecución.** Algunos solo aparecen al recorrer un caso concreto. Otros, como un error de sintaxis, pueden detectarse antes de ejecutar la primera instrucción.
- **Quien ejecuta necesita el intérprete instalado.**

## Comparación

| | Compilador | Intérprete |
| --- | --- | --- |
| Trabajo principal | Generar otra representación | Ejecutar las operaciones de una representación |
| Resultado | Código máquina, bytecode u otro código | Efectos y resultados de la ejecución |
| Momento | Por adelantado o durante la ejecución, con JIT | Durante la ejecución |
| Coste característico | Traducción y posibles optimizaciones | Despacho de las operaciones interpretadas |
| Portabilidad | Depende del formato y destino generado | Depende del intérprete y del entorno disponibles |
| Errores | Las comprobaciones dependen del lenguaje y la herramienta | Puede haber análisis previo y comprobaciones al ejecutar |

### La misma suma en dos recorridos

Para `2 + 3`, un compilador puede generar una instrucción que cargue `5`, calculando la suma durante la traducción. Un intérprete de árboles puede visitar los nodos `2` y `3` y aplicar la suma al ejecutar. Ambos deben producir `5`: cambia dónde se realiza el trabajo. Un compilador también podría generar una suma, y un intérprete podría recibir un árbol ya simplificado.

Al elegir una implementación, importan el tiempo de arranque, el trabajo repetido, los destinos de distribución y el entorno disponible. Un servicio que ejecuta millones de veces una función puede amortizar una optimización que no compensa en un guion de una sola ejecución. Hay que medir ese caso, no deducir el resultado de la etiqueta.

## La realidad está en medio

Muchas implementaciones combinan traducción y ejecución mediante dos mecanismos.

### Bytecode y máquina virtual

El código fuente puede compilarse a un lenguaje intermedio, el **bytecode**. Sus operaciones se definen para una máquina abstracta; no se eligen necesariamente como instrucciones de la CPU del equipo.

Después, un programa llamado **máquina virtual** ejecuta ese bytecode. Algunas implementaciones también compilan durante la ejecución, como explica [cómo ejecuta JavaScript un motor como V8](/articulos/motores-de-javascript-y-jit/). Separar las etapas permite reutilizar el análisis previo; la portabilidad exige una máquina virtual y unas dependencias compatibles.

Java suele compilarse a bytecode para la JVM. CPython, una implementación de Python, también genera bytecode y lo ejecuta en su máquina virtual. Ese bytecode no es un formato universal: su compatibilidad depende de la implementación y de la versión.

### Compilación en tiempo de ejecución

Un compilador **JIT** (*just in time*) traduce a código máquina mientras el programa ya está funcionando.

En un motor por niveles, puede empezar interpretando para arrancar pronto y compilar después partes usadas con frecuencia. No todo JIT sigue esa política. Al observar la ejecución, puede usar información de los valores y caminos reales para especializar código, con comprobaciones para abandonar una optimización cuando sus supuestos dejan de cumplirse.

Así trabajan los motores de JavaScript de los navegadores, y también las máquinas virtuales de Java y de C#.

## Es cosa de la implementación

"Lenguaje compilado" y "lenguaje interpretado" son atajos. Compilar o interpretar es una propiedad de la **herramienta** que ejecuta el lenguaje, no del lenguaje en sí. Para un mismo lenguaje pueden existir compiladores e intérpretes.

## Otras traducciones

- **Transpilador.** Traduce entre lenguajes de un nivel parecido. El de [TypeScript](/articulos/que-es-typescript/) produce JavaScript.
- **Enlazador.** Conecta las partes compiladas y sus referencias. Puede producir un ejecutable o una biblioteca, incorporar código y dejar dependencias compartidas que se resuelven al ejecutar.

## Qué ocurre dentro

Muchas cadenas de compilación e interpretación comparten fases, que detalla con un compilador de juguete [cómo funciona un compilador por dentro](/articulos/como-funciona-un-compilador-por-dentro/):

1. **Análisis léxico.** El texto se divide en piezas con significado, llamadas *tokens*: palabras clave, nombres, números, símbolos.
2. **Análisis sintáctico.** Se reconoce la estructura del programa y puede representarse como un árbol sintáctico: operaciones con expresiones subordinadas. No es un árbol binario de búsqueda.
3. **Análisis semántico.** Se aplican las comprobaciones previas que permita el lenguaje, por ejemplo sobre nombres o [tipos](/articulos/tipado-estatico-y-dinamico/). Otras comprobaciones pueden quedar para la ejecución.

A partir de ahí, una etapa puede generar otra representación y otra puede ejecutarla. La organización concreta varía; no todas las herramientas construyen un árbol ni mantienen estas fases separadas.

## Confusiones frecuentes

- **Equiparar compilación y tipado estático.** Una traducción puede conservar comprobaciones de tipos para la ejecución; un intérprete puede ejecutar código previamente verificado.
- **Dar por portátil cualquier fuente interpretado.** Una llamada exclusiva de un sistema operativo no se vuelve universal por usar un intérprete.
- **Atribuir todos los errores a una fase.** Una división problemática o un archivo ausente dependen de datos y condiciones que pueden aparecer después de compilar.

## Lo esencial

- Un compilador genera otra representación; un intérprete ejecuta sus operaciones.
- Rendimiento, comprobaciones y portabilidad dependen de la implementación y del entorno.
- Bytecode y JIT permiten combinar etapas de compilación e interpretación.
- Es una característica de la herramienta, no del lenguaje.
