Un **archivo binario** organiza sus bytes según un formato que no se interpreta solo como texto. Puede ser una imagen, una base de datos o un programa. En una descarga, **el binario** suele significar la versión compilada del programa, lista para un entorno compatible.

La palabra no garantiza que sea ejecutable ni que funcione en tu equipo. Aquí seguiremos un **ejecutable nativo**: contiene instrucciones para una CPU concreta. Otros programas se distribuyen como scripts o bytecode y necesitan un intérprete o una máquina virtual.

## Texto y binario usan bytes

Todos los [archivos](/articulos/que-es-un-archivo/) contienen [bytes](/articulos/que-es-un-byte/). En el texto, una [codificación](/articulos/codificacion-de-caracteres/) indica cómo interpretarlos como caracteres. El editor debe reconocerla para mostrarlos correctamente.

En una imagen PNG, unos bytes identifican el formato, otros describen dimensiones y otros contienen datos comprimidos. Puede incluir fragmentos de texto, pero leerlo todo como letras no reconstruye la imagen. Cambiar `.png` por `.txt` tampoco transforma su contenido.

Los formatos permiten que distintos programas interpreten la misma secuencia. Un ejecutable añade instrucciones y datos de carga para que el sistema prepare su ejecución.

## Del código fuente a las instrucciones

Este programa C calcula el doble de siete:

```c
#include <stdio.h>

int doble(int x) {
	return x * 2;
}

int main(void) {
	printf("%d\n", doble(7));
	return 0;
}
```

En Linux con GCC, guarda el texto como `doble.c`, compílalo con `gcc -O2 doble.c -o doble` y ejecuta `./doble`. Imprime `14`. El ejemplo utiliza un valor cuyo doble cabe en `int`; una multiplicación con signo que desbordase no tendría ese comportamiento garantizado en C.

Una posible traducción de la función `doble` para x86-64 con la convención System V es:

| Bytes, en hexadecimal | Ensamblador, sintaxis Intel | Efecto |
| --- | --- | --- |
| `8d 04 3f` | `lea eax, [rdi + rdi]` | Calcula el doble y guarda los 32 bits inferiores en `eax` |
| `c3` | `ret` | Devuelve el control a quien llamó |

Al entrar, el argumento ocupa `edi`, la parte inferior de `rdi`; al salir, el resultado está en `eax`. `lea` realiza aritmética de direcciones **sin leer memoria**. En este caso sirve para sumar el argumento consigo mismo. La [ABI](/articulos/que-es-una-abi/) fija cómo pasan los argumentos y resultados; otras convenciones usan otros registros.

El **ensamblador** es una representación legible de las instrucciones. El procesador consume sus bytes. El compilador podría elegir otra secuencia o calcular `doble(7)` por adelantado dentro de `main`: la tabla muestra una traducción posible de la función, no todo el ejecutable.

## Qué necesita el sistema para cargarlo

Los cuatro bytes anteriores no bastan para crear un programa que el sistema pueda abrir. Un formato ejecutable incluye información adicional:

1. **Cabecera:** identifica el formato, la arquitectura y otras propiedades.
2. **Código y datos:** las instrucciones, constantes y valores iniciales.
3. **Información de carga:** qué partes colocar en memoria y con qué permisos.
4. **Entrada y dependencias:** dónde empezar y qué componentes externos resolver.

En **ELF**, habitual en Linux, las **secciones** organizan contenido para herramientas como el enlazador; los **segmentos** describen agrupaciones utilizadas al cargarlo. No son dos nombres para lo mismo. **PE** es el formato utilizado por ejecutables y bibliotecas de Windows. Compartir formato tampoco basta: un ELF puede contener instrucciones x86-64 o AArch64, por ejemplo.

La diferencia entre [x86 y Arm](/articulos/arquitecturas-x86-y-arm/) afecta al código nativo. No hace que una foto PNG sea exclusiva de una CPU: basta un lector compatible. El recorrido de [ejecutable a proceso](/articulos/del-ejecutable-al-proceso/) desarrolla cómo el sistema prepara memoria y ejecución.

## Reconocer una firma no valida el archivo

Muchos formatos empiezan con una **firma de formato**, también llamada número mágico. ELF comienza con cuatro bytes: `7f 45 4c 46`. PNG utiliza ocho: `89 50 4e 47 0d 0a 1a 0a`.

Este ejemplo recibe un array de bytes e identifica esos prefijos. No comprueba el resto del archivo:

```js
const NUMEROS_MAGICOS = [
	{ formato: "ELF", bytes: [0x7f, 0x45, 0x4c, 0x46] },
	{ formato: "PNG", bytes: [0x89, 0x50, 0x4e, 0x47, 0x0d, 0x0a, 0x1a, 0x0a] },
];

function identificar(primeros) {
	const encontrado = NUMEROS_MAGICOS.find((m) => m.bytes.every((b, i) => primeros[i] === b));
	return encontrado?.formato ?? "desconocido";
}

console.log(identificar([0x7f, 0x45, 0x4c, 0x46])); // "ELF"
console.log(identificar([0x89, 0x50, 0x4e, 0x47])); // "desconocido"
console.log(identificar([0x89, 0x50, 0x4e, 0x47, 0x0d, 0x0a, 0x1a, 0x0a])); // "PNG"
```

La segunda entrada está truncada: faltan cuatro bytes de la firma PNG. La tercera tiene la firma completa, pero sigue sin contener una imagen. Para validarla harían falta sus bloques obligatorios y otras comprobaciones. La orden `file` utiliza firmas y más reglas de inspección; no se limita a mirar la extensión ni a esta función.

## Bibliotecas: enlazado estático y dinámico

El programa anterior usa `printf`, una función de biblioteca. El **enlazador** conecta referencias del código con sus definiciones. Puede incorporar código de biblioteca al resultado o dejar dependencias que se resuelven durante la ejecución.

| Criterio | Enlazado estático | Enlazado dinámico |
| --- | --- | --- |
| Código de esa biblioteca | Se incorpora al resultado | Permanece en un componente compartido |
| Distribución | No necesita cargar por separado esa biblioteca | Necesita encontrar una versión compatible |
| Tamaño del ejecutable | Puede crecer al incorporar código | Puede ser menor; la dependencia también ocupa espacio |
| Actualización | Hay que volver a enlazar y distribuir el resultado | Puede sustituirse la biblioteca si conserva la compatibilidad necesaria |

Se pueden mezclar ambas formas. Incluso un programa enlazado estáticamente depende del sistema, sus interfaces y quizá archivos de datos o servicios. «Estático» no significa autosuficiente en cualquier máquina.

En Linux, el cargador dinámico busca las bibliotecas requeridas al arrancar; si no encuentra una necesaria, el inicio falla. Un programa también puede cargar bibliotecas más tarde, por ejemplo mediante `dlopen`. Que una actualización mantenga el nombre del archivo no garantiza la misma ABI ni el mismo comportamiento.

## Binarios y confianza

La **firma de formato** no es una **firma digital**. La primera ayuda a reconocer una estructura; la segunda permite comprobar autoría e integridad respecto a una clave en la que confías. Un [hash](/articulos/funciones-hash/) permite comparar contenido con un valor esperado, pero no autentica a su autor si el valor esperado también procede de una fuente manipulada.

Un binario puede analizarse mediante [ingeniería inversa](/articulos/ingenieria-inversa/), aunque no conserve el fuente original. Una compilación reproducible permite contrastar un resultado con unas fuentes y herramientas declaradas; no demuestra que el programa carezca de fallos. Al ejecutarlo actúa con los permisos y restricciones de su entorno.

## Errores comunes

- **Equiparar archivo binario y ejecutable.** Una imagen también es binaria y no contiene necesariamente instrucciones de CPU.
- **Elegir solo por «64 bits».** Importan ISA, formato, ABI, bibliotecas y sistema operativo.
- **Confundir identificación con seguridad.** Un prefijo correcto no demuestra validez, autenticidad ni ausencia de comportamiento dañino.

## Lo esencial

- Un formato da significado a los bytes; no todo binario es un programa.
- Un ejecutable nativo combina instrucciones con información para cargarlo.
- Reconocer una firma de formato no valida el archivo ni su compatibilidad.
- El enlazado determina cómo se incorporan o resuelven bibliotecas, con dependencias y límites en ambos casos.
