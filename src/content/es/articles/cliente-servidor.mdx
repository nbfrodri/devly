El **modelo cliente-servidor** es una forma de organizar una aplicación en dos tipos de programas: los **clientes**, que piden cosas, y los **servidores**, que las ofrecen. Casi todo lo que usas en internet funciona así.

## Qué problema resuelve

Imagina una red social en la que cada persona tuviera en su móvil una copia de todas las publicaciones. Las copias no coincidirían, ocuparían demasiado y nadie podría fiarse de los datos de otro.

Una solución es concentrar la gestión de los datos y las reglas en un servicio al que se conectan los clientes. Ese servicio puede ejecutarse en varias máquinas. Facilita aplicar reglas comunes, pero la consistencia de las copias y la seguridad siguen necesitando un diseño explícito.

## Los dos papeles

Un **cliente** es el programa que inicia la comunicación. Suele ser lo que tienes delante: el navegador o una aplicación del móvil. Se encarga de mostrar la información y de recoger lo que haces.

Un **servidor** es un programa que espera peticiones y las responde. Guarda los datos, aplica las reglas y decide qué puede ver cada cliente.

"Servidor" se usa para dos cosas: el programa y la máquina donde se ejecuta. Lo que define a un servidor es el papel que cumple, no el tipo de ordenador. Tu propio portátil hace de servidor cuando desarrollas una web en él.

## Un intercambio completo

Esto es lo que ocurre cuando consultas tus pedidos en una tienda en línea:

1. Pulsas "Mis pedidos". El cliente prepara una petición.
2. La petición viaja por la red hasta el servidor mediante [HTTP](/articulos/que-es-http/).
3. El servidor comprueba quién eres y si tienes permiso: son la [autenticación y la autorización](/articulos/autenticacion-y-autorizacion/).
4. Consulta los pedidos en la [base de datos](/articulos/que-es-una-base-de-datos/).
5. Prepara una respuesta con esos datos y la envía.
6. El cliente la recibe y la muestra en pantalla.

En este intercambio HTTP, el cliente solicita el recurso y el servidor responde. Eso no impide que, después de establecer un canal como [WebSocket](/articulos/websockets/), el servidor envíe novedades sin una petición nueva por cada mensaje.

## Frontend y backend

En desarrollo web, estas dos mitades tienen nombre:

- **Frontend**: la interfaz con la que interactúa el usuario. En la web utiliza [HTML](/articulos/que-es-html/), [CSS](/articulos/que-es-css/) y JavaScript. Parte de su preparación puede ejecutarse en el servidor, como ocurre al generar HTML antes de enviarlo.
- **Backend**: el código que se ejecuta en el servidor. Gestiona datos, usuarios y reglas.

Quien trabaja en las dos partes se llama desarrollador **full stack**.

Dentro del backend, una forma muy extendida de organizar el código es el [patrón MVC](/articulos/patron-mvc/).

El frontend y el backend se comunican a través de una [API](/articulos/que-es-una-api/): el conjunto de peticiones que el servidor acepta.

## Por qué no fiarse del cliente

El cliente se ejecuta en el dispositivo de cada persona, que puede modificarlo o enviar peticiones hechas a mano. Por eso hay una regla básica: **todo lo que importa se comprueba en el servidor**.

Si una web oculta el botón de borrar a quien no es administrador, eso es una comodidad, no una protección. La protección es que el servidor rechace la petición de borrado cuando no viene de un administrador.

## Muchos clientes a la vez

Un servidor atiende a muchos clientes simultáneamente. Cuando las peticiones superan lo que una máquina puede procesar, hay dos salidas: usar una máquina más potente o repartir el trabajo entre varias. Repartirlo es lo que permite que servicios muy grandes sigan funcionando con millones de usuarios, y resulta mucho más fácil si los servidores no guardan nada entre peticiones, es decir, si son [stateless](/articulos/stateful-y-stateless/).

## No es el único modelo

En una red **entre pares** o *peer-to-peer* no hay un servidor central: cada participante hace de cliente y de servidor a la vez. Se usa, por ejemplo, para compartir archivos. La mayoría de las aplicaciones web, sin embargo, siguen el modelo cliente-servidor.

## Errores comunes

- **Equiparar servidor con una máquina especial.** El papel lo cumple un programa; una misma máquina puede alojar clientes y servidores.
- **Confiar en un botón oculto para proteger una operación.** El cliente puede modificarse, por lo que el servicio debe comprobar permisos al recibir la petición.
- **Suponer que un servicio central garantiza datos idénticos en todo momento.** Puede haber réplicas y cachés con estados distintos.

## Lo esencial

- El cliente pide y muestra; el servidor guarda, decide y responde.
- En una petición HTTP, el cliente inicia el intercambio y el servidor responde.
- El frontend presenta la interfaz; el backend atiende servicios y aplica reglas.
- Las comprobaciones de seguridad se hacen en el servidor.
