**MongoDB** es una base de datos que guarda la información en **documentos**, estructuras parecidas a [JSON](/articulos/formatos-de-datos-json-csv-xml/), en lugar de en filas y tablas. Es la más conocida de las [bases de datos NoSQL](/articulos/bases-de-datos-nosql/) de documentos.

## Qué problema resuelve

En una base relacional, un pedido con sus líneas y su dirección de envío se reparte en varias tablas. Para leerlo completo hay que reunirlas con [JOIN](/articulos/tipos-de-join/), y para guardarlo, descomponer el objeto del programa en filas.

En MongoDB se guarda como está: un documento con todo dentro.

```javascript
{
	_id: ObjectId("6710a1f2c3d4e5f6a7b8c9d0"),
	cliente: "Ana",
	fecha: ISODate("2026-10-14"),
	direccion: { calle: "Mayor 1", ciudad: "Madrid" },
	lineas: [
		{ producto: "Teclado", cantidad: 1, precio: 40 },
		{ producto: "Ratón", cantidad: 2, precio: 15 }
	]
}
```

Leer el pedido es una sola operación, y la forma del dato coincide con la que tiene en el código.

## Los conceptos

| MongoDB | Equivalente relacional |
| --- | --- |
| Base de datos | Base de datos |
| Colección | Tabla |
| Documento | Fila |
| Campo | Columna |
| Documento incrustado | Tablas unidas con JOIN |

Cada documento tiene un campo `_id` único. Si no se indica, MongoDB lo genera.

Por dentro, los documentos se guardan en **BSON**, una versión binaria de JSON con más tipos, como fechas y números de distinta precisión.

## Esquema flexible

Los documentos de una colección no tienen que tener los mismos campos. Uno puede tener `telefono` y otro no, sin declarar nada antes.

Es cómodo cuando los datos varían o el modelo todavía está cambiando. Pero el esquema no desaparece: **se traslada al código**. La aplicación tiene que saber qué campos puede encontrar, y convivir con documentos antiguos que tienen otra forma.

Para evitar el desorden, MongoDB permite definir **reglas de validación** que los documentos deben cumplir. Usarlas es recomendable.

## Consultar

Las consultas no se escriben en [SQL](/articulos/que-es-sql/), sino como documentos que describen lo que se busca:

```javascript
db.productos.find({ precio: { $lt: 100 }, etiquetas: "oficina" });
```

"Productos con precio menor que 100 y con la etiqueta oficina". Los operadores empiezan por `$`.

La lógica equivale a este filtro:

```js
const productos = [
	{ nombre: "Teclado", precio: 40, etiquetas: ["oficina"] },
	{ nombre: "Monitor", precio: 180, etiquetas: ["oficina", "imagen"] },
	{ nombre: "Auriculares", precio: 60, etiquetas: ["audio"] },
];

const encontrados = productos.filter(
	(p) => p.precio < 100 && p.etiquetas.includes("oficina"),
);

console.log(encontrados.map((p) => p.nombre).join(" ")); // "Teclado"
```

Como en cualquier base de datos, sin un [índice](/articulos/indices-de-bases-de-datos/) sobre los campos consultados, hay que recorrer la colección entera.

### Agregaciones

Para agrupar, calcular y transformar se usa una **canalización de agregación**: una serie de etapas, donde cada una recibe los documentos de la anterior.

```javascript
db.pedidos.aggregate([
	{ $match: { estado: "pagado" } },
	{ $group: { _id: "$cliente", total: { $sum: "$importe" } } },
	{ $sort: { total: -1 } }
]);
```

Filtra los pedidos pagados, suma el importe por cliente y ordena de mayor a menor. Es la misma idea que encadenar órdenes en una [terminal](/articulos/terminal-y-shell/).

## La decisión clave: incrustar o referenciar

Al diseñar, hay que decidir cómo representar las relaciones.

- **Incrustar.** Los datos relacionados van dentro del documento, como las líneas dentro del pedido.
- **Referenciar.** Se guarda el identificador de otro documento, como una clave foránea.

| | Incrustar | Referenciar |
| --- | --- | --- |
| Lectura | Una operación | Varias, o una unión |
| Datos repetidos | Posibles | No |
| Actualizar un dato compartido | En cada copia | En un solo sitio |
| Conviene cuando | Se leen juntos y pertenecen al padre | Se comparten o crecen sin límite |

La regla del modelado en MongoDB es **diseñar según cómo se va a consultar**: lo que se lee junto, se guarda junto. Es lo contrario de la [normalización](/articulos/normalizacion-de-bases-de-datos/) relacional, que parte de la estructura de los datos y no de su uso.

Un documento tiene un tamaño máximo de 16 megabytes. Una lista que crece sin fin, como los comentarios de una publicación muy popular, no se incrusta.

## Repartirse entre máquinas

MongoDB se diseñó para funcionar en varias máquinas.

- **Conjuntos de réplicas.** Varias copias de los datos. Una acepta las escrituras; si falla, las demás eligen otra automáticamente.
- **Particionado.** Los datos se reparten entre máquinas según una **clave de partición**. Viene incluido.

Lo que eso implica se explica en [replicación y particionado](/articulos/replicacion-y-particionado/). Elegir mal la clave de partición es difícil de corregir después.

## Transacciones

Modificar un solo documento siempre ha sido atómico. Como un documento puede contener todo un pedido, muchas operaciones no necesitan más.

Las [transacciones](/articulos/transacciones-y-acid/) que abarcan varios documentos existen desde la versión 4.0. Funcionan, con un coste de rendimiento. Si un diseño las necesita constantemente, es señal de que los datos son muy relacionales.

## Cuándo encaja

- **Datos con forma de documento**: catálogos con atributos distintos por producto, contenidos, perfiles.
- **Estructura variable** o en evolución rápida.
- **Datos que se leen enteros**, por su identificador.
- **Volúmenes que exigen repartirse** entre muchas máquinas.

## Cuándo no

- **Datos muy relacionados**, que se consultan cruzándolos de muchas formas. Las uniones existen, pero no son su punto fuerte.
- **Integridad estricta entre entidades.** No hay claves foráneas que la base de datos imponga.
- **Informes y análisis** con consultas que no se previeron al diseñar.

Un error frecuente ha sido elegir MongoDB por no tener que definir un esquema, para datos que eran relacionales. El ahorro inicial se paga después, cuando hay que cruzar la información. Además, las bases relacionales guardan hoy documentos JSON, como hace [PostgreSQL](/articulos/que-es-postgresql/), lo que cubre muchos casos intermedios. La comparación general está en [SQL frente a NoSQL](/articulos/sql-frente-a-nosql/).

## Licencia

El código de MongoDB es público, pero su licencia, la SSPL, impone condiciones a quien lo ofrezca como servicio, y la organización que define el término no la reconoce como código abierto. Para usarlo en una aplicación propia no supone diferencia.

## Lo esencial

- MongoDB guarda documentos parecidos a JSON, agrupados en colecciones.
- El esquema es flexible, lo que traslada al código la responsabilidad de la estructura.
- Se modela según cómo se consultan los datos: lo que se lee junto, se guarda junto.
- Incluye replicación y particionado.
- Encaja con datos en forma de documento, y mal con datos muy relacionados.
