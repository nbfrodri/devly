Las [pruebas automáticas](/articulos/pruebas-de-software/) se clasifican por **cuánto abarcan**. Una **prueba unitaria** comprueba una pieza pequeña, como una función, aislada del resto. Una **prueba de integración** comprueba que varias piezas funcionan juntas, por ejemplo el código y la base de datos. Una **prueba de extremo a extremo** recorre la aplicación completa como lo haría un usuario.

## Unitarias

Comprueban una unidad de comportamiento pequeña. Puede ser una función, una clase o varias piezas que colaboran en memoria; aislarla no exige sustituir cada función auxiliar.

```js
import assert from "node:assert/strict";

function precioConIva(precio) {
	return Math.round(precio * 121) / 100;
}

assert.equal(precioConIva(100), 121);
assert.equal(precioConIva(0), 0);

console.log("pruebas superadas"); // pruebas superadas
```

- **Rapidísimas**: miles en segundos.
- **Acotadas**: si una falla, hay menos código y dependencias que investigar.
- **Limitadas**: una pieza puede funcionar sola y fallar al juntarse con las demás.

Si la pieza depende de algo externo, como una API, en la prueba se sustituye por un **doble**: una versión falsa que responde lo que conviene.

## De integración

Comprueban la **colaboración** entre piezas: que el código guarda y lee bien de una base de datos real, que dos servicios se entienden, que una [API](/articulos/que-es-una-api/) responde con el formato esperado.

- Detectan errores que las unitarias no ven: consultas [SQL](/articulos/que-es-sql/) mal escritas, formatos que no coinciden.
- Son más lentas y necesitan preparar un entorno: una base de datos de pruebas, por ejemplo.

## De extremo a extremo

Arrancan la aplicación completa y la manejan desde fuera, como un usuario: abren el navegador, rellenan un formulario, pulsan "comprar" y comprueban que aparece la confirmación.

- **Comprueban el recorrido integrado**: si pasan, hay evidencia sobre ese flujo, esos datos y ese entorno. No acreditan todos los casos ni todos los entornos.
- **Suelen costar más**: incluyen arranque, comunicación y esperas. La intermitencia puede deberse a una sincronización incorrecta o a estado compartido; no es una propiedad inevitable de este alcance.
- **Cuesta diagnosticarlas**: un fallo puede venir de cualquier parte.

## Comparación

| | Unitarias | De integración | De extremo a extremo |
| --- | --- | --- | --- |
| Alcance | Una pieza | Varias piezas juntas | Todo el sistema |
| Coste habitual | Poco arranque y pocas dependencias | Preparar los colaboradores reales | Preparar el recorrido completo |
| Estado que controlar | Entradas de la unidad | Datos y configuración de las piezas | Datos, servicios, usuario y sincronización |
| Si fallan | Zona pequeña que investigar | Frontera entre piezas | Diagnóstico que atraviesa varias capas |
| Confianza que dan | Sobre la pieza | Sobre la colaboración | Sobre el producto |

## La pirámide

Una recomendación clásica, la **pirámide de pruebas**, propone muchas pruebas pequeñas y rápidas, una capa de integración y pocos recorridos completos. Busca detectar cada fallo con una comprobación suficientemente representativa y fácil de mantener.

No es una cuota universal ni implica que las unitarias detecten la mayoría de los defectos en cualquier producto. En una biblioteca de cálculo pesa la lógica; en un servicio que transforma y guarda mensajes pueden pesar sus integraciones. La distribución depende de los riesgos.

El error habitual es la pirámide invertida: casi todo probado de extremo a extremo, con una batería lenta y frágil en la que nadie confía.

## Todas tienen su sitio

Ninguna sustituye a las otras. Las unitarias dicen que las piezas funcionan; las de integración, que encajan; las de extremo a extremo, que el producto hace lo que debe. Se ejecutan juntas en el [pipeline de integración continua](/articulos/integracion-y-despliegue-continuos/).

### La misma compra en los tres niveles

Un carrito contiene un artículo de 100 euros; con el impuesto del ejemplo, el total es 121. La unitaria comprueba ese cálculo y sus límites sin guardar pedidos. Detectaría una fórmula equivocada, pero pasaría aunque el código escribiera en una columna inexistente.

La de integración ejecuta el guardado contra una base de pruebas, recupera el pedido y comprueba importe e identificador. Puede descubrir una consulta incorrecta o una restricción incumplida. Todavía no demuestra que el botón envíe el carrito correcto.

La de extremo a extremo abre el carrito, confirma la compra y comprueba el pedido resultante. Detectaría que el botón no llama al servidor. Para probar todas las combinaciones de redondeo, repetir ese recorrido sería más costoso que variar entradas en la prueba pequeña. Las tres aportan evidencia distinta sobre la misma operación.

## Confusiones frecuentes

- **Llamar unitaria a cualquier prueba rápida.** El alcance depende de qué componentes ejercita, no del cronómetro.
- **Suponer que usar navegador significa extremo a extremo.** Puedes probar un componente en navegador con el servidor sustituido; hay que describir qué incluye el recorrido.
- **Sustituir toda integración por dobles.** Una respuesta inventada no verifica el contrato ni las restricciones del proveedor real.
- **Contar pruebas como medida de calidad.** Cien casos redundantes pueden dejar sin comprobar la única frontera que falla.

## Lo esencial

- Las unitarias prueban una pieza aislada; son rápidas y precisas.
- Las de integración comprueban que varias piezas colaboran bien.
- Las de extremo a extremo comprueban recorridos completos en un entorno concreto.
- La pirámide orienta el reparto; los riesgos y el coste deciden la combinación útil.
