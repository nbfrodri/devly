**OLTP**, procesamiento de transacciones en línea, es el uso de una [base de datos](/articulos/que-es-una-base-de-datos/) para el **funcionamiento diario** de una aplicación: muchas operaciones pequeñas y rápidas, como crear un pedido o actualizar un saldo. **OLAP**, procesamiento analítico en línea, es su uso para **analizar**: consultas que suelen agregar muchas filas para responder preguntas de negocio.

Tienen necesidades tan distintas que se suelen resolver con sistemas diferentes.

## OLTP

Es lo que hace la base de datos de una tienda en línea mientras la gente compra:

- Registrar un pedido.
- Descontar unidades del almacén.
- Consultar el carrito de un usuario.

Es habitual que cada operación toque pocas filas y que muchas coincidan; importan la latencia y la concurrencia que necesita la aplicación. Además deben ser correctas aunque coincidan: son [transacciones ACID](/articulos/transacciones-y-acid/).

El ejemplo se ejecuta en una base SQLite nueva y continúa en el bloque siguiente. Todas las filas representan la misma tienda; los importes están en céntimos:

```sql
CREATE TABLE productos (id INTEGER PRIMARY KEY, existencias INTEGER NOT NULL CHECK (existencias >= 0));
CREATE TABLE ventas (id INTEGER PRIMARY KEY, region TEXT NOT NULL, fecha TEXT NOT NULL, importe_centimos INTEGER NOT NULL);
INSERT INTO productos VALUES (42, 3);
INSERT INTO ventas VALUES (1, 'norte', '2026-10-01', 1000), (2, 'norte', '2026-10-02', 1500);

UPDATE productos SET existencias = existencias - 1 WHERE id = 42 AND existencias > 0;
SELECT existencias FROM productos WHERE id = 42;
```

Quedan dos unidades. Esta sentencia ilustra una actualización pequeña; registrar una compra completa exigiría coordinar también el pedido y comprobar si se descontó alguna fila.

## OLAP

Es lo que hace el equipo de negocio al preguntar:

```sql
SELECT region, substr(fecha, 1, 7) AS mes, SUM(importe_centimos) AS total_centimos
FROM ventas
GROUP BY region, mes
ORDER BY region, mes;
```

El resultado es `norte | 2026-10 | 2500`: se agregan las ventas de una misma región y un mismo mes para responder una pregunta distinta de descontar una unidad. El código presupone fechas ISO `AAAA-MM-DD`; no está filtrando cinco años ni garantiza recorrer millones de filas. Con una historia extensa, el volumen y el coste pueden crecer mucho. La latencia requerida depende del informe y de si es interactivo.

## Comparación

| | OLTP | OLAP |
| --- | --- | --- |
| Uso | Operaciones del día a día | Análisis e informes |
| Consultas típicas | Operaciones acotadas y concurrentes | Agregaciones y exploración |
| Filas por operación | Habitualmente pocas | Desde subconjuntos pequeños hasta grandes recorridos |
| Escrituras | Cambios de la aplicación | Lotes o actualizaciones incrementales |
| Diseño frecuente | [Normalizado](/articulos/normalizacion-de-bases-de-datos/) | Modelos dimensionales u otras tablas analíticas |
| Almacenamiento frecuente | Por filas | Por columnas; no es obligatorio |
| Usuarios | La aplicación y sus clientes | Analistas |
| Prioridad | Rapidez y consistencia de cada operación | Velocidad de las agregaciones |
| Datos | Actuales | Históricos |

## Cuándo separar los sistemas

- **Rendimiento.** Una consulta analítica pesada puede competir por recursos con las operaciones de los usuarios.
- **Acceso distinto.** Las filas suelen favorecer operaciones sobre registros; las columnas, agregaciones de pocos campos. Son opciones del motor, no definiciones de OLTP y OLAP.
- **Historia.** El análisis puede necesitar conservar versiones y periodos que la aplicación ya no usa. Una base operativa también puede mantener historia si se diseña para ello.

Una solución habitual es copiar los datos por lotes o incrementalmente, con [procesos ETL](/articulos/procesos-etl/), de las bases OLTP a un [almacén de datos](/articulos/almacen-de-datos-y-lago-de-datos/) para OLAP.

## La frontera se acorta

Existen sistemas llamados **HTAP**, híbridos, que intentan servir los dos usos sobre los mismos datos, para analizar en tiempo real sin esperar a la copia nocturna. Y muchas bases de datos operativas ofrecen réplicas de lectura que pueden descargar trabajo de la principal, aunque la replicación tiene costes y puede introducir retraso, como explica [replicación y particionado](/articulos/replicacion-y-particionado/).

## Confusiones frecuentes

- **Identificar OLAP con un volumen mínimo.** La finalidad analítica no depende de alcanzar un millón de filas.
- **Suponer que separar siempre compensa.** Añade operación, copias y retraso; si la carga cabe y cumple sus objetivos en un sistema, puede no hacer falta otro.
- **Confundir réplica con historia completa.** Replicar el estado actual no conserva por sí solo todas sus versiones anteriores.

## Lo esencial

- OLTP es el uso operativo: muchas transacciones pequeñas, rápidas y consistentes.
- OLAP responde preguntas analíticas mediante consultas y agregaciones.
- Normalización, esquemas dimensionales y almacenamiento por filas o columnas son elecciones de diseño.
- Separar cargas puede ayudar; también existen sistemas híbridos y análisis en bases operativas.
