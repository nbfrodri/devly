La **memoria caché del procesador** conserva copias de datos e instrucciones cerca de las unidades que los usan. En muchos [procesadores](/articulos/como-funciona-un-procesador/) está integrada en el mismo chip. Encontrar una copia válida permite evitar el acceso a un nivel más lento, como la [memoria RAM](/articulos/memoria-ram-y-almacenamiento/). Cuánto ayuda depende del programa y del equipo.

Es el mismo principio de una [caché](/articulos/que-es-una-cache/): conservar una copia para reducir el coste de obtenerla de nuevo. Aquí el hardware gestiona bloques de memoria.

## Qué problema resuelve

El procesador puede necesitar datos más deprisa de lo que la RAM puede entregarlos. Si una instrucción depende de una lectura que aún no ha llegado, tiene que esperar; ejecutar otras instrucciones independientes puede ocultar parte de ese retraso, pero no lo elimina.

Como ejemplo de escala, una CPU de 2 GHz tiene ciclos de 0,5 nanosegundos. Una lectura que tardara 100 nanosegundos ocuparía 200 de esos ciclos. Son valores ilustrativos, no una medición de cualquier equipo ni una afirmación de que toda la CPU permanezca parada.

¿Por qué no hacer toda la memoria igual de rápida? La RAM estática, o SRAM, usada en muchas cachés necesita más área por bit que la RAM dinámica, o DRAM, de la memoria principal. Capacidad, latencia, energía y coste condicionan el diseño.

## La jerarquía de memoria

Una organización habitual combina varios niveles. Los nombres describen su papel; no fijan una capacidad ni una latencia universal.

| Nivel | Papel en esa organización |
| --- | --- |
| Registros | Operandos y resultados que usan las instrucciones; acceder a ellos tampoco es instantáneo |
| Caché L1 | Primer nivel de caché, pequeño y de baja latencia |
| Caché L2 | Más capacidad que L1, normalmente con mayor latencia |
| Caché L3, si existe | Otro nivel de mayor capacidad, a menudo compartido |
| RAM | Memoria principal, con más capacidad y una latencia de acceso normalmente mayor |

El almacenamiento persistente tiene otra función: conserva archivos. No es simplemente una L4 a la que cualquier fallo de caché llegue de forma automática.

En muchos procesadores, cada núcleo tiene sus propias cachés L1 y L2, y varios núcleos comparten una L3. La distribución exacta depende de la arquitectura.

## Por qué funciona: la localidad

Una caché de unos kilobytes delante de gigabytes de RAM parece inútil. Puede ayudar mucho cuando los accesos presentan uno de estos patrones:

- **Localidad temporal.** Volver a usar pronto lo que se ha usado hace poco. La variable de un [bucle](/articulos/bucles/) se lee en cada vuelta.
- **Localidad espacial.** Si se usa un dato, es probable que enseguida se usen los que están a su lado. Recorrer un [array](/articulos/arrays/) es acceder a posiciones consecutivas.

Conservar una línea puede aprovechar la repetición de accesos; traerla completa puede aprovechar accesos a sus vecinos. Un recorrido con poca reutilización puede beneficiarse poco, y un conjunto de datos demasiado grande no cabe entero.

## Cómo trabaja

La caché organiza las copias en bloques llamados **líneas de caché**. Un tamaño de 64 [bytes](/articulos/que-es-un-byte/) es habitual en CPU de propósito general, pero depende de la arquitectura.

Cuando el procesador necesita un dato:

- **Acierto.** La línea válida está en ese nivel. Se obtiene con la latencia de ese nivel, que también depende de cómo se atienda el acceso.
- **Fallo.** La línea no está disponible en ese nivel. En una lectura normal de memoria cacheable se busca en otros niveles y, si es necesario, en RAM. Al instalarla puede hacer falta desalojar otra; una línea modificada puede requerir escribir sus datos antes de reutilizar su espacio.

Este programa simula lecturas en una caché de **colocación directa**: cada bloque solo puede ocupar una posición, calculada con el resto de la división. Tiene ocho líneas de cuatro bytes y empieza vacía. El modelo admite una lista no vacía de direcciones enteras no negativas y cantidades de líneas y bytes por línea enteras positivas:

```js
function tasaDeAciertos(direcciones, lineas = 8, tamanoDeLinea = 4) {
	const cache = new Array(lineas).fill(null);
	let aciertos = 0;

	for (const direccion of direcciones) {
		const bloque = Math.floor(direccion / tamanoDeLinea);
		const posicion = bloque % lineas;

		if (cache[posicion] === bloque) {
			aciertos = aciertos + 1;
		} else {
			cache[posicion] = bloque;
		}
	}

	return aciertos / direcciones.length;
}

const seguidas = Array.from({ length: 64 }, (_, i) => i);
const aSaltos = Array.from({ length: 64 }, (_, i) => i * 32);

console.log(tasaDeAciertos(seguidas)); // 0.75
console.log(tasaDeAciertos(aSaltos)); // 0
```

Con accesos consecutivos, el primero de cada línea falla y los tres siguientes aciertan: un 75 %. Con accesos a saltos grandes, cada uno cae en una línea distinta y **todos fallan**.

Son 64 accesos en ambos casos, pero a regiones distintas: el primero usa las direcciones 0 a 63; el segundo, 0, 32, 64 y así hasta 2016. En esta simulación, todos los saltos compiten por la posición 0 de la caché, porque el número de bloque es múltiplo de ocho. El ejemplo muestra tanto localidad espacial como conflictos de colocación; no mide tiempos de un procesador real.

### Seguir un desalojo

Con esa misma configuración, las direcciones 0, 1, 32 y 0 producen esta secuencia:

| Dirección | Bloque: dirección dividida entre 4, sin decimales | Posición: bloque módulo 8 | Resultado |
| --- | --- | --- | --- |
| 0 | 0 | 0 | Fallo: se instala el bloque 0 |
| 1 | 0 | 0 | Acierto: sigue el bloque 0 |
| 32 | 8 | 0 | Fallo: el bloque 8 sustituye al 0 |
| 0 | 0 | 0 | Fallo: el bloque 0 ya no estaba |

Solo hay un acierto de cuatro, aunque las otras siete posiciones están libres. No basta con tener capacidad total: también importa dónde puede colocarse cada bloque. Una caché asociativa permite varias posiciones posibles y reduce algunos conflictos; no elimina todos los [fallos de caché](/articulos/fallos-de-cache/).

## Lo que implica al programar

El programa normalmente no pide cada carga en caché de forma explícita, pero su patrón de acceso puede influir mucho en el rendimiento.

### El orden de recorrido

Si una tabla de dos dimensiones se almacena fila tras fila, recorrerla **por filas** avanza por posiciones consecutivas. Recorrerla **por columnas** salta de una fila a otra en cada paso. Otros formatos almacenan por columnas: hay que conocer la disposición real. Un array de arrays de JavaScript tampoco garantiza un único bloque contiguo.

Las dos formas leen los mismos datos y hacen las mismas operaciones. Con tablas grandes, la segunda puede ser varias veces más lenta.

### Arrays frente a listas enlazadas

Los elementos de un array contiguo están juntos. Los nodos de una [lista enlazada](/articulos/listas-enlazadas/) pueden estar repartidos por toda la memoria, y cada salto de uno al siguiente es un posible fallo. Los arrays de un lenguaje dinámico pueden contener referencias a objetos almacenados en otras regiones.

Por eso un array suele ser más rápido de recorrer aunque, sobre el papel, las dos estructuras tengan la misma [complejidad](/articulos/complejidad-algoritmica/). La notación O cuenta operaciones, no lo que tarda cada una.

### Tamaño de los datos

Guardar juntos los campos que se usan juntos puede aprovechar mejor cada línea. Compactar datos no garantiza una mejora: hay que considerar el coste de decodificarlos, la alineación y las escrituras de otros hilos.

### Varios hilos

Si dos [hilos](/articulos/hilos-y-concurrencia/), en núcleos distintos, modifican variables diferentes de la **misma línea**, pueden obligar a transferir repetidamente el permiso para escribirla. En un protocolo basado en invalidaciones, obtener ese permiso invalida otras copias cuando las hay; varias escrituras seguidas del mismo propietario no necesitan repetir todo el intercambio. Es **falsa compartición**: se comparte la línea aunque las variables sean distintas.

## Lo que el procesador hace por su cuenta

- **Precarga.** Algunos mecanismos intentan anticipar accesos y traer líneas antes de necesitarlas. Acertar puede reducir esperas; equivocarse consume ancho de banda y espacio.
- **Desalojo.** La colocación limita qué línea puede sustituirse. Cuando hay varias candidatas, la política puede aproximar el uso reciente o seguir otros criterios; no todas aplican LRU, la elección de la línea que lleva más tiempo sin usarse.
- **Coherencia.** La [coherencia de caché](/articulos/coherencia-de-cache/) coordina copias y permisos entre núcleos. No sustituye la sincronización entre hilos ni fija por sí sola el orden de accesos a direcciones distintas.

## No optimizar a ciegas

Antes de reorganizar datos, comprueba qué limita la ejecución. Mejorar localidad no resolverá una espera de red ni un algoritmo que hace demasiado trabajo. Los bucles de cálculo numérico, videojuegos, bases de datos o compresión son ejemplos donde merece la pena investigar los accesos a memoria.

Hay herramientas que cuentan fallos y otros eventos del procesador. Conviene relacionarlos con el tiempo de la tarea que quieres mejorar: menos fallos no garantiza por sí solo menor duración.

## Errores comunes

- **Pensar que un fallo significa que toda la caché está llena.** La traza tiene siete posiciones libres y aun así desaloja el bloque 0: ambos bloques compiten por una posición.
- **Suponer que cada elemento de un array dinámico está junto al anterior en memoria.** El lenguaje puede guardar referencias y objetos separados; hay que conocer la representación.
- **Cambiar la disposición sin medir.** Una mejora de localidad puede añadir trabajo o perjudicar a otro hilo. Comprueba el resultado con la misma carga.

## Lo esencial

- Una copia válida en caché puede evitar un acceso a un nivel más lento; un acierto tampoco es instantáneo.
- La localidad temporal reutiliza datos; la espacial aprovecha vecinos dentro de una línea.
- Capacidad, colocación y política de reemplazo condicionan qué líneas siguen disponibles.
- Organización de datos y coordinación entre núcleos afectan al resultado; hay que medir antes de optimizar.
