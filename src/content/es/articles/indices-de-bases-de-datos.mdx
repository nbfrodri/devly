Un **índice** es una estructura auxiliar que una [base de datos](/articulos/que-es-una-base-de-datos/) mantiene para encontrar filas con rapidez. Es la principal herramienta para que una consulta lenta pase a ser rápida.

## Qué problema resuelve

Para filtrar una tabla sin un acceso alternativo útil, el motor puede leerla fila por fila y comprobar la condición. Se llama **recorrido completo** (*full scan*).

El coste crece con los datos visitados. No hay una conversión fija a milisegundos: influyen la memoria disponible, el almacenamiento, el ancho de las filas y cuántas necesita devolver la consulta.

Un índice funciona como el de un libro. Para encontrar dónde se habla de un tema no lees el libro entero: vas al índice alfabético del final, localizas la palabra y saltas a la página.

## Cómo es por dentro

Un índice de tipo **árbol B** guarda claves ordenadas y referencias a las filas. Puede incluir una o varias columnas; otros tipos de índice, como hash, organizan la información de otra manera.

Como está ordenado, se puede descartar parte de las claves en cada paso. El [árbol B](/articulos/arboles-b/) tiene muchos hijos por nodo: cada página permite elegir el intervalo que contiene la clave. Su altura reducida ayuda a limitar accesos a páginas; no significa que cada paso descarte exactamente la mitad.

En un modelo de comparación de claves de tamaño fijo, la [complejidad](/articulos/complejidad-algoritmica/) distingue localizar el comienzo de un resultado y recorrerlo:

| Operación | Recorrido completo | Búsqueda en un árbol equilibrado |
| --- | --- | --- |
| Localizar una clave | O(n) | O(log n) |
| Entregar k coincidencias | Recorrer las n filas y producir el resultado | Localizar el intervalo y recorrer sus k entradas |

El índice no elimina el coste de entregar muchas filas ni los accesos a la tabla para obtener columnas que no contiene. Un resultado de casi toda la tabla puede favorecer el recorrido completo.

## Verlo en funcionamiento

Las bases de datos permiten preguntar **cómo** van a ejecutar una consulta. Este ejemplo usa SQLite desde Node.js:

```js
import { DatabaseSync } from "node:sqlite";

const db = new DatabaseSync(":memory:");
db.exec("CREATE TABLE usuarios (id INTEGER PRIMARY KEY, correo TEXT, ciudad TEXT)");

function plan(consulta) {
	return db.prepare(`EXPLAIN QUERY PLAN ${consulta}`).all()[0].detail;
}

const consulta = "SELECT * FROM usuarios WHERE correo = 'ana@ejemplo.com'";

console.log(plan(consulta).includes("SCAN")); // true

db.exec("CREATE INDEX idx_correo ON usuarios (correo)");

console.log(plan(consulta).includes("USING INDEX idx_correo")); // true
```

Antes de crear el índice, el plan es recorrer la tabla. Después, la misma consulta, sin cambiar una letra, usa el índice.

Eso es importante: **los índices no cambian las consultas**. Se crean aparte, y la base de datos decide por sí sola cuándo usarlos.

La orden para ver el plan cambia de nombre según el sistema; en la mayoría es `EXPLAIN`. Puedes seguir un ejemplo completo en [cómo se lee un plan de ejecución SQL](/articulos/planes-de-ejecucion-sql/).

## Lo que cuesta un índice

Si los índices solo tuvieran ventajas, se crearía uno por cada columna. No es así.

- **Ocupan espacio.** Cada índice es una copia de datos.
- **Añaden trabajo a las escrituras.** Insertar o borrar exige mantener los índices afectados; una actualización puede alterar las claves y requerir mantenimiento adicional.

Un índice intercambia espacio y mantenimiento por accesos potencialmente más baratos. Diez índices inútiles pueden encarecer las escrituras sin mejorar las consultas que importan.

## Qué columnas indexar

Las que aparecen en las condiciones de las consultas frecuentes:

- En el `WHERE`: `WHERE correo = ...`.
- En las combinaciones entre tablas: las claves foráneas que se usan en un `JOIN`.
- En el `ORDER BY`: como el índice ya está ordenado, puede ahorrar la ordenación.

Los motores suelen respaldar una clave primaria con una estructura de acceso. PostgreSQL crea un índice único; en SQLite, `INTEGER PRIMARY KEY` puede ser el identificador de fila del propio almacenamiento, sin un índice secundario separado.

### Cuándo no ayuda

- **Tablas pequeñas.** Leerlas enteras puede ser más barato.
- **Filtros que conservan muchas filas.** Importa la distribución: aunque una columna solo tenga «sí» y «no», buscar un «sí» muy raro sí puede aprovechar un índice.
- **Tablas en las que se escribe mucho y se lee poco**, como un registro de eventos.

## Índices de varias columnas

Un índice puede abarcar varias columnas, y **el orden importa**.

Un índice sobre `(ciudad, apellido)` está ordenado primero por ciudad y, dentro de cada ciudad, por apellido. Como una guía telefónica ordenada por población y luego por nombre.

| Consulta | Acceso que permite el orden |
| --- | --- |
| Por ciudad | Localizar el grupo de esa ciudad |
| Por ciudad y apellido | Localizar un intervalo dentro del grupo |
| Solo por apellido | No forma un único intervalo; depende de recorridos y optimizaciones del motor |

Buscar un apellido sin fijar ciudad puede requerir visitar varios grupos. Algunos motores aprovechan *skip scan* para realizar búsquedas por grupo cuando compensa. El prefijo izquierdo es una buena guía para el acceso directo, no una prohibición absoluta de usar otras columnas.

## Cuando existe y no se usa

Es frecuente crear un índice y comprobar que la consulta sigue lenta. Las causas habituales:

- **Aplicar una función a la columna.** `WHERE LOWER(correo) = ...` no ofrece el mismo acceso que comparar el valor original; puede necesitar un índice sobre la expresión.
- **Buscar por el final de un texto.** `LIKE '%gmail.com'` no delimita un prefijo en el árbol B. `LIKE 'ana%'` puede hacerlo si la intercalación y las reglas del motor son compatibles.
- **Que la consulta devuelva casi toda la tabla.** Si hay que leer la mayoría de las filas, el recorrido completo es más barato y la base de datos lo elige.

## Índices únicos

Un índice puede además imponer una regla: que no haya dos filas con el mismo valor. Es la forma de garantizar, por ejemplo, que no se registren dos usuarios con el mismo correo. La comprobación es rápida precisamente porque el índice existe.

## Cómo proceder

1. No crear índices "por si acaso".
2. Localizar las consultas lentas midiendo.
3. Ver su plan de ejecución.
4. Crear el índice que esa consulta necesita.
5. Volver a medir.

## Lo esencial

- Un índice es una estructura de acceso; un árbol B organiza claves ordenadas y referencias.
- Puede reducir el trabajo para localizar filas, pero el tamaño del resultado sigue importando.
- Su utilidad debe compensar espacio y mantenimiento de escrituras.
- En un índice de varias columnas, el orden determina qué consultas lo aprovechan.
- El plan de ejecución muestra si una consulta lo está usando.
