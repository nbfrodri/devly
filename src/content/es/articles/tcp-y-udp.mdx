**TCP** y **UDP** son [protocolos](/articulos/que-es-un-protocolo-de-red/) de transporte: permiten intercambiar datos entre puntos de comunicación de los programas. TCP ofrece un **flujo ordenado de bytes** y recupera pérdidas mediante retransmisiones. UDP envía **mensajes separados**, llamados datagramas, sin ordenar ni retransmitir por sí mismo. Una conexión TCP también puede interrumpirse; UDP no garantiza menor tiempo de llegada.

## Qué problema resuelven

El protocolo IP lleva paquetes de una [dirección IP](/articulos/que-es-una-direccion-ip/) a otra, pero se queda corto en dos cosas:

- **La IP no identifica por sí sola al programa.** En un ordenador puede haber varios servicios de red. Hace falta distinguir sus puntos de comunicación.
- **IP no ofrece entrega fiable y ordenada.** Un paquete puede perderse, duplicarse o llegar después de otro enviado más tarde.

Ambos añaden puertos; TCP añade además recuperación y orden. Trabajan por encima de IP, en la **capa de transporte** de los [modelos de red](/articulos/modelos-osi-y-tcp-ip/).

## Los puertos

Los [**puertos**](/articulos/que-es-un-puerto/) son números de 16 bits que ayudan a identificar puntos de comunicación. El campo admite valores de 0 a 65 535, aunque el 0 está reservado; no es un puerto ordinario para publicar un servicio.

Si la IP es la dirección de un edificio, el puerto se parece al número del piso. Estos son puertos convencionales; un servicio puede configurarse en otro:

| Puerto | Servicio |
| --- | --- |
| 80 | [HTTP](/articulos/que-es-http/) |
| 443 | HTTPS |
| 53 | [DNS](/articulos/que-es-dns/) |

El límite de 65 535 se debe a que el número de puerto ocupa 16 [bits](/articulos/que-es-un-bit/).

```js
console.log(2 ** 16 - 1); // 65535
```

## TCP: un flujo ordenado con recuperación

TCP (*Transmission Control Protocol*) organiza los bytes en una conexión entre dos extremos. Para recuperar pérdidas y mantener el orden hace varias cosas.

### Establece una conexión

Antes de enviar datos, las dos partes se ponen de acuerdo con un intercambio de tres mensajes:

1. El cliente envía `SYN`: "quiero conectarme".
2. El servidor responde `SYN-ACK`: "de acuerdo, yo también".
3. El cliente confirma con `ACK`: "recibido".

A partir de ahí los datos pueden circular en los dos sentidos.

### Numera y confirma

Cada segmento lleva un número de secuencia que indica la posición de sus datos en el flujo de [bytes](/articulos/que-es-un-byte/). No es simplemente el número del paquete. El receptor utiliza esas posiciones para detectar huecos, ordenar y descartar duplicados.

El receptor envía confirmaciones, llamadas **ACK**. Si los datos no se confirman, el emisor puede retransmitirlos al vencer un temporizador o detectar otras señales de pérdida. La entrega al programa respeta el orden del flujo.

### Regula la velocidad

El **control de flujo** limita lo pendiente según lo que admite el receptor. El [**control de congestión**](/articulos/control-de-congestion-tcp/) ajusta el envío según señales del camino. Son límites distintos: tener memoria libre en el destino no significa que la red tenga capacidad disponible.

Todo esto tiene un coste: el intercambio inicial, las confirmaciones y las esperas cuando algo se pierde añaden retraso.

## UDP: enviar y ya está

UDP (*User Datagram Protocol*) transporta datagramas individuales con puertos y longitud. Incluye un campo de comprobación de errores, cuyo uso depende de la versión de IP; esa comprobación no cifra el contenido ni autentica a quien lo envió.

- No establece conexión: envía directamente.
- No confirma la recepción ni reenvía lo perdido.
- No garantiza el orden.

Evita las confirmaciones y retransmisiones propias de TCP, pero eso no determina cuánto tarda la red. Si la aplicación necesita recuperar pérdidas, ordenar o controlar la congestión, debe resolverlo ella u otro protocolo construido sobre UDP.

## El mismo envío con una pérdida

Queremos transmitir `ABCDEF`, seis bytes en ASCII. Para comparar, suponemos que TCP ya está conectado y divide estos datos en dos segmentos; con UDP, la aplicación elige dos mensajes: `ABC` y `DEF`. En ambos casos se pierde el primer envío y llega el segundo.

| Paso | TCP | UDP sin recuperación añadida |
| --- | --- | --- |
| Se envía `ABC` | Ocupa posiciones 1000–1002; se pierde | Primer datagrama; se pierde |
| Llega `DEF` | Ocupa 1003–1005; falta el inicio | Segundo datagrama disponible para el programa |
| El receptor espera `ABC` | No entrega `DEF` como si fuera el inicio del flujo; puede guardarlo | UDP no sabe que falta otro mensaje |
| El emisor detecta la pérdida | Retransmite los bytes no confirmados | UDP no retransmite por su cuenta |
| Llega la retransmisión | El programa puede leer `ABCDEF` en orden | Sigue habiendo solo `DEF`, salvo una acción de la aplicación |

TCP tampoco garantiza que el programa lea seis bytes en una sola operación: puede recibirlos en varias lecturas. No conserva las fronteras de las escrituras originales. El programa necesita reglas para reconocer dónde termina cada mensaje.

Si se corta la conexión antes de recuperar `ABC`, TCP no puede fabricar los bytes. Puede terminar con un error; la aplicación debe definir además cuánto está dispuesta a esperar.

## Cuál se usa para qué

| | TCP | UDP |
| --- | --- | --- |
| Unidad que ve el programa | Flujo de bytes | Datagramas separados |
| Conexión de transporte | Sí | No |
| Recuperación de pérdidas | Retransmisiones | No incorporada |
| Orden de entrega | Orden del flujo | Sin garantía de orden |
| Consecuencia de una pérdida | Puede retrasar bytes posteriores | Puede faltar un mensaje sin retener otros |
| Límites | La conexión puede fallar | La aplicación debe gestionar lo que necesite |

La elección depende de qué es peor para cada aplicación: perder datos o esperar.

- **Un archivo** necesita todos sus bytes correctos. TCP puede proporcionar esa entrega ordenada, pero la aplicación también debe comprobar que terminó la transferencia.
- **Audio en directo** puede preferir seguir con muestras nuevas cuando las antiguas ya no sirven a tiempo. UDP permite esa política; la aplicación aún necesita gestionar pérdidas, ritmo y congestión.
- **DNS** utiliza UDP y TCP, entre otros transportes. Una consulta pequeña puede evitar abrir una conexión TCP, pero no todas las respuestas ni todos los usos siguen ese camino.

## HTTP y la capa de transporte

HTTP/1.1 y HTTP/2 se apoyan normalmente en TCP. HTTP/3 usa **QUIC**, que funciona sobre UDP y ofrece flujos fiables y ordenados, además de cifrado y control de congestión. Por eso «usa UDP» no significa que una descarga tolere perder bytes: hay que mirar qué se construye encima.

## Errores comunes

- **Confundir un ACK con una operación terminada.** Confirma recepción en TCP, no que el programa haya guardado un archivo o procesado un pago.
- **Leer cada bloque recibido como un mensaje completo en TCP.** Las lecturas pueden dividir o juntar escrituras; el protocolo de aplicación debe marcar sus límites.
- **Elegir UDP solo porque «es más rápido».** La red sigue teniendo colas y pérdidas. Añadir recuperación también añade trabajo y esperas.

## Lo esencial

- TCP y UDP llevan datos de un programa a otro; los puertos indican a qué programa.
- TCP recupera pérdidas y entrega bytes en orden, mientras la conexión pueda progresar.
- UDP conserva datagramas separados sin recuperación ni orden incorporados.
- La elección depende del protocolo completo y de cómo debe reaccionar la aplicación ante pérdidas y retrasos.
