Una operación **atómica** se completa entera o no se hace en absoluto: nunca queda a medias. Una operación **idempotente** tiene el mismo efecto previsto sobre el estado al repetirla con los mismos datos; la respuesta puede cambiar. Las dos sirven para que un sistema se comporte bien cuando algo falla, pero protegen de fallos distintos.

## Atomicidad

**Atómico** significa indivisible dentro de un alcance definido. En una transacción de base de datos, sus cambios se confirman juntos o se deshacen juntos. Qué pueden observar otras transacciones mientras se ejecuta depende también del aislamiento; es otra propiedad.

El ejemplo clásico es la transferencia bancaria: restar de una cuenta y sumar en otra. Si se hace de forma atómica, o se aplican los dos cambios o ninguno. Una transacción abortada no deja confirmado solo el débito. Que otras operaciones puedan ver estados intermedios es una cuestión de aislamiento, y una transferencia entre sistemas independientes necesita coordinación adicional.

Es la A de las [propiedades ACID](/articulos/transacciones-y-acid/) de las bases de datos, que la garantizan mediante transacciones.

El término se usa también en [concurrencia](/articulos/condiciones-de-carrera-y-bloqueos/), con un matiz: una operación atómica se comporta como indivisible frente a las otras tareas que participan en ese modelo. No significa necesariamente que la CPU no pueda interrumpir su implementación.

**Protege de:** quedarse a medio hacer.

## Idempotencia

Una operación es **idempotente** si repetirla no cambia nada más allá de lo que hizo la primera vez.

El botón de llamada de un ascensor es idempotente: pulsarlo cinco veces tiene el mismo efecto que pulsarlo una. El de un timbre no: cada pulsación suena.

```js
const usuario = { nombre: "Ana", visitas: 0, activo: false };

function activar(cuenta) {
	cuenta.activo = true;
}

function contarVisita(cuenta) {
	cuenta.visitas = cuenta.visitas + 1;
}

activar(usuario);
activar(usuario);
console.log(usuario.activo); // true

contarVisita(usuario);
contarVisita(usuario);
console.log(usuario.visitas); // 2
```

`activar` es idempotente: da igual llamarla una vez que diez. `contarVisita` no lo es: cada llamada cambia el resultado.

La diferencia suele estar en cómo se expresa el cambio. "Pon el saldo en 70" es idempotente. "Resta 30 al saldo" no lo es.

**Protege de:** hacerlo más de una vez.

## Por qué importa la idempotencia: los reintentos

En una red, cuando envías una petición y no llega respuesta, no puedes saber qué ha pasado. Hay tres posibilidades:

1. La petición no llegó.
2. Llegó, pero falló al procesarse.
3. Llegó y se procesó, pero la respuesta se perdió.

Desde el cliente las tres se ven igual. Un reintento puede recuperar la operación si el fallo era temporal. Debe tener límites y conservar la identidad de la operación; la idempotencia evita efectos adicionales por repetirla, pero no evita saturar el servicio ni autoriza cualquier petición. Si no lo es, en el tercer caso se ejecuta dos veces: dos pagos, dos pedidos.

Por eso [HTTP](/articulos/que-es-http/) define qué métodos son idempotentes, como explica el artículo sobre [REST](/articulos/que-es-rest/):

| Método | ¿Idempotente? | Motivo |
| --- | --- | --- |
| `GET` | Sí | Solo lee |
| `PUT` | Sí | Sustituye el recurso por el mismo contenido |
| `DELETE` | Sí | Borrar algo ya borrado lo deja igual |
| `POST` | No por definición del método | Una API puede añadir deduplicación; no se debe presuponer |

### Hacer idempotente lo que no lo es

Crear un pago no es idempotente por naturaleza. Se consigue que lo sea con una **clave de idempotencia**: el cliente genera un identificador único para la operación y lo envía con la petición. Si reintenta, envía el mismo.

El servidor recuerda las claves que ya ha procesado. Dentro del plazo y del alcance de deduplicación definidos por la API, una repetida recupera el resultado anterior. Debe rechazarse reutilizar la misma clave para datos distintos; una nueva operación necesita una nueva clave.

```js
const procesados = new Map();
let cobros = 0;

function cobrar(clave, importe) {
	if (procesados.has(clave)) {
		const anterior = procesados.get(clave);
		if (anterior.importe !== importe) {
			throw new Error("clave reutilizada con otro importe");
		}
		return anterior;
	}

	cobros = cobros + 1;
	const resultado = { cobro: cobros, importe };
	procesados.set(clave, resultado);

	return resultado;
}

cobrar("pedido-123", 50);
cobrar("pedido-123", 50);
cobrar("pedido-123", 50);

console.log(cobros); // 1
```

Tres llamadas con la misma clave y un solo incremento del contador. Es una simulación secuencial en memoria: no mueve dinero, no resiste reinicios y no coordina varios procesos. La implementación real debe conservar la deduplicación y resolver las peticiones concurrentes.

## Comparación

| | Atomicidad | Idempotencia |
| --- | --- | --- |
| Garantiza | Todo o nada dentro de su alcance | El mismo efecto previsto al repetir |
| Protege de | Operaciones a medias | Operaciones duplicadas |
| Se refiere a | Los pasos dentro de una operación | Varias ejecuciones de la misma operación |
| Se consigue con | Transacciones para todo-o-nada; primitivas atómicas en concurrencia | Diseño de la operación, deduplicación con alcance definido |
| Ejemplo | Una transferencia entre cuentas | Reintentar un pago sin cobrar dos veces |

## Son independientes

Una operación puede tener una propiedad sin la otra:

| | Idempotente | No idempotente |
| --- | --- | --- |
| **Atómica** | Fijar el estado de un pedido en "enviado" dentro de una transacción | Una transferencia dentro de una transacción |
| **No atómica** | Actualizar dos servicios con valores fijos, sin transacción | Sumar puntos en dos servicios, sin transacción |

Por ejemplo, A empieza con 100 y B con 0. Transferir 30 dentro de una transacción deja 70 y 30. Repetir otra transacción idéntica deja 40 y 60: cada transferencia fue completa, pero hubo dos. Si ambas peticiones llevan la misma identidad de operación y el sistema deduplica correctamente, el segundo intento conserva 70 y 30. Las propiedades resuelven fallos diferentes del mismo caso.

## Se necesitan las dos

En un sistema real se complementan. El ejemplo de la clave de idempotencia tiene un punto débil: guardar la clave y hacer el cobro son dos pasos. Si el sistema falla entre ellos, la clave puede quedar anotada sin cobro, o el cobro hecho sin clave.

Si el efecto y la clave pertenecen a la misma base de datos, pueden confirmarse en una transacción que además impida reclamar la misma clave simultáneamente, por ejemplo mediante una restricción única. Un cerrojo por sí solo no deshace cambios tras un fallo.

Si el cobro lo realiza un proveedor externo, la transacción local no puede deshacer automáticamente ese cobro. Se necesita coordinación: conservar una intención de envío, reutilizar una clave aceptada por el proveedor y reconciliar resultados inciertos. El patrón de bandeja de salida transaccional guarda la intención junto al cambio local para enviarla después; aún requiere tratar duplicados y fallos del destino.

## Confusiones frecuentes

- **"Idempotente significa que no cambia nada."** Puede cambiar algo la primera vez. Lo que no hace es cambiar más al repetirse.
- **"Si es atómica, es segura de reintentar."** No. Dos transferencias atómicas son dos transferencias.
- **"Idempotente significa que devuelve siempre lo mismo."** La idempotencia habla del efecto, no de la respuesta. Borrar dos veces puede responder primero "borrado" y después "no existe", y sigue siendo idempotente.

Diseñar [reintentos](/articulos/reintentos-de-peticiones/) exige combinar idempotencia con límites de tiempo y carga: un timeout no demuestra que la operación no se haya aplicado.

## Lo esencial

- Atómico: la operación se hace entera o no se hace.
- Idempotente: repetir la operación no produce efectos adicionales.
- La atomicidad protege de quedarse a medias; la idempotencia, de ejecutar dos veces.
- El alcance importa: una transacción local no cubre automáticamente servicios externos, y la deduplicación necesita persistencia y coordinación cuando hay reinicios o concurrencia.
