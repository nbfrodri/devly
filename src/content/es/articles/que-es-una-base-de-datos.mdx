Una **base de datos** es un conjunto organizado de información que un programa puede consultar y modificar. El sistema que la gestiona ofrece mecanismos para buscar, conservar datos y controlar cambios; sus garantías dependen del diseño y de la configuración.

## Qué problema resuelve

Lo que un programa guarda en [variables](/articulos/que-es-una-variable/) desaparece cuando el programa se cierra. Para conservar los datos hay que escribirlos en el disco.

Lo más simple sería usar un archivo de texto. Funciona con pocos datos, pero pronto aparecen los problemas:

- **Buscar es lento.** Para encontrar un dato hay que leer el archivo entero.
- **Dos escrituras a la vez se pisan.** Si dos personas guardan al mismo tiempo, una pierde sus cambios.
- **Un corte a medias deja datos rotos.** Si el programa falla mientras escribe, el archivo puede quedar incompleto.
- **Nada impide datos sin sentido.** Una edad con letras, un pedido de un cliente que no existe.

El programa que gestiona una base de datos se llama **sistema gestor de bases de datos**. Ofrece mecanismos para abordar esos problemas, como índices, restricciones y transacciones. [PostgreSQL](/articulos/que-es-postgresql/), MySQL y SQLite son ejemplos. Hay que elegir y configurar esos mecanismos: guardar algo en una base no garantiza por sí solo que sea correcto.

## El modelo relacional

El tipo de base de datos más extendido es el **relacional**, propuesto por Edgar F. Codd en 1970. Organiza la información en **tablas**.

Una tabla se parece a una hoja de cálculo:

| id | nombre | ciudad |
| --- | --- | --- |
| 1 | Ana | Madrid |
| 2 | Luis | Sevilla |
| 3 | Marta | Madrid |

- Cada **fila** es un elemento: aquí, un cliente.
- Cada **columna** representa un atributo, como nombre o ciudad, con reglas sobre los valores que admite.

El esquema declara columnas, [tipos](/articulos/tipos-de-datos/) y restricciones. Su cumplimiento depende del motor: PostgreSQL rechaza texto no convertible en una columna entera; SQLite admite tipado flexible por defecto y ofrece tablas `STRICT` para imponer tipos más rígidos. También hay que declarar las reglas de negocio que se quieran comprobar.

## Identificar cada fila

Puede haber dos clientes que se llamen Ana y vivan en Madrid. Para distinguirlos, cada fila tiene un valor que no se repite: la **clave primaria**. En el ejemplo es la columna `id`.

## Relacionar tablas

Los pedidos de esos clientes van en otra tabla. En lugar de repetir el nombre y la ciudad en cada pedido, se guarda solo el `id` del cliente:

| id | cliente_id | total |
| --- | --- | --- |
| 10 | 1 | 25 |
| 11 | 1 | 40 |
| 12 | 3 | 15 |

La columna `cliente_id` es una **[clave foránea](/articulos/que-es-una-clave-foranea/)**: aquí referencia la clave primaria de clientes. Los pedidos 10 y 11 son de Ana; el 12, de Marta. En general, una clave foránea puede comprender varias columnas y referenciar una clave única admitida por el motor, incluso dentro de su misma tabla.

Guardar cada dato una sola vez, que es el objetivo de la [normalización](/articulos/normalizacion-de-bases-de-datos/), tiene una ventaja importante. Si Ana se muda, se cambia su ciudad en una única fila y todos sus pedidos quedan actualizados, porque nunca copiaron el dato.

La base de datos también vigila estas relaciones: se le puede indicar que rechace un pedido cuyo `cliente_id` no exista. A esa garantía se le llama **integridad referencial**.

## Todo o nada

Una transferencia bancaria tiene dos pasos: restar de una cuenta y sumar en otra. Si el sistema falla entre los dos, el dinero desaparecería.

Una [**transacción**](/articulos/transacciones-y-acid/) agrupa cambios para confirmarlos juntos o descartarlos. La aplicación debe comprobar que ambas operaciones lograron lo esperado y confirmar solo entonces. Un error de una sentencia no provoca automáticamente la anulación de toda la transacción en todos los motores.

## Encontrar rápido

Para evitar ciertos recorridos completos, se crean [**índices**](/articulos/indices-de-bases-de-datos/). Los basados en árboles mantienen claves ordenadas y permiten descartar regiones en cada paso, una idea relacionada con la [búsqueda binaria](/articulos/busqueda-binaria/). Hay otros tipos de índice. Pueden acelerar consultas compatibles, a cambio de ocupar espacio y añadir trabajo a las escrituras que los modifican.

## Otros tipos

No todas las bases de datos son relacionales. Las llamadas [**NoSQL**](/articulos/bases-de-datos-nosql/) organizan los datos de otra forma: como documentos, como pares de clave y valor o como grafos. Se eligen cuando la forma de los datos o el volumen encajan mal en tablas. Las relacionales siguen siendo la opción habitual para la mayoría de aplicaciones.

## Errores comunes

- **Esperar que el gestor conozca las reglas del negocio.** Una cantidad negativa puede ser válida para el tipo numérico; hay que declarar la restricción que la prohíba cuando corresponda.
- **Confiar en una relación solo porque la columna acaba en `_id`.** Hay que declarar la clave foránea y comprobar que se aplica. En SQLite se activa con `PRAGMA foreign_keys = ON` en cada conexión.
- **Confundir transacción y copia de seguridad.** La transacción controla cambios; una [copia](/articulos/copias-de-seguridad/) permite recuperar un estado anterior ante otros fallos.

## Lo esencial

- Una base de datos organiza información; el gestor ofrece mecanismos de persistencia, consulta y control de cambios.
- En el modelo relacional los datos van en tablas de filas y columnas.
- La clave primaria identifica cada fila; la clave foránea relaciona una tabla con otra. Cómo se diseñan esas relaciones lo explica el [modelo entidad-relación](/articulos/modelo-entidad-relacion/).
- Las transacciones garantizan que un grupo de cambios se aplica entero o no se aplica.

Para pedir y modificar datos en una base relacional se usa un lenguaje propio: [SQL](/articulos/que-es-sql/).
