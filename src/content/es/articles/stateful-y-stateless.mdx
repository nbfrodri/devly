Un componente **stateful** (con estado) conserva contexto entre interacciones. Uno **stateless** (sin estado) no depende de un contexto de sesión guardado en esa instancia para entender la siguiente petición. La distinción necesita un límite concreto: una instancia web puede ser intercambiable aunque la aplicación conserve sesiones en otro servicio.

## Qué es el estado

El **estado** es la información que un sistema conserva entre una interacción y la siguiente: quién ha iniciado sesión, qué hay en el carrito, por qué paso de un formulario vas.

La diferencia entre los dos modelos no es si esa información existe, que casi siempre existe, sino **dónde se guarda** y quién la aporta en cada petición.

## Un ejemplo cotidiano

Vas a una cafetería de barrio y pides "lo de siempre". El camarero te conoce y sabe qué servirte. Eso es stateful: la conversación depende de lo que él recuerda.

En una máquina expendedora, cada compra empieza de cero. Introduces el dinero y marcas el código, sin que importe lo que compraste ayer. Eso es stateless: cada interacción es completa en sí misma.

## Cómo funciona cada uno

### Stateful

En la variante más sencilla, una instancia del servidor guarda en memoria datos de cada cliente. Las peticiones pueden omitir ese contexto porque la instancia ya lo conoce.

Si ese contexto solo existe en una instancia, las peticiones que lo necesiten deben llegar a ella. Si cae, se pierde su copia en memoria. Es posible replicar o externalizar el estado, pero eso añade decisiones sobre actualización, disponibilidad y recuperación.

### Stateless

La instancia no necesita recordar la conversación anterior: cada petición aporta el contexto necesario o las referencias para obtenerlo de servicios compartidos. Eso no impide consultar datos persistentes.

Cualquier instancia equivalente puede atender la siguiente petición. Esto facilita repartir trabajo, aunque una petición en curso puede fallar y el almacén compartido también puede estar indisponible. El tamaño de los mensajes depende de cuánto contexto se envíe.

Este programa imita los dos modelos con un contador:

```js
function crearContadorConEstado() {
	let total = 0;

	return function sumar() {
		total = total + 1;
		return total;
	};
}

const sumar = crearContadorConEstado();
console.log(sumar()); // 1
console.log(sumar()); // 2

function sumarSinEstado(totalActual) {
	return totalActual + 1;
}

console.log(sumarSinEstado(1)); // 2
console.log(sumarSinEstado(1)); // 2
```

La primera función recuerda cuántas veces se ha llamado, así que la misma llamada da resultados distintos. La segunda recibe el valor actual y no lo conserva. Además es una función pura, por lo que aquí la misma entrada da la misma salida; un servicio stateless que consulte la hora o una base de datos puede responder distinto.

## Comparación

| | Stateful | Stateless |
| --- | --- | --- |
| Contexto de sesión local | Se conserva entre peticiones | No se necesita en esa instancia |
| Tamaño de las peticiones | Puede omitir contexto ya guardado | Depende del contexto o identificadores enviados |
| Añadir instancias | Hay que dirigir, compartir o replicar el estado | Se pueden repartir peticiones entre instancias equivalentes |
| Si una instancia falla | Hay que recuperar su estado si no está compartido | Otra puede atender nuevas peticiones; las activas pueden fallar |
| Preparar una prueba | Incluir el estado previo necesario | Preparar la petición y las dependencias externas |

## HTTP es stateless, pero las webs recuerdan

[HTTP](/articulos/que-es-http/) define la semántica de cada petición de forma independiente; una aplicación construida sobre él sí puede relacionarlas. Por ejemplo, una tienda recuerda el carrito combinando dos piezas:

- **El cliente.** El navegador guarda un identificador en una **cookie** y lo envía en las peticiones que cumplen sus reglas de ámbito. Ese envío automático también puede intervenir en un ataque [CSRF](/articulos/csrf/).
- **Un almacén compartido.** Los datos de la sesión se guardan en una [base de datos](/articulos/que-es-una-base-de-datos/) a la que acceden todos los servidores.

En este diseño, las **instancias web** son intercambiables porque no conservan la única copia de la sesión. La **aplicación** sigue teniendo sesiones con estado. No debe confundirse esta organización con la restricción stateless de REST descrita por Fielding: esta exige que el contexto de sesión proceda de cada petición, no de una conversación almacenada en el servidor.

## Cuándo conviene cada uno

**Instancias sin sesiones locales** resultan útiles en servicios web y [API](/articulos/que-es-una-api/): facilitan repartir carga y reemplazar procesos. Hay que considerar también el coste y la disponibilidad de sus dependencias.

**Stateful** es necesario cuando la propia función consiste en guardar datos, como una base de datos, o cuando hay una conexión continua en la que reenviar todo el contexto en cada mensaje sería un desperdicio: una partida de un juego en línea, una videollamada.

## Confusiones frecuentes

- **Stateless no significa "sin datos".** Se refiere al contexto que el componente necesita conservar; no prohíbe leer o escribir recursos persistentes.
- **No es una propiedad de toda la aplicación.** Una aplicación suele tener partes stateless, como los servidores web, y partes stateful, como la base de datos.

## Lo esencial

- El estado es la información que se conserva entre interacciones.
- Hay que especificar qué componente guarda contexto y qué información aporta cada petición.
- Los sistemas stateless [escalan](/articulos/escalado-vertical-y-horizontal/) y se recuperan de fallos con más facilidad.
- El estado no se elimina: se traslada al cliente o a un almacén compartido.
