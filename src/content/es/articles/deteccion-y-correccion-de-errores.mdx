Los datos se alteran: el ruido cambia [bits](/articulos/que-es-un-bit/) en una transmisión, y la radiación o el desgaste los cambian en una memoria o un disco. Para **detectar** esos errores se añade a los datos información redundante, calculada a partir de ellos, que el receptor vuelve a calcular y compara. Con suficiente redundancia, también se pueden **corregir**, sin pedir que se repita el envío.

## Qué problema resuelve

Un solo bit cambiado puede convertir una transferencia de 10 euros en una de 1034, o un programa en otro que se cuelga. Y los errores ocurren:

- En una [señal](/articulos/senales-analogicas-y-digitales/), el ruido puede hacer que un 0 se lea como 1.
- En la memoria, una partícula de radiación puede invertir un bit.
- En el almacenamiento, las celdas se degradan con el tiempo.

No se pueden evitar del todo. Se pueden diseñar mecanismos que detecten o corrijan determinados patrones de error; ninguno de estos códigos garantiza detectar cualquier alteración posible.

## La idea: añadir redundancia

Enviar el mensaje dos veces permite detectar una diferencia entre copias: si no coinciden, algo falló. Si ambas se alteran del mismo modo, la comparación no lo detecta. Pero cuesta el doble, y no dice cuál de las dos es la buena.

Las técnicas reales añaden **unos pocos bits** calculados a partir de los datos. El receptor repite el cálculo. Si no coincide, hubo un error.

## Paridad

La más simple: un bit adicional que hace que el número total de unos sea par.

```js
const paridad = (bits) => bits.reduce((a, b) => a ^ b, 0);

const dato = [1, 0, 1, 1, 0, 0, 1];
const enviado = [...dato, paridad(dato)];

console.log(paridad(enviado)); // 0

enviado[2] = enviado[2] ^ 1;

console.log(paridad(enviado)); // 1
```

Con el bit añadido, el total de unos es par y la comprobación da 0. Si un bit cambia por el camino, da 1: hay un error.

Sus límites:

- **Si cambian dos bits, no lo detecta**: la paridad vuelve a cuadrar.
- **No dice qué bit falló.**

Es barata, y se usó durante mucho tiempo en memorias y comunicaciones simples.

## Sumas de comprobación

Se suman los datos, en bloques, y el resultado se envía con ellos. Es la **suma de comprobación**, en inglés *checksum*.

La suma de Internet utilizada en la cabecera IPv4 y en TCP/UDP trabaja sobre palabras de 16 bits. IPv6 no lleva esa suma en su cabecera base. Este ejemplo solo ilustra el cálculo sobre una lista de enteros de 0 a 65535; no construye una cabecera ni la pseudocabecera que requiere el transporte:

```js
function sumaDeComprobacion(bloques) {
	let suma = 0;

	for (const bloque of bloques) {
		suma = suma + bloque;
		suma = (suma & 0xffff) + (suma >> 16);
	}

	return ~suma & 0xffff;
}

const bloques = [0x4500, 0x0073, 0x0000, 0x4000, 0x4011];
const comprobacion = sumaDeComprobacion(bloques);

console.log(comprobacion.toString(16)); // "3a7b"
console.log(sumaDeComprobacion([...bloques, comprobacion])); // 0
console.log(sumaDeComprobacion([bloques[1], bloques[0], ...bloques.slice(2), comprobacion])); // 0
```

El receptor suma todo, comprobación incluida. En esta función, 0 significa que la comprobación coincide; no prueba que todos los datos sean los originales. El último resultado intercambia dos palabras y sigue dando cero.

Es rápida de calcular, y detecta muchos errores, pero no todos: si dos bloques se intercambian, la suma no cambia.

## CRC

La **comprobación de redundancia cíclica** o **CRC** calcula un resto mediante una división binaria especial. Cada cadena se interpreta como un **polinomio** con coeficientes 0 o 1: `1011` representa `x³ + x + 1`. La resta se hace con XOR, sin préstamos ni acarreos.

Un ejemplo de tres bits de comprobación usa el divisor `1011`, cuyo grado —la mayor potencia— es 3:

1. Al mensaje `1101` se añaden tres ceros: `1101000`.
2. Se alinea el divisor con el primer 1 y se hace XOR: `1101000 XOR 1011000 = 0110000`.
3. Se repite: `0110000 XOR 0101100 = 0011100`, después `0011100 XOR 0010110 = 0001010` y `0001010 XOR 0001011 = 0000001`.
4. El resto es `001`. Se envía `1101001`, que al dividirse por el mismo divisor deja resto cero.

Si una alteración cambia ese resto, se detecta. Algunos patrones de error también dejan resto cero: no todos son detectables. CRC-32 usa un divisor de grado 32 y parámetros adicionales, como el valor inicial y el orden de los bits. Este es un cálculo compatible con gzip:

```js
function crc32(texto) {
	let crc = 0xffffffff;

	for (const byte of new TextEncoder().encode(texto)) {
		crc = crc ^ byte;

		for (let i = 0; i < 8; i++) {
			crc = crc & 1 ? (crc >>> 1) ^ 0xedb88320 : crc >>> 1;
		}
	}

	return (~crc >>> 0).toString(16);
}

console.log(crc32("123456789")); // "cbf43926"
console.log(crc32("123456789") === crc32("123456780")); // false
```

En este ejemplo, cambiar un carácter cambia el resultado. La función calcula CRC-32 con los parámetros usados por gzip sobre los bytes UTF-8 del texto.

Las garantías dependen del polinomio, de la longitud del bloque y del patrón de error. Una **ráfaga** abarca desde el primer bit alterado hasta el último, incluidos los que queden entre ambos. Un CRC de grado `r` cuyo divisor termina en 1 detecta cualquier ráfaga de longitud como máximo `r`; la detección de errores dispersos requiere examinar el código concreto. Distintas variantes se utilizan en Ethernet, wifi, archivos y almacenamiento.

Un CRC protege contra el **azar**, no contra un atacante. Alguien que modifique los datos a propósito puede recalcular el CRC. Frente a un atacante hace falta autenticidad: por ejemplo un MAC con clave, una firma verificada o un hash comparado con una referencia obtenida por un canal confiable. Un [hash](/articulos/funciones-hash/) sin esa protección también puede sustituirse junto a los datos.

## Corregir

Detectar un error puede llevar a descartar, registrar el fallo o pedir una retransmisión. A veces no es posible: una sonda espacial a horas de distancia, un CD rayado, una memoria que hay que leer ya.

Para corregir hace falta más redundancia: suficiente para saber **qué bit** falló.

### El código de Hamming

Richard Hamming lo ideó en 1950. Con 4 bits de datos añade 3 de control, cada uno vigilando un grupo distinto de posiciones. Los grupos se solapan de forma que cada posición queda cubierta por una combinación única de bits de control.

Al recibir, se comprueba cada grupo. **Si hubo como máximo un bit alterado**, la combinación de grupos que fallan identifica su posición. El bloque siguiente supone entradas de bits válidas y un bloque recibido de siete posiciones:

```js
function codificar([a, b, c, d]) {
	return [a ^ b ^ d, a ^ c ^ d, a, b ^ c ^ d, b, c, d];
}

function corregir(recibido) {
	const bloque = [...recibido];
	const c1 = bloque[0] ^ bloque[2] ^ bloque[4] ^ bloque[6];
	const c2 = bloque[1] ^ bloque[2] ^ bloque[5] ^ bloque[6];
	const c4 = bloque[3] ^ bloque[4] ^ bloque[5] ^ bloque[6];
	const posicion = c1 + 2 * c2 + 4 * c4;

	if (posicion > 0) {
		bloque[posicion - 1] = bloque[posicion - 1] ^ 1;
	}

	return { posicion, datos: [bloque[2], bloque[4], bloque[5], bloque[6]] };
}

const bloque = codificar([1, 0, 1, 1]);
console.log(bloque.join("")); // "0110011"

bloque[4] = bloque[4] ^ 1;

const resultado = corregir(bloque);
console.log(resultado.posicion); // 5
console.log(resultado.datos.join("")); // "1011"
```

Se envía `0110011` y, al invertir el quinto bit, se recibe `0110111`. Las comprobaciones recorren estos grupos:

| Comprobación | Posiciones, empezando en 1 | Resultado |
| --- | --- | --- |
| c1 | 1, 3, 5, 7 | 1 |
| c2 | 2, 3, 6, 7 | 0 |
| c4 | 4, 5, 6, 7 | 1 |

`1 + 2 × 0 + 4 × 1 = 5`: se invierte el quinto bit y se recupera `1011`. La combinación de comprobaciones se llama **síndrome**. Con dos bits erróneos, este decodificador puede invertir un tercero y empeorar el bloque. Hamming (7,4) corrige un error; no distingue de forma fiable dos errores cuando interpreta todo síndrome no nulo como uno solo. La variante extendida añade paridad para corregir uno y detectar dos.

## Dónde se usa

| Técnica | Dónde |
| --- | --- |
| Paridad | Memorias antiguas, algunos protocolos |
| Suma de comprobación | Cabecera IPv4; segmentos TCP y datagramas UDP con sus reglas |
| CRC | Ethernet, wifi, ZIP, gzip, discos |
| Corrección de errores | Memoria ECC, SSD, CD y DVD, códigos QR, redes móviles, sondas espaciales |

- **[Memoria ECC](/articulos/memoria-ecc/).** Muchas configuraciones usan códigos que corrigen un bit y detectan dos por bloque protegido; hay otras capacidades. A mayor volumen y tiempo de operación, aumenta la exposición a fallos, sin que un error en una instalación concreta sea seguro.
- **SSD.** Las celdas flash se degradan, y el controlador corrige constantemente bits erróneos sin que nadie lo note.
- **Códigos QR.** Se leen aunque estén parcialmente tapados o manchados.
- **Comunicaciones.** El wifi y las redes móviles añaden corrección a cada transmisión. Es lo que permite trabajar cerca del límite de capacidad que estableció Shannon.

## El equilibrio

Más redundancia permite detectar y corregir más errores, a cambio de transmitir más bits. Se elige según lo ruidoso que sea el canal y lo caro que sea repetir.

- **Canal fiable, repetir es barato**: detectar y reenviar. Es lo que hace TCP.
- **Canal ruidoso o repetir imposible**: corregir.

## Errores comunes

- **Interpretar «comprobación correcta» como identidad garantizada.** Distintas entradas pueden compartir la misma suma o CRC.
- **Aplicar corrección de un bit a cualquier bloque dañado.** Fuera del límite del código puede producir una palabra incorrecta que parezca válida.
- **Confundir detección accidental con autenticidad.** Un atacante puede recalcular una comprobación sin clave.

## Lo esencial

- Los errores son un riesgo; cada código ofrece detección o corrección para patrones determinados.
- Se añade información redundante calculada a partir de los datos, y el receptor la recalcula.
- Paridad, sumas y CRC tienen costes y conjuntos de errores detectables distintos.
- Hamming (7,4) localiza y corrige un bit alterado bajo ese supuesto de error.
- Estas técnicas protegen del azar, no de la manipulación intencionada.
