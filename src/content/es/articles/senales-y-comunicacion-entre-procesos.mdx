La **comunicación entre procesos**, o **IPC**, permite que programas en ejecución intercambien datos o se coordinen. Sus espacios de memoria están protegidos, pero el sistema puede autorizar canales o regiones compartidas. Aislamiento no significa imposibilidad de colaborar.

Supón un programa A que genera nombres de frutas y otro B que los ordena. Necesitamos entregar datos, saber cuándo termina la entrada, recibir la respuesta y detectar un fallo. No basta con que ambos procesos existan.

## Tuberías: transportar bytes

Una **tubería**, o *pipe*, ofrece un canal de bytes en un sentido. Lo escrito por un extremo se lee por el otro. No conserva por sí sola mensajes: dos escrituras pueden llegar juntas en una lectura o una escritura repartirse en varias. Las aplicaciones deben acordar cómo separar sus datos.

En el ejemplo usaremos saltos de línea. A entrega tres nombres y cierra su extremo de escritura; B puede reconocer el fin de entrada y producir la ordenación. Otra conexión devuelve la respuesta.

Este programa completo usa Node.js en Linux, con `sort` disponible. Guárdalo como `ordenar.mjs` y ejecútalo con `node ordenar.mjs`:

```js
import { spawnSync } from "node:child_process";

const resultado = spawnSync("sort", {
	input: "pera\nmanzana\nuva\n",
	encoding: "utf8",
	env: { ...process.env, LC_ALL: "C" },
});

if (resultado.error) throw resultado.error;
if (resultado.status !== 0) {
	throw new Error(`sort no terminó correctamente: ${resultado.status}, ${resultado.signal}`);
}

console.log(resultado.stdout.trim().split("\n").join(" ")); // "manzana pera uva"
```

`LC_ALL=C` fija las reglas de comparación para estos nombres ASCII. Node crea el proceso y gestiona sus conexiones de entrada y salida. `spawnSync` espera su terminación y conserva la respuesta en memoria; es cómodo para este ejemplo pequeño, pero bloquearía trabajo concurrente del programa que lo llama. También impone límites al volumen capturado.

Una tubería tiene capacidad limitada. Si el receptor no consume datos, el escritor puede quedarse esperando o recibir un resultado que indique que debe intentarlo después, según el modo. Esa **contrapresión** evita tratar el canal como una memoria infinita.

El lector detecta fin de entrada cuando se han cerrado **todos** los descriptores que conservan el extremo de escritura y ya no quedan datos. Si un proceso deja uno abierto por accidente, el otro puede seguir esperando. La [terminal](/articulos/terminal-y-shell/) usa estas conexiones al interpretar `|`.

## Señales: notificar acontecimientos

Una **señal** notifica un acontecimiento a un proceso o hilo. Cada señal tiene una acción predeterminada; muchas permiten instalar un **manejador**, código que responde cuando se entrega. No es lo mismo solicitar una acción que demostrar que ya se ha completado.

| Señal | Significado habitual y acción predeterminada en Linux |
| --- | --- |
| `SIGINT` | Interrupción, frecuentemente por Ctrl+C; termina el proceso |
| `SIGTERM` | Solicitud de terminación; termina si no se instala otro manejo |
| `SIGKILL` | Terminación forzada, sin manejador de la aplicación |
| `SIGHUP` | Desconexión de terminal; por defecto termina |
| `SIGCHLD` | Cambio de estado de un hijo; por defecto se ignora la señal |
| `SIGSTOP` | Detener la ejecución hasta que se permita continuar |

Algunos servicios interpretan `SIGHUP` como recarga de configuración porque lo programan así; no es el efecto universal de la señal. `SIGKILL` y `SIGSTOP` no pueden capturarse ni ignorarse. Tampoco debe confundirse `SIGKILL` con una promesa de desaparición instantánea: el núcleo puede estar esperando que termine una operación no interrumpible.

Para cerrar ordenadamente un servicio, un recorrido posible es:

1. El administrador envía `SIGTERM` con la autorización necesaria.
2. Un manejador instalado por el servicio solicita dejar de aceptar trabajo nuevo.
3. La aplicación termina o cancela sus operaciones pendientes y cierra recursos.
4. El proceso termina y quien lo supervisa comprueba el resultado.

Sin ese manejo, `SIGTERM` no guarda por sí sola documentos ni espera tareas de la aplicación. Los manejadores nativos además tienen restricciones sobre las funciones que pueden llamar; un entorno como Node ofrece su propia interfaz de eventos.

Las señales pueden incluir información asociada; las de tiempo real admiten colas y valores. Varias señales estándar iguales pendientes pueden agruparse en una sola notificación. Por eso no conviene usar una señal estándar por fruta y suponer que se contará cada envío.

## Sockets: acordar una conversación

Un **[socket](/articulos/que-es-un-socket/)** es un extremo de comunicación. Los sockets locales de tipo Unix conectan procesos de la misma máquina; los de red pueden conectar equipos diferentes o procesos del mismo equipo.

Según su tipo, ofrecen un flujo de bytes o mensajes. Un flujo requiere delimitar cada solicitud, igual que nuestra tubería; una petición podría contener una longitud y después los nombres. La aplicación aún debe acordar respuestas, errores y cierre.

Los sockets locales pueden evitar parte del recorrido de red, pero no hay una ventaja de velocidad universal. Tipo de mensaje, tamaño, copias y carga importan. Si B debe atender a muchos clientes, una conexión por cliente puede expresar mejor la conversación que dos tuberías creadas para un único hijo.

## Memoria compartida: ver la misma región

Dos procesos autorizados pueden mapear una región común en sus espacios de direcciones. A escribiría los nombres allí y B los leería sin transportarlos todos por una tubería. Eso puede reducir copias, pero aún hay costes de preparación, coherencia y coordinación.

Hay que indicar qué datos están completos y quién puede modificarlos. Si A reemplaza una entrada mientras B la interpreta, aparece una [condición de carrera](/articulos/condiciones-de-carrera-y-bloqueos/). Compartir una dirección accesible no establece un protocolo correcto; hacen falta mecanismos de sincronización y reglas de propiedad.

| Mecanismo | Qué aporta | Qué debe acordar la aplicación |
| --- | --- | --- |
| Señal | Notificación con semántica definida | Respuesta y límites de entrega |
| Tubería | Flujo de bytes en un sentido | Formato, cierre y consumo |
| Socket | Canal local o de red según su tipo | Protocolo, identificación y errores |
| Memoria compartida | Región accesible a varios procesos | Publicación, propiedad y sincronización |

## Errores comunes

- **Suponer que una lectura equivale a un mensaje.** Los flujos no conservan esa separación.
- **Esperar el final sin cerrar la entrada.** El otro proceso puede estar esperando más datos.
- **Elegir por una tabla de velocidades universales.** Primero define contrato, alcance y volumen; después mide el recorrido real.

## Lo esencial

- IPC permite colaboración autorizada entre procesos.
- Enviar, recibir, cerrar y terminar son acontecimientos distintos.
- Cada mecanismo exige un protocolo y tratamiento de errores.
- Compartir memoria reduce ciertos movimientos, pero no elimina la sincronización.
