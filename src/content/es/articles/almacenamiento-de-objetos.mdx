El **almacenamiento de objetos** es una forma de guardar datos en la que cada archivo se trata como un **objeto**: los datos, unos **metadatos** que los describen y un **identificador único** para encontrarlo. Los objetos se guardan en un espacio **plano**, sin jerarquía de carpetas. Es el tipo de almacenamiento que usan los servicios en la [nube](/articulos/computacion-en-la-nube/) para fotos, vídeos, copias de seguridad y los archivos estáticos de las webs.

El servicio más conocido es Amazon S3, y todos los proveedores tienen el suyo.

## Tres formas de guardar datos

| | Bloques | Archivos | Objetos |
| --- | --- | --- | --- |
| Unidad | Bloques de tamaño fijo | Archivos en carpetas | Objetos con clave y metadatos |
| Organización | La decide el sistema de archivos de encima | Jerarquía de directorios | Espacio plano |
| Acceso | Como un disco | Rutas, como en tu ordenador | Por red, con peticiones HTTP |
| Uso típico | Discos de máquinas virtuales, bases de datos | Carpetas compartidas | Fotos, vídeos, copias, archivos de una web |
| Modificar un trozo | Sí | Sí | No: se sustituye el objeto entero |

Un [sistema de archivos](/articulos/sistema-de-archivos/) organiza los datos en carpetas. El almacenamiento de objetos renuncia a eso a cambio de escalar casi sin límite y a un coste bajo.

## Cubos, claves y objetos

En S3, los objetos se guardan en **buckets** (cubos), y cada objeto tiene una **clave**: su nombre dentro del cubo. En la dirección `https://mi-cubo.s3.amazonaws.com/fotos/perro.jpg`, el cubo es `mi-cubo` y la clave es `fotos/perro.jpg`.

Esa barra parece una carpeta, pero no lo es: la clave entera es un texto. Las "carpetas" que muestran las consolas son una ilusión creada filtrando por **prefijo**:

```js
const cubo = new Map();

function guardar(clave, datos, metadatos = {}) {
	cubo.set(clave, { datos, metadatos, tamano: datos.length });
}

function listar(prefijo) {
	return [...cubo.keys()].filter((clave) => clave.startsWith(prefijo));
}

guardar("fotos/perro.jpg", "...", { tipo: "image/jpeg" });
guardar("fotos/gato.jpg", "...", { tipo: "image/jpeg" });
guardar("documentos/factura.pdf", "...", { tipo: "application/pdf" });

console.log(listar("fotos/").join(", ")); // "fotos/perro.jpg, fotos/gato.jpg"
console.log(cubo.get("documentos/factura.pdf").metadatos.tipo); // "application/pdf"
```

Se accede a los objetos con peticiones HTTP: `PUT` para subir, `GET` para descargar, `DELETE` para borrar. Por eso se pueden servir directamente a un navegador, a menudo a través de una [CDN](/articulos/que-es-una-cdn/).

## Para qué es bueno

- **Datos no estructurados** en grandes cantidades: imágenes, vídeo, audio, registros, datos de sensores. Google Cloud recuerda que buena parte de los datos actuales son así y no encajan en una base de datos tradicional.
- **Escala**: se pueden guardar miles de millones de objetos sin pensar en discos.
- **Coste**: más barato que el almacenamiento en bloques para grandes volúmenes.
- **Durabilidad**: el proveedor guarda varias copias en distintos lugares.
- **Versiones**: S3 permite conservar las versiones anteriores de cada objeto, útil contra borrados accidentales y como parte de las [copias de seguridad](/articulos/copias-de-seguridad/).

## Para qué no

- **Datos que cambian a menudo en partes pequeñas**: para modificar un byte hay que reescribir el objeto entero.
- **Bases de datos**: necesitan almacenamiento en bloques, con acceso rápido a posiciones concretas.
- **Baja latencia extrema**: cada acceso es una petición por la red.

## Seguridad

Un cubo mal configurado, accesible públicamente sin querer, es una de las causas más repetidas de filtraciones de datos. Los proveedores permiten controlar el acceso con políticas del cubo y con [gestión de identidades y accesos](/articulos/gestion-de-identidades-y-accesos/), y lo prudente es que todo sea privado salvo lo que deba ser público.

## Disponibilidad frente a durabilidad

La **disponibilidad** expresa si el servicio puede atender operaciones dentro de unas condiciones. La **durabilidad** se refiere a conservar los datos. Un objeto puede seguir guardado y resultar temporalmente inaccesible; un servicio puede responder correctamente a muchas solicitudes mientras un dato concreto se ha perdido.

| Criterio | Disponibilidad | Durabilidad |
| --- | --- | --- |
| Pregunta | ¿Puedo utilizarlo ahora según el objetivo? | ¿Se conserva lo almacenado? |
| Fallo ilustrativo | Una interrupción impide leer | El contenido ya no puede recuperarse |
| Medición | Indicador y ventana definidos | Probabilidad o historial de pérdida según el modelo |
| Técnicas relacionadas | Redundancia de servicio y recuperación | Redundancia de datos, comprobación y recuperación |

Para una foto, una avería de red puede impedir verla sin destruirla. Borrar su única versión válida puede perderla aunque el sistema continúe atendiendo otras operaciones. No traduzcas una cifra de durabilidad en minutos de disponibilidad: tienen denominadores y contratos distintos.

Las garantías dependen de la clase de almacenamiento y su configuración. Replicar datos no sustituye protegerlos frente a cambios autorizados por error o conservar versiones históricas. Una estrategia de [copias de seguridad](/articulos/copias-de-seguridad/) necesita contemplar también esos casos.

### Una foto inaccesible o una versión perdida

Imagina que los datos de una foto se conservan en varias ubicaciones, pero una avería impide autenticar peticiones durante veinte minutos. La foto no se ha perdido: hay un problema de disponibilidad. Si después vuelve el acceso y el contenido original está intacto, no hubo por ese hecho una pérdida de durabilidad.

En otro incidente, un cliente autorizado sustituye la foto por un archivo equivocado y no existe ninguna versión recuperable. El servicio puede devolver respuestas rápidas y exitosas con ese nuevo archivo. La disponibilidad del servicio no recupera el contenido anterior; hace falta una política de versiones o recuperación adecuada a ese tipo de cambio.

Por eso, al elegir almacenamiento, pregunta separadamente cuánto tiempo puede estar inaccesible un objeto y qué mecanismos protegen su conservación frente a cada fallo. Una cifra de durabilidad de diseño no significa que cualquier borrado legítimamente autorizado pueda deshacerse. El contrato debe aclarar qué pérdida modela y qué responsabilidades quedan en la configuración del sistema.

## Lo esencial

- El almacenamiento de objetos guarda cada archivo como un objeto con datos, metadatos y una clave única.
- Los objetos viven en cubos, en un espacio plano: las carpetas son prefijos de la clave.
- Se accede por HTTP y escala casi sin límite a bajo coste.
- Es ideal para archivos que se leen mucho y se modifican enteros, no para bases de datos.
