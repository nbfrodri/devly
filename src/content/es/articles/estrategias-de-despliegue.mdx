Una **estrategia de despliegue** es la forma en que se sustituye la versión de una aplicación en producción. La **actualización progresiva** reemplaza copias por etapas; **blue-green** cambia el tráfico entre dos entornos; **canary** expone primero la versión a un grupo limitado. Buscan mantener el servicio y controlar el riesgo, pero ninguna garantiza por sí sola una reversión segura.

## Qué problema resuelven

La forma más simple de actualizar es parar la versión antigua y arrancar la nueva. Tiene dos defectos:

- **Hay un corte.** Entre una cosa y otra, el servicio no responde.
- **Si la nueva falla, fallan todos los usuarios**, y volver a la anterior significa repetir el proceso al revés, con otro corte.

Reducir el impacto de cada actualización facilita publicar cambios pequeños con frecuencia, como propone el [despliegue continuo](/articulos/integracion-y-despliegue-continuos/). La frecuencia adecuada depende del servicio y de sus comprobaciones.

Todas se apoyan en tener varias copias de la aplicación tras un [balanceador de carga](/articulos/balanceador-de-carga/), que decide a cuáles envía el tráfico.

## Actualización progresiva

En inglés, *rolling update*. Las copias se sustituyen de una en una, o por grupos:

1. Se arranca una copia con la versión nueva.
2. Cuando responde bien, se incluye en el reparto.
3. Se retira una copia antigua.
4. Se repite hasta que no queda ninguna.

- **A favor:** permite mantener el servicio con capacidad adicional limitada si las copias sanas pueden atender la carga. Es la estrategia por defecto de los Deployments de [Kubernetes](/articulos/que-es-kubernetes/).
- **En contra:** durante el proceso conviven las dos versiones. Y volver atrás es otra actualización progresiva, que lleva su tiempo.

## Blue-green

Se mantienen **dos entornos completos e idénticos**. Uno, llamado azul, atiende a los usuarios. El otro, verde, está parado o en reserva.

1. Se despliega la versión nueva en el verde.
2. Se prueba ahí, sin usuarios.
3. Se cambia el balanceador para que todo el tráfico vaya al verde.
4. El azul queda intacto, con la versión anterior.

Si algo va mal, se puede devolver el tráfico al azul sin reinstalar la versión anterior. Aun así, hay que considerar conexiones abiertas, propagación del cambio y compatibilidad de los datos.

- **A favor:** facilita devolver el tráfico al entorno anterior y probar la nueva versión antes de exponerla.
- **En contra:** exige el doble de infraestructura, al menos durante el cambio. Y todos los usuarios pasan a la vez: si hay un fallo que las pruebas no vieron, lo sufren todos hasta que se revierte.

## Canary

La versión nueva se publica primero para **una pequeña parte** de los usuarios. Si se comporta bien, se amplía.

1. Se despliega junto a la actual.
2. Se le envía, por ejemplo, el 5 % del tráfico.
3. Se comparan las [métricas](/articulos/observabilidad/) de las dos: errores, latencia.
4. Si son buenas, se sube al 25 %, al 50 %, al 100 %.
5. Si empeoran, se devuelve todo a la versión anterior.

El nombre viene de los canarios que los mineros llevaban a las galerías: más sensibles que las personas a los gases tóxicos, avisaban del peligro antes de que afectara a los demás.

```js
function version(usuarioId, porcentajeNuevo) {
	return usuarioId % 100 < porcentajeNuevo ? "nueva" : "estable";
}

const usuarios = Array.from({ length: 1000 }, (_, i) => i);
const conLaNueva = usuarios.filter((u) => version(u, 5) === "nueva");

console.log(conLaNueva.length); // 50
console.log(version(3, 5)); // "nueva"
console.log(version(42, 5)); // "estable"
```

El reparto se calcula a partir del identificador del usuario, y no al azar en cada petición. Con un porcentaje fijo, una misma persona conserva su grupo. Al aumentar el porcentaje, algunas pasan a la versión nueva. El 5 % exacto se cumple aquí porque los identificadores distribuyen uniformemente los restos de 0 a 99; una población real puede necesitar otro criterio de asignación.

- **A favor:** limita la exposición inicial y aporta observaciones de tráfico real. No cubre automáticamente todos los casos ni evita daños en datos compartidos.
- **En contra:** es la más compleja. Exige enrutar por porcentajes y buenas métricas. Sin ellas, es una actualización lenta y nada más.

## Comparación

### El mismo carrito con tres estrategias

Imagina una tienda con cuatro copias de su aplicación y una versión nueva del carrito. Ambas versiones pueden leer los datos existentes. Estos son tres recorridos posibles:

| Estrategia | Primer paso con tráfico real | Si el carrito calcula mal un descuento |
| --- | --- | --- |
| Progresiva | Añadir una copia nueva y retirar una antigua cuando la nueva esté preparada | Detener la sustitución y recuperar copias antiguas; parte del tráfico ya alcanzó la nueva |
| Blue-green | Preparar cuatro copias nuevas en el segundo entorno y cambiar el tráfico hacia él | Devolver tráfico al entorno anterior, si sigue siendo compatible |
| Canary | Mantener las copias antiguas y enviar un 5 % de usuarios a una copia nueva | Retirar ese grupo de la versión nueva y revisar las compras afectadas |

Una de cinco copias no equivale necesariamente al 5 % de usuarios: el reparto del canary debe configurarse y medirse. En los tres casos, recuperar la versión anterior evita nuevas compras defectuosas, pero no corrige automáticamente las ya guardadas. Por eso importa comprobar el resultado del carrito además de que el servidor responda.

### Criterios para decidir

| | Progresiva | Blue-green | Canary |
| --- | --- | --- | --- |
| Cómo cambia | Copia a copia | Todo de golpe | Por porcentajes |
| Infraestructura extra | Poca | El doble | Poca |
| Vuelta atrás del tráfico | Requiere sustituir copias | Cambio hacia el entorno anterior | Retirar tráfico de la versión nueva |
| Exposición inicial | Crece con las copias nuevas | Todo el tráfico que se cambia | Grupo limitado |
| Complejidad | Baja | Media | Alta |

## El obstáculo común: la base de datos

El código se puede tener en dos versiones a la vez. A menudo ambas comparten una [base de datos](/articulos/que-es-una-base-de-datos/), cuyo estado también cambia.

Si la versión nueva renombra una columna, la antigua, que sigue en marcha durante el despliegue o a la que quizá haya que volver, deja de funcionar.

La solución es que cada cambio del esquema sea compatible con las dos versiones, y hacerlo en pasos:

1. **Ampliar.** Se añade una columna compatible con el código antiguo. Hay que comprobar valores por defecto, restricciones y el coste de modificar la tabla.
2. **Migrar.** Se mantiene la escritura compatible y se copian los datos existentes. Antes de cambiar las lecturas a la columna nueva, se comprueba que esté completa y actualizada.
3. **Contraer.** Cuando ninguna versión usa la columna antigua, se elimina.

Son etapas que pueden requerir varios despliegues. La contracción elimina compatibilidad: después de borrar la columna antigua no puedes restaurar sin más una versión que todavía la necesita. La reversión debe planearse antes de cada etapa.

Por lo mismo, las [API](/articulos/que-es-una-api/) deben ser compatibles hacia atrás, y las operaciones, [idempotentes](/articulos/atomicidad-e-idempotencia/): durante el cambio, una petición puede repetirse contra otra versión.

## Desplegar no es lanzar

Hay una distinción útil:

- **Desplegar** es poner código en producción.
- **Lanzar** es que los usuarios vean una funcionalidad.

Los [**interruptores o banderas de funcionalidad**](/articulos/que-es-una-bandera-de-funcionalidad/), en inglés *feature flags*, las separan. El código nuevo se despliega apagado, tras una condición:

```js
const interruptores = { nuevoCarrito: false };

function verCarrito() {
	return interruptores.nuevoCarrito ? "carrito nuevo" : "carrito actual";
}

console.log(verCarrito()); // "carrito actual"

interruptores.nuevoCarrito = true;
console.log(verCarrito()); // "carrito nuevo"
```

Si la configuración puede cambiar en ejecución, encenderlo o apagarlo no requiere desplegar otra versión. La rapidez depende de cómo se propague esa configuración. Se puede encender para el equipo, luego para unos pocos, luego para todos.

| Criterio | Desplegar | Lanzar |
| --- | --- | --- |
| Qué cambia | La versión instalada | Quién puede utilizar el comportamiento |
| Ejemplo | Instalar el código del carrito nuevo | Activarlo para el 5 % de las cuentas |
| Verificación | Salud técnica y compatibilidad | Experiencia, errores y resultado para usuarios |
| Reversión | Volver a otra versión si sigue siendo compatible | Desactivar la bandera si el sistema lo admite |

En el mismo ejemplo, puedes desplegar el lunes con la bandera apagada, comprobar el sistema y lanzar el martes para un grupo. También puedes lanzar directamente durante el despliegue si la funcionalidad es sencilla y ese control adicional no aporta nada. Separarlos es una herramienta para coordinar cambios y reducir exposición, no una obligación para cada modificación.

Desactivar no siempre basta: las compras ya guardadas, los mensajes enviados o los cambios de esquema no desaparecen. Y si una rama antigua deja de ser compatible con los datos nuevos, la bandera ya no ofrece una reversión segura. Verifica qué se puede recuperar antes de tratarla como un botón universal de deshacer.

### Distinguir un fallo de instalación de uno de uso

Para seguir el mismo carrito, separa dos fallos. Si la versión nueva no arranca, afecta al despliegue aunque la bandera esté apagada: el proceso contiene y carga código nuevo. Si arranca bien, pero el cálculo del carrito falla solo cuando se activa, retirar el acceso mediante la bandera puede reducir la exposición sin cambiar la versión instalada.

Un despliegue canary limita qué instancias reciben la versión; un lanzamiento gradual limita quién ve el comportamiento. Pueden coincidir o combinarse, pero no miden exactamente lo mismo. Un problema de arranque se detecta con la salud de las instancias; un error de precio necesita comprobar resultados del recorrido de compra.

Su coste es que cada interruptor añade una rama al código. Los que ya no se usan se eliminan; si no, se acumulan y nadie sabe qué combinaciones están probadas.

## Condiciones que hay que preparar

- **Comprobaciones de salud**, para saber si una copia nueva funciona antes de enviarle tráfico.
- **Despliegues automatizados.** A mano no son fiables.
- **Observabilidad.** Sin métricas no se sabe si la versión nueva es peor.
- **Tratamiento del estado.** Las sesiones y los trabajos en curso deben sobrevivir al reemplazo o terminar de forma controlada. Sacar las sesiones de las copias es una opción; los servicios con estado necesitan una estrategia específica.

## Cómo elegir

- **Progresiva** como punto de partida: sencilla y suficiente para la mayoría.
- **Blue-green** cuando interesa conservar el entorno anterior listo para recuperar tráfico y se puede asumir la capacidad adicional.
- **Canary** cuando hay mucho tráfico, un fallo sale caro y se dispone de buenas métricas.
- **Interruptores** además de cualquiera, para separar el despliegue del lanzamiento.

Las [migraciones de base de datos](/articulos/migraciones-de-bases-de-datos/) coordinan esquema, datos y versiones del código mediante etapas compatibles.

## Confusiones frecuentes

- **Confundir salud con corrección.** Una copia puede responder y calcular mal un precio. Las señales deben cubrir el comportamiento que cambia.
- **Confundir retirar tráfico con deshacer efectos.** Una compra o una escritura ya realizada sigue existiendo después de la reversión.
- **Tratar la contracción del esquema como reversible por defecto.** El código anterior puede depender de datos que ya no están disponibles.

## Lo esencial

- La actualización progresiva sustituye copias por etapas; mantener capacidad y compatibilidad permite conservar el servicio.
- Blue-green conserva dos entornos y facilita cambiar el tráfico, pero no deshace los datos modificados.
- Canary limita la exposición inicial y la amplía según observaciones representativas.
- La reversión depende también del esquema, los efectos ya producidos y el estado compartido.
