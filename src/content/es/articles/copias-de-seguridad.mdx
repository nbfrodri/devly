Una **copia de seguridad** es una copia de los datos guardada aparte, para poder **recuperarlos** si los originales se pierden o se dañan. La palabra clave es recuperar: una copia que no se puede restaurar no sirve de nada, y muchas organizaciones lo descubren el día que la necesitan.

## De qué protegen

Los datos se pierden de muchas formas:

| Causa | Ejemplo |
| --- | --- |
| Fallo de hardware | Un [disco o una SSD](/articulos/discos-duros-y-ssd/) que deja de funcionar |
| Error humano | Un borrado o una actualización sin filtro que modifica todas las filas |
| Error de software | Un programa que corrompe los datos |
| Ataques | Programas de secuestro que cifran los datos y piden un rescate |
| Desastres | Incendio, inundación, robo |
| Fallo del proveedor | Un servicio en la nube que pierde datos o cierra |

## La replicación no es una copia de seguridad

La [replicación](/articulos/replicacion-y-particionado/) propaga cambios entre copias. Si alguien borra una tabla por error, el borrado también puede propagarse. Un ataque puede afectar a varias copias si comparten permisos, infraestructura o el flujo de cambios comprometido; no tiene por qué hacerlo con el mismo mecanismo ni al instante.

La replicación puede ayudar ante el fallo de una máquina. Una copia de seguridad conserva el estado de **un momento pasado**, pero su protección depende de retención, integridad, aislamiento y capacidad de restauración.

Tampoco lo es un [RAID](/articulos/raid/), que combina varios discos para sobrevivir a la avería de uno, ni la papelera, ni una carpeta sincronizada con la nube.

## La regla 3-2-1

La recomendación clásica:

- **3** copias de los datos, contando la original.
- En **2** soportes distintos.
- **1** de ellas fuera del lugar donde están los originales.

Así se reducen fallos compartidos, como la avería de un disco o un incendio en la oficina. El número de copias no basta: si todas dependen de las mismas credenciales comprometidas, un único incidente puede afectar a varias.

Otra medida es conservar al menos una copia **inmutable** o **desconectada**. Los ataques de secuestro pueden intentar alterar las copias accesibles. Impedir su modificación durante la retención o aislarla reduce ese riesgo, pero siguen importando su integridad, las claves para descifrarla y la posibilidad de restaurarla.

## Dos objetivos

Antes de elegir cómo copiar, hay que decidir qué se necesita. Dos cifras lo resumen:

| Objetivo | Pregunta | Ejemplo |
| --- | --- | --- |
| RPO, punto de recuperación | ¿Cuántos datos podemos permitirnos perder? | Como mucho una hora |
| RTO, tiempo de recuperación | ¿Cuánto tiempo podemos estar sin servicio? | Como mucho cuatro horas |

Si las copias válidas se completan cada 24 horas y no hay otro historial, la pérdida puede acercarse a un día. Eso describe la capacidad del mecanismo; el RPO es el objetivo que se exige. Si una copia falla o está corrupta, la pérdida real puede superar ese intervalo.

Cuanto más exigentes, más caro. Una tienda en línea y un blog personal no necesitan lo mismo.

## Tipos de copia

| Tipo | Qué copia | Restaurar |
| --- | --- | --- |
| Completa | Todo | Lo más simple: una sola copia |
| Incremental | Lo cambiado desde la última copia, de cualquier tipo | La completa y todas las incrementales posteriores |
| Diferencial | Lo cambiado desde la última completa | La completa y la última diferencial |

Lo habitual es combinarlas: una completa a la semana e incrementales cada día.

Se guardan varias, no solo la última. Si un error se descubre una semana tarde, la copia de ayer ya contiene el error. Una política de **retención** típica: las diarias de una semana, las semanales de un mes, las mensuales de un año.

## Bases de datos

Copiar los archivos de una base de datos mientras funciona puede producir una copia incoherente: unos archivos de un momento y otros de otro.

- **Volcado lógico.** Una herramienta de la base de datos exporta el contenido como instrucciones [SQL](/articulos/que-es-sql/) o en un formato propio, de forma coherente. Sencillo y portable, y lento con bases grandes.
- **Copia física y registro de cambios.** Se copian los archivos y, además, se guarda continuamente el registro de cada cambio. Permite la **recuperación a un instante concreto**: devolver la base al estado de las 14:32:10, justo antes del borrado accidental.

Los servicios gestionados de bases de datos en la nube suelen ofrecer esto de serie, y conviene comprobar cuánto tiempo guardan.

## Una copia sin probar no es una copia

El error más común es no restaurar nunca hasta que hace falta. Entonces aparecen los problemas: la copia estaba vacía, incompleta, corrupta, cifrada con una clave que nadie encuentra, o tarda tres días en restaurarse.

Hay que **ensayar la restauración** con regularidad, en un entorno aparte, y medir cuánto tarda. Es la única forma de saber si se cumplen el RPO y el RTO.

Como mínimo, comprobar que el contenido no se ha alterado:

```js
import { createHash } from "node:crypto";

const huella = (contenido) => createHash("sha256").update(contenido).digest("hex");

const original = "pedidos de octubre";
const huellaGuardada = huella(original);

const restaurado = "pedidos de octubre";

console.log(huella(restaurado) === huellaGuardada); // true
```

La igualdad de una [huella criptográfica](/articulos/funciones-hash/) permite detectar alteraciones con una probabilidad de colisión despreciable para este uso, si la huella de referencia es fiable. No demuestra que la copia inicial estuviera completa ni que el sistema pueda arrancar con ella: eso requiere ensayar la restauración.

## Proteger las copias

Las copias contienen todos los datos, así que son un objetivo tan valioso como la base de datos misma.

- **Cifrarlas**, y guardar la clave en un lugar distinto de la copia. Perder la clave es perder la copia.
- **Restringir el acceso**: pocas personas y servicios pueden leerlas o borrarlas.
- **Cumplir las normas de conservación.** Los datos personales se guardan solo el tiempo justificado, también en las copias, como pide el [RGPD](/articulos/rgpd-y-proteccion-de-datos/).

## Copia, réplica y snapshot

Una **copia de seguridad** está destinada a recuperar un estado conservado. Una **réplica** mantiene otro ejemplar operativo siguiendo cambios. Una **instantánea**, o *snapshot*, representa un punto en el tiempo mediante las capacidades del almacenamiento o del sistema que la crea.

Para una eliminación accidental, una réplica que recibe el borrado no conserva automáticamente el estado previo. Una copia histórica puede permitir recuperarlo. Una instantánea anterior también puede ayudar, pero necesitas conocer su retención, independencia y procedimiento de restauración.

| Criterio | Copia de seguridad | Réplica | Snapshot |
| --- | --- | --- | --- |
| Uso principal | Recuperación | Continuidad y reparto | Conservar un estado puntual |
| Sigue cambios posteriores | Según nuevas copias | Habitualmente sí | No en esa instantánea |
| Protege ante borrado propagado | Si conserva una versión válida | No necesariamente | Si sigue disponible el estado anterior |
| Independencia del origen | Debe diseñarse | Depende de la arquitectura | Depende de su implementación |

Un snapshot puede compartir bloques, cuenta o infraestructura con el origen, o almacenarse de otra forma según el servicio. No supongas independencia por su nombre. Para una base de datos, además, debes asegurar que el punto recuperado sea consistente o pueda recuperarse mediante sus registros.

Puedes combinar las tres técnicas. La decisión se comprueba restaurando y midiendo los objetivos de pérdida de datos y tiempo de recuperación, no únicamente verificando que existe un archivo llamado copia.

### Recuperar el mismo incidente de tres formas

Supón una tabla borrada por error a las diez. La réplica aplica el borrado segundos después: puede seguir ofreciendo servicio y carecer ya de la tabla. Un snapshot de las nueve conserva un punto anterior, si su implementación y retención permiten restaurarlo. Una copia independiente de la noche anterior conserva otro punto, quizá más antiguo, pero fuera del alcance del fallo que afectó al almacenamiento principal.

### Si falla el servidor pero los datos siguen bien

Ahora cambia el incidente: falla el servidor, pero los datos siguen correctos en otra réplica. Promocionarla puede recuperar el servicio antes que restaurar una copia completa. Son fallos diferentes y las técnicas aportan ventajas distintas.

La recuperación necesita comprobar también lo que se pierde entre el punto conservado y el incidente. Una copia más un registro de cambios puede permitir avanzar hasta un instante anterior al borrado. Sin ese historial, restaurar a las nueve recupera la tabla y pierde cambios válidos posteriores. La decisión debe incluir cómo se reconciliarán.

## Lo esencial

- Una copia de seguridad sirve si se puede restaurar; hay que probarlo.
- La replicación y los RAID no son copias de seguridad: replican también los errores.
- La regla 3-2-1 y copias inmutables o desconectadas reducen riesgos distintos; hay que comprobar su independencia y restauración.
- El RPO fija cuántos datos se pueden perder; el RTO, cuánto tiempo sin servicio.
- Las copias se cifran y se protegen como los datos originales.
