**Redis** es un almacén de datos que guarda la información en la memoria [RAM](/articulos/memoria-ram-y-almacenamiento/), y ofrece mecanismos de persistencia en disco. Funciona como un gran diccionario: a cada **clave** le corresponde un **valor**. Eso lo hace extremadamente rápido, y lo convierte en la herramienta habitual para cachés, sesiones, contadores y colas.

Es una [base de datos NoSQL](/articulos/bases-de-datos-nosql/) del tipo clave-valor.

## Qué problema resuelve

Una base relacional puede resolver consultas y restricciones complejas, y también utiliza memoria para evitar accesos a disco. Redis se especializa en operaciones sobre estructuras mantenidas en memoria; no toda consulta necesita el mismo trabajo.

Hay datos que se leen miles de veces por segundo y que no necesitan nada de eso: la sesión de un usuario, el resultado de una consulta cara, un contador de visitas. Para ellos, lo que importa es la velocidad.

Trabajar en memoria y ofrecer operaciones concretas puede reducir la latencia. El tiempo observado depende también de la red, la carga, el tamaño de los datos y la orden; no hay una garantía universal de menos de un milisegundo.

## Claves y valores

Las operaciones básicas son guardar, leer y borrar por clave. Los bloques de órdenes se ejecutan en `redis-cli`, conectado a un servidor de práctica vacío:

```
SET usuario:42:nombre "Ana"
GET usuario:42:nombre
DEL usuario:42:nombre
```

Las respuestas son `OK`, `Ana` y `1` (una clave borrada). Los dos puntos en las claves son una convención para organizarlas. Redis no los interpreta.

La búsqueda por clave se apoya en una [tabla hash](/articulos/tablas-hash/) y tiene coste esperado constante respecto al número de claves bajo sus supuestos. Eso no significa idéntica latencia con cualquier carga, tamaño de clave o resultado.

## Más que texto: las estructuras

Lo que distingue a Redis de un simple diccionario es que los valores pueden ser estructuras de datos, con operaciones propias que se ejecutan en el servidor.

| Tipo | Qué es | Uso típico |
| --- | --- | --- |
| Cadena | Texto, número o datos binarios | Caché, contadores |
| Lista | Secuencia ordenada | Colas, últimos elementos |
| Conjunto | Elementos sin repetir | Etiquetas, usuarios únicos |
| Hash | Campos y valores, como un objeto | Los datos de un usuario |
| Conjunto ordenado | Elementos con una puntuación | Clasificaciones, prioridades |
| Flujo | Registro de eventos al que se añade | Mensajería |

Un contador:

```
INCR visitas:portada
```

En el servidor vacío devuelve 1: `INCR` inicia la clave ausente en cero y la incrementa. Es **atómico** frente a otras órdenes: mil incrementos ejecutados con éxito sobre el mismo contador, sin otras modificaciones, lo aumentan en mil. Reintentar tras una respuesta perdida podría incrementarlo otra vez. Sin esa garantía, dos clientes podrían leer el mismo valor y escribir el mismo resultado, la [condición de carrera](/articulos/condiciones-de-carrera-y-bloqueos/) clásica.

Una clasificación, con un conjunto ordenado:

```
ZADD puntos 150 "ana" 90 "luis" 210 "marta"
ZREVRANGE puntos 0 1
```

Devuelve los dos primeros, Marta y Ana, ya ordenados. Redis mantiene el orden a medida que cambian las puntuaciones.

## Caducidad

A cualquier clave se le puede poner un tiempo de vida. Cuando vence, Redis la borra.

```
SET sesion:8f3a "usuario 42" EX 3600
```

Esa sesión desaparece al cabo de una hora. Este programa imita el mecanismo:

```js
const almacen = new Map();

function guardar(clave, valor, segundos, ahora) {
	almacen.set(clave, { valor, caduca: ahora + segundos });
}

function leer(clave, ahora) {
	const entrada = almacen.get(clave);

	if (!entrada || entrada.caduca <= ahora) {
		almacen.delete(clave);
		return null;
	}

	return entrada.valor;
}

guardar("sesion:42", "ana", 60, 0);

console.log(leer("sesion:42", 30)); // "ana"
console.log(leer("sesion:42", 61)); // null
```

La caducidad es lo que hace a Redis tan adecuado para una [caché](/articulos/que-es-una-cache/): los datos antiguos se eliminan solos.

## Para qué se usa

- **Caché.** Se guarda el resultado de una operación cara. La siguiente vez se lee de Redis y no se repite.
- **Sesiones.** Con varios servidores tras un [balanceador](/articulos/balanceador-de-carga/), las [sesiones](/articulos/sesiones-y-tokens/) deben estar en un sitio común y rápido.
- **Limitación de peticiones.** Un contador por cliente, con caducidad, como se describe en [limitación de peticiones](/articulos/limitacion-de-peticiones/).
- **Colas de trabajo.** Las listas permiten añadir por un extremo y retirar por el otro, la base de una [cola de mensajes](/articulos/colas-de-mensajes/) sencilla.
- **Publicación y suscripción**, para avisar en el momento a los clientes conectados.
- **Clasificaciones y contadores** en tiempo real.
- **Bloqueos** entre varios servidores, para que solo uno haga una tarea.

## Ejecución de las órdenes

En una instancia, las operaciones ordinarias sobre estas estructuras se ejecutan de forma serializada en el hilo principal. Redis también utiliza otros hilos para ciertos trabajos, incluida entrada/salida según versión y configuración:

- **Una operación como `INCR` no intercala un incremento ajeno entre su lectura y escritura.** Eso no convierte varias órdenes independientes en una sola operación atómica.
- **El coste depende de la orden.** Recorrer o devolver muchas claves cuesta más que consultar una pequeña por su nombre.

La consecuencia es la misma que en [Node.js](/articulos/que-es-nodejs/): una orden lenta detiene a todas las demás. Pedir todas las claves de una base grande con `KEYS *` puede dejar el servidor sin responder. En producción se evita.

## ¿Y si se apaga?

La memoria se pierde al cortarse la corriente. Redis ofrece dos formas de guardar en disco:

| Mecanismo | Cómo funciona | Qué se puede perder |
| --- | --- | --- |
| Instantáneas | Vuelca toda la memoria a un archivo cada cierto tiempo | Lo escrito desde la última |
| Registro de órdenes (AOF) | Registra escrituras; la política decide cuándo sincronizar | Con sincronización cada segundo, puede perderse alrededor del último segundo; otras políticas tienen otros límites |

Se pueden combinar. La durabilidad depende de persistencia, sincronización, almacenamiento y fallos previstos. La atomicidad de una orden no garantiza por sí sola su conservación tras una caída; son propiedades distintas de [ACID](/articulos/transacciones-y-acid/).

Para una caché no importa: si se pierde, se reconstruye. Para datos que no existen en ningún otro sitio, hay que pensarlo.

## Cuando la memoria se llena

La memoria es limitada, y más cara que el disco. Se configura un máximo y una **política de expulsión**: qué borrar para hacer sitio. Lo habitual en una caché es eliminar lo que lleva más tiempo sin usarse.

Al alcanzar `maxmemory`, la política `noeviction` rechaza las escrituras que necesitan más memoria. Con políticas de expulsión puede borrar claves elegibles; si no las hay, también puede rechazar. En Redis de 64 bits, `maxmemory` vale 0 por defecto, sin límite configurado: no hay que esperar que eso proteja al proceso de agotar la memoria del sistema.

## Varias máquinas

- **Réplicas.** Copias que siguen a un servidor principal, para repartir lecturas y sustituirlo si falla.
- **Clúster.** Los datos se reparten entre varias máquinas según la clave.

Son la [replicación y el particionado](/articulos/replicacion-y-particionado/) de cualquier base de datos distribuida.

## Lo que no es

- **Elegirlo como almacén principal requiere estudiar las garantías.** Su uso como caché junto a [PostgreSQL](/articulos/que-es-postgresql/) es distinto de conservar datos que no existen en otro lugar. Además de clave-valor, versiones y productos actuales ofrecen búsqueda, documentos y otras capacidades.
- **No es gratis.** Todo ocupa RAM.
- **Introduce datos duplicados.** Una caché puede quedar desactualizada respecto al original. Decidir cuándo invalidarla es la parte difícil.

## Licencia y alternativas

Redis cambió sus condiciones de licencia en 2024, y de ahí surgió Valkey, una bifurcación mantenida por la Linux Foundation. Hay otros almacenes compatibles con su protocolo. La compatibilidad de órdenes y funciones depende de cada producto y versión. Redis 8 añadió AGPLv3 como opción junto a RSALv2 y SSPLv1; hay que consultar la licencia concreta de la distribución elegida.

## Errores comunes

- **Confundir caducidad y validez del dato.** El origen puede cambiar antes de que venza la clave; la caché necesita una política de actualización.
- **Separar una operación compuesta en lectura y escritura.** Dos clientes pueden intercalarse; usa una operación atómica adecuada al caso.
- **Tratar memoria, persistencia y réplica como una sola garantía.** Hay que decidir cuánto se puede perder y comprobar la recuperación con la configuración elegida.

## Lo esencial

- Redis guarda los datos en memoria, como pares de clave y valor.
- Sus valores pueden ser listas, conjuntos, hashes y otras estructuras.
- Las claves pueden caducar solas, lo que lo hace ideal como caché.
- Operaciones como `INCR` son atómicas frente a otras órdenes; una secuencia de órdenes requiere coordinación propia.
- Su papel como caché o almacén principal exige garantías y políticas de recuperación diferentes.
