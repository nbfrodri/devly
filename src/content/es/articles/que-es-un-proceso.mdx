Un **proceso** es una instancia de un programa en ejecución, con memoria, recursos y estado propios. El programa describe qué hacer; el proceso conserva lo que está ocurriendo al hacerlo. Una receta es el programa; una preparación concreta del plato es el proceso.

## Programa y proceso no son lo mismo

Un programa puede estar guardado en archivos sin que nadie lo esté ejecutando. Al iniciarlo, el [sistema operativo](/articulos/que-es-un-sistema-operativo/) prepara un contexto de ejecución: memoria accesible, instrucciones por ejecutar y recursos iniciales. No necesita cargar de golpe todos sus archivos en RAM; algunas partes pueden incorporarse cuando se usan.

En un programa interpretado, un intérprete ejecuta las instrucciones del lenguaje dentro de un proceso. El archivo de código fuente no se convierte sin más en instrucciones de la CPU.

Un mismo programa puede tener varias instancias. Imagina un conversor que se lanza dos veces: el proceso A trabaja con `foto-a.png` y el B con `foto-b.png`. Ambos ejecutan el mismo código, pero pueden estar en pasos distintos y conservar datos distintos.

La relación con las ventanas depende de la aplicación. Dos ventanas pueden pertenecer al mismo proceso, y una sola aplicación puede repartir su trabajo entre varios. Contar ventanas no permite contar procesos.

## Qué conserva el sistema

- **Un identificador**, normalmente un número llamado **PID**. Distingue procesos dentro de un ámbito del sistema; puede reutilizarse después de que un proceso termine.
- **Un espacio de direcciones** con código, datos y zonas disponibles para nuevas asignaciones. No implica que toda esa memoria esté ocupando RAM física. Lo explica la [memoria virtual](/articulos/memoria-virtual/).
- **Estado de ejecución**: el punto por el que va cada hilo y sus registros del [procesador](/articulos/como-funciona-un-procesador/).
- **Recursos y permisos**: por ejemplo, archivos abiertos, conexiones y la identidad con la que puede acceder a ellos.

En los dos conversores, una variable llamada `ancho` puede valer 800 en A y 1200 en B. Usar el mismo nombre, o incluso la misma dirección virtual, no obliga a compartir el mismo dato físico.

## Aislamiento y sus límites

En un sistema con protección de memoria, un proceso no obtiene acceso arbitrario a la memoria privada de otro por conocer su dirección. El sistema operativo configura permisos que el hardware comprueba.

Eso no significa que toda memoria esté separada: se pueden autorizar regiones compartidas o mecanismos de inspección. Tampoco garantiza que un fallo solo afecte al proceso que lo causó. Si A termina de forma inesperada, B puede seguir ejecutándose, pero ambos podrían depender de un archivo que A dejó incompleto o de un servicio que ya no responde.

El aislamiento limita daños directos; no elimina las dependencias entre programas ni todos los errores de software.

## En ejecución, listo y bloqueado

Para seguir el reparto de CPU, supongamos **dos procesos con un solo hilo cada uno** y un único contexto de ejecución disponible, sin multihilo simultáneo. Usaremos tres estados básicos:

| Estado | Qué falta para avanzar |
| --- | --- |
| En ejecución | Nada: la CPU está ejecutando sus instrucciones |
| Listo | Que el planificador le asigne CPU |
| Bloqueado | Que ocurra un evento que espera, como finalizar una lectura |

Sigamos A y B en una ejecución posible:

| Paso | A | B | Qué ocurre |
| --- | --- | --- | --- |
| 1 | En ejecución | Listo | A calcula el tamaño de su imagen |
| 2 | Bloqueado | En ejecución | A pide una lectura y debe esperar; B aprovecha la CPU |
| 3 | Listo | En ejecución | La lectura de A termina, pero B conserva su turno |
| 4 | En ejecución | Listo | El planificador elige A y guarda el estado de B |

La transición clave es la tercera: **dejar de esperar datos no equivale a empezar a ejecutar**. A ya tiene lo que necesitaba, pero todavía necesita turno. Un proceso que espera activamente consultando una condición seguiría ejecutándose cuando tiene CPU; no estaría bloqueado en este sentido.

Un proceso bloqueado no ejecuta instrucciones de su hilo durante esa espera, pero conserva recursos como memoria y archivos. El sistema también puede gastar CPU en completar la operación que lo despertará. Bloqueado no significa «sin coste».

## Repartir el procesador

El [planificador](/articulos/planificador-de-procesos/) decide qué tarea lista obtiene CPU según su política. Puede cambiar de tarea porque la actual se bloquea, termina, agota su turno o aparece otra con prioridad suficiente. No todas las políticas usan el mismo intervalo fijo.

El [cambio de contexto](/articulos/cambio-de-contexto/) guarda el estado necesario de quien sale y restaura el de quien entra. A puede continuar desde su punto de ejecución conservado, pero sí puede observar que pasó tiempo o que cambió un recurso compartido. Guardar registros no congela el resto del mundo.

Si hay varios núcleos, A y B pueden ejecutarse en paralelo. Si hay menos recursos de ejecución que tareas listas, el sistema tiene que repartirlos.

## Cómo nace y cómo termina

Los sistemas ofrecen operaciones para crear procesos e iniciar programas. En Unix, por ejemplo, `fork` crea un proceso hijo a partir del padre y la familia `exec` sustituye el programa que ejecuta un proceso. Son acciones diferentes: ejecutar otro programa con `exec` no crea por sí solo otro PID. Otros sistemas ofrecen interfaces distintas.

Un proceso termina cuando acaba su trabajo, sufre un fallo fatal o es detenido con los permisos necesarios. El sistema libera sus recursos; puede conservar temporalmente información de la terminación para que otro proceso la recoja. Un archivo ya escrito no se borra automáticamente al salir.

## Varios hilos dentro de un proceso

Un proceso puede contener varios [hilos](/articulos/hilos-y-concurrencia/): flujos de ejecución con su punto de ejecución y su pila de llamadas, que comparten el espacio de direcciones del proceso.

Con varios hilos, uno puede estar bloqueado mientras otro ejecuta. Por eso la tabla anterior usaba deliberadamente procesos de un solo hilo: en un sistema real, la planificación suele trabajar con esas unidades de ejecución.

Compartir memoria facilita intercambiar datos, pero exige coordinación cuando el orden importa. Dos actualizaciones sin la sincronización adecuada pueden producir una [condición de carrera](/articulos/condiciones-de-carrera-y-bloqueos/). La comparación [proceso e hilo](/articulos/proceso-e-hilo/) desarrolla cuándo conviene cada organización.

## Errores comunes

- **Confundir el programa con una instancia.** Dos procesos pueden ejecutar el mismo código con datos y estados diferentes.
- **Contar ventanas como procesos.** La aplicación decide cómo reparte su trabajo; una ventana no es una unidad del planificador.
- **Equiparar listo con bloqueado.** Al primero solo le falta CPU; el segundo espera además un evento. Añadir CPU no resuelve una lectura todavía pendiente.

## Lo esencial

- Un proceso reúne una ejecución de un programa, su memoria, recursos y estado.
- La protección de memoria limita accesos; compartir recursos o depender de otro proceso requiere tener en cuenta esas relaciones.
- En el modelo de un hilo, listo significa esperar CPU y bloqueado significa esperar un evento.
- El planificador reparte CPU y el cambio de contexto permite continuar; varios hilos comparten memoria dentro de un proceso.
