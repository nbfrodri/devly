Los sistemas basados en **Linux**, **Windows** y **macOS** administran hardware y ejecutan programas, pero ofrecen interfaces y entornos diferentes. Aquí comparamos su uso en un ordenador de desarrollo. Linux designa una familia de sistemas construidos alrededor de un núcleo; Windows y macOS son familias de productos de Microsoft y Apple.

## Qué compone cada entorno

[Linux](/articulos/que-es-linux/) se integra en [distribuciones](/articulos/distribuciones-de-linux/) con bibliotecas, gestores de paquetes y políticas de actualización propias. Windows utiliza el núcleo de la familia NT, servicios e [interfaces para las aplicaciones, o APIs](/articulos/que-es-una-api/). macOS utiliza XNU, que combina componentes como Mach y BSD, junto con aplicaciones y frameworks de Apple: conjuntos de herramientas y estructuras para desarrollar programas.

Linux y macOS comparten convenciones de tipo Unix, pero no tienen las mismas bibliotecas ni ejecutan automáticamente los mismos binarios. La familia del sistema orienta sobre ciertas interfaces; no resuelve toda la compatibilidad.

| Criterio | Distribución Linux | Windows | macOS |
| --- | --- | --- | --- |
| Integración y mantenimiento | Proyecto y proveedores de la distribución | Microsoft y proveedores de componentes | Apple y proveedores de componentes |
| Núcleo | Linux, con versión y configuración concretas | Familia Windows NT | XNU |
| Entorno de aplicaciones | Depende de distribución y paquetes | APIs y herramientas de Windows | APIs y frameworks de macOS |
| Hardware admitido | Arquitecturas, controladores y configuración compatibles | Requisitos de la edición y controladores | Modelos admitidos por esa versión de macOS |
| Licencias y coste | Licencias de cada componente; puede haber soporte de pago | Condiciones de la edición y su adquisición | Condiciones de Apple y del software instalado |

Un sistema puede incorporar componentes abiertos y cerrados. Precio, acceso al código y permiso de redistribución son cuestiones distintas.

## El mismo proyecto: leer un archivo de datos

Nuestro proyecto guarda `Foto.csv` dentro de una carpeta llamada `Datos`. El archivo contiene una cabecera y una fila. Queremos obtener esas dos líneas en los tres entornos.

### Construir la ruta

En un entorno Linux típico puede estar bajo `/home/ana/proyecto`; en macOS, bajo `/Users/ana/proyecto`; en Windows, bajo una ruta como `C:\Users\Ana\proyecto`. Son ejemplos, no ubicaciones obligatorias.

La biblioteca de rutas del lenguaje permite unir componentes usando las reglas del entorno. No convierte cualquier ruta ajena en una ruta equivalente: unir nombres y traducir la ubicación de un archivo son problemas distintos.

Este programa Node.js crea sus propios datos temporales y utiliza siempre la misma escritura de los nombres. Guárdalo como `leer.mjs` y ejecútalo con `node leer.mjs` en un entorno con Node disponible:

```js
import { mkdtempSync, mkdirSync, writeFileSync, readFileSync,
	unlinkSync, rmdirSync, existsSync } from "node:fs";
import { tmpdir } from "node:os";
import { join } from "node:path";

const base = mkdtempSync(join(tmpdir(), "devly-rutas-"));
const carpeta = join(base, "Datos");
const archivo = join(carpeta, "Foto.csv");
try {
	mkdirSync(carpeta);
	writeFileSync(archivo, "valor\n12\n", "utf8");
	const lineas = readFileSync(archivo, "utf8").trim().split(/\r?\n/);
	console.log(lineas.length); // 2
} finally {
	if (existsSync(archivo)) unlinkSync(archivo);
	if (existsSync(carpeta)) rmdirSync(carpeta);
	rmdirSync(base);
}
```

El ejemplo lee líneas; no es un analizador completo de CSV. Tampoco usa una carpeta fija que pudiera contener datos anteriores.

### Respetar mayúsculas y contenido

Si el código intenta abrir `datos/foto.csv`, puede funcionar donde los nombres no distinguen mayúsculas y fallar donde sí. Lo correcto es utilizar `Datos` y `Foto.csv`, como se crearon.

La sensibilidad depende del sistema de archivos y de su configuración. APFS tiene variantes con y sin distinción; Windows puede configurar esa propiedad por directorio en NTFS. En Linux es habitual distinguir nombres, pero los volúmenes montados también tienen sus reglas. No se deduce únicamente del logotipo del sistema operativo.

Los [finales de línea](/articulos/salto-de-linea-en-windows-y-linux/) también pertenecen al contenido y a las herramientas. El patrón del ejemplo admite LF y CRLF; no presupone que todo archivo de Windows tenga uno ni que todo archivo de Linux tenga otro.

## Acceder y ejecutar no es lo mismo

Para leer el archivo hay que tener acceso a su ruta y contenido. Linux y macOS ofrecen permisos de tipo Unix y mecanismos adicionales; Windows utiliza reglas de acceso basadas en identidades y listas. Copiar un archivo entre formatos no conserva necesariamente todas esas reglas.

Ejecutar un programa exige además un formato y un entorno admitidos. Los ejecutables nativos habituales usan ELF en Linux, PE en Windows y Mach-O en macOS, con [arquitectura y ABI](/articulos/que-es-una-abi/) compatibles. Ni añadir `.exe` ni conceder ejecución transforma bytes arbitrarios en un programa válido.

El ejemplo usa código JavaScript y una instalación de Node para cada destino. Una dependencia con código nativo puede necesitar una compilación distinta; que el archivo fuente sea idéntico no garantiza que toda su cadena de dependencias lo sea.

## WSL, máquinas virtuales y contenedores

**WSL** permite utilizar entornos Linux desde Windows. WSL 1 traduce llamadas mediante una capa de compatibilidad; WSL 2 ejecuta un núcleo Linux en una máquina virtual administrada. Su integración no elimina diferencias de rutas, permisos o acceso a archivos entre ambos lados.

Un **[contenedor Linux](/articulos/contenedores-y-maquinas-virtuales/)** necesita un núcleo Linux compatible. En macOS, herramientas como Docker Desktop lo proporcionan mediante una máquina virtual; en Windows pueden utilizar WSL 2 u otros mecanismos. También existen contenedores de Windows.

Un contenedor ayuda a fijar herramientas y bibliotecas, pero arquitectura, núcleo, volúmenes y servicios externos siguen influyendo. Para nuestro proyecto, montar una carpeta anfitriona puede conservar diferencias de nombres o permisos que no aparecen dentro de la imagen.

## Elegir según la tarea

Si necesitas una aplicación, un dispositivo o una herramienta de plataforma concreta, empieza comprobando sus sistemas y versiones admitidos. Si el proyecto se publicará en Linux, prueba su ejecución allí aunque desarrolles en otro entorno. El mismo criterio se aplica a un destino Windows o macOS.

La continuidad de actualizaciones, las necesidades del equipo y el soporte disponible también cuentan. No hay una clasificación universal de rendimiento, facilidad o seguridad que decida todos los proyectos.

## Errores comunes

- **Equiparar familia Unix con binarios intercambiables.** Las interfaces y dependencias concretas pueden diferir.
- **Dar por válida una ruta porque funciona en un equipo.** Comprueba nombres, base, volumen y permisos.
- **Suponer que el contenedor reproduce todo el ordenador.** Fija parte del entorno; aún hay dependencias externas.

## Lo esencial

- Los tres entornos resuelven necesidades similares con interfaces y componentes distintos.
- El mismo proyecto debe definir rutas, nombres, formatos y permisos coherentes.
- Fuente compartida no garantiza compatibilidad de todas las dependencias.
- La prueba relevante es ejecutar el proyecto en sus destinos reales.
