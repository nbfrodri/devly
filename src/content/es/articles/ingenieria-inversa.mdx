La **ingeniería inversa** estudia un programa ya construido para reconstruir su comportamiento, estructura o interfaces. Puede partir de un [binario](/articulos/que-es-un-binario/) sin disponer de su fuente, aunque también aprovecha documentación, símbolos de depuración y otras evidencias disponibles.

Sirve para recuperar conocimiento perdido, estudiar compatibilidad, investigar fallos o preservar software. El resultado suele ser una explicación contrastada de cómo funciona, no una recuperación literal de lo que escribió su autor.

## Análisis estático: inspeccionar sin ejecutar

**Desensamblar** convierte bytes de instrucciones en una representación legible. Hay que conocer arquitectura, modo y punto de inicio; los mismos bytes pueden interpretarse de otra forma bajo otro modelo. `objdump`, de GNU Binutils, permite inspeccionar archivos objeto y desensamblar código para los destinos admitidos por su instalación.

**Descompilar** intenta reconstruir operaciones y control de flujo en una forma parecida a un lenguaje de alto nivel. Nombres, tipos o estructuras pueden haberse perdido o transformado; algunos sobreviven en símbolos y metadatos. Varias fuentes distintas pueden generar el mismo código máquina, así que no suele existir una única reconstrucción original.

## Un desensamblador que conoce su formato

Usaremos una máquina didáctica con acumulador de ocho bits. CARGAR (`01`) y SUMAR (`02`) llevan un operando de un byte; PARAR (`ff`) no lleva ninguno. SUMAR conserva el resultado módulo 256. Es el mismo modelo que desarrolla [emuladores](/articulos/emuladores/).

Este desensamblador recibe un array de bytes que se supone contiene instrucciones desde la posición cero. Recorre toda la entrada y rechaza códigos desconocidos u operandos ausentes:

```js
const INSTRUCCIONES = { 0x01: "CARGAR", 0x02: "SUMAR", 0xff: "PARAR" };

function desensamblar(bytes) {
	if (!Array.isArray(bytes) || !Array.from(bytes).every(
		(b) => Number.isInteger(b) && b >= 0 && b <= 255,
	)) throw new TypeError("La entrada debe contener bytes");

	const lineas = [];
	let pc = 0;
	while (pc < bytes.length) {
		const codigo = bytes[pc];
		const nombre = INSTRUCCIONES[codigo];
		if (!nombre) throw new Error(`Instrucción desconocida en ${pc}`);
		if (codigo === 0xff) {
			lineas.push(`${pc}: ${nombre}`);
			pc += 1;
		} else {
			if (pc + 1 >= bytes.length) throw new Error(`Falta el operando en ${pc}`);
			lineas.push(`${pc}: ${nombre} ${bytes[pc + 1]}`);
			pc += 2;
		}
	}
	return lineas.join("; ");
}

console.log(desensamblar([0x01, 5, 0x02, 7, 0x02, 30, 0xff])); // "0: CARGAR 5; 2: SUMAR 7; 4: SUMAR 30; 6: PARAR"
```

La longitud importa: tras CARGAR en cero, el siguiente código está en dos, no en uno. El cinco es un dato de la instrucción. Para `[0x01]` falta ese dato, así que el resultado no puede ser «CARGAR undefined».

La función muestra instrucciones; **no las ejecuta**. Por eso puede describir `[0x01, 5]` aunque el emulador no acepte terminar sin PARAR. También recorre bytes después de PARAR, que podrían ser datos o código no alcanzado: la suposición de que toda la entrada es código pertenece a este ejemplo, no a cualquier binario real.

## De las instrucciones a una hipótesis

Con la semántica definida podemos reconstruir el estado:

| Instrucción | Acumulador después |
| --- | --- |
| CARGAR 5 | 5 |
| SUMAR 7 | 12 |
| SUMAR 30 | 42 |
| PARAR | Se devuelve 42 |

La hipótesis es «este programa devuelve 42». Ejecutarlo en el emulador permite contrastarla. Cambiar el operando 30 por 31 produce 43 según el mismo modelo. Si observásemos otra cosa, revisaríamos la decodificación, la semántica o las condiciones iniciales.

En un programa con entradas variables, probar un caso no demuestra todos sus comportamientos. Un análisis debe distinguir qué afirma el código, qué se ha observado y qué sigue siendo una hipótesis.

## Análisis dinámico y herramientas

El **análisis dinámico** observa el programa mientras se ejecuta: argumentos, resultados, memoria y operaciones externas. Un [depurador](/articulos/que-es-un-depurador/) permite detenerse en puntos concretos e inspeccionar el estado. Esa observación puede depender de la entrada, del entorno y de la temporización.

**Ghidra** combina desensamblado, descompilación, análisis de flujo y automatización para distintos formatos y procesadores. Sus nombres y tipos inferidos deben contrastarse; una representación legible puede ser incorrecta si parte de una arquitectura o dirección equivocada.

Para software potencialmente dañino, el entorno de análisis requiere aislamiento y control de archivos y comunicaciones. Una [máquina virtual](/articulos/virtualizacion/) ayuda a separar recursos, pero no garantiza contención si comparte datos sensibles, tiene servicios expuestos o existe una vulnerabilidad de escape.

## Qué dificulta la reconstrucción

- **Optimización:** una función puede integrarse en otra o desaparecer por completo; el código generado no conserva necesariamente la organización del fuente.
- **Código y datos mezclados:** una secuencia de bytes puede parecer una instrucción sin ejecutarse nunca.
- **Ofuscación y generación dinámica:** el programa puede ocultar o construir operaciones durante su ejecución; una pasada estática no las revela todas.

## Límites legales: España

El artículo 100 de la Ley de Propiedad Intelectual, consultado el 15 de octubre de 2026, distingue dos supuestos. Su apartado 3 permite al usuario legítimo estudiar el funcionamiento durante operaciones que tiene derecho a realizar. Los apartados 5 a 7 regulan la reproducción y traducción indispensables para obtener interoperabilidad con un programa independiente.

Esta segunda excepción exige una persona facultada, información que no esté disponible de forma fácil y rápida y limitarse a las partes necesarias. Restringe el uso y la comunicación de lo obtenido y no permite crear una expresión sustancialmente similar ni perjudicar injustificadamente la explotación normal. No es una autorización general para copiar cualquier programa. La jurisdicción, los derechos disponibles y los actos concretos determinan el análisis; observar y descompilar no son permisos intercambiables.

## Errores comunes

- **Tomar el descompilado por el fuente original.** Es una reconstrucción, con información conservada y decisiones inferidas.
- **Concluir seguridad porque una ejecución no falló.** Puede haber caminos que la prueba no recorrió.
- **Leer cualquier byte como código.** Hay que justificar formato, arquitectura y límites de las instrucciones.

## Lo esencial

- La ingeniería inversa reconstruye conocimiento a partir de un programa y sus evidencias.
- Desensamblar, descompilar y observar la ejecución responden a preguntas distintas.
- Las hipótesis necesitan condiciones explícitas y comprobaciones.
- La posibilidad técnica de analizar software no determina por sí sola los derechos para hacerlo.
