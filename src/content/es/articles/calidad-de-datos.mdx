La **calidad de datos** mide si unos datos son **adecuados para el uso** que se les va a dar. No hay datos perfectos en abstracto: los mismos datos pueden servir para un informe mensual y no para facturar. Se valora con varias dimensiones, como si están completos, si son exactos o si están al día.

## Por qué importa

Las decisiones, los informes y los modelos de [aprendizaje automático](/articulos/que-es-el-aprendizaje-automatico/) heredan los defectos de sus datos. Un cliente duplicado recibe dos cartas; una fecha mal escrita desordena un informe; un modelo entrenado con etiquetas erróneas aprende errores.

## Las dimensiones

El marco de calidad de datos del gobierno británico, una de las referencias públicas, usa dimensiones como estas:

| Dimensión | Pregunta | Ejemplo de fallo |
| --- | --- | --- |
| Completitud | ¿Falta algo? | Clientes sin correo |
| Exactitud | ¿Refleja la realidad? | Una dirección antigua |
| Unicidad | ¿Hay duplicados? | La misma persona dos veces |
| Coherencia | ¿Cuadra entre sistemas? | Un pedido sin cliente |
| Actualidad | ¿Está al día? | Precios del año pasado |
| Validez | ¿Cumple el formato y las reglas? | Una edad de 250 años |

## Medirla

Parte de la calidad se puede medir con reglas automáticas. En este ejemplo, el formulario admite edades enteras de 0 a 120; es una regla del sistema, no una prueba de la edad real:

```js
const clientes = [
	{ correo: "ana@ejemplo.com", edad: 34 },
	{ correo: null, edad: 41 },
	{ correo: "luis@ejemplo", edad: 250 },
	{ correo: "ana@ejemplo.com", edad: 34 },
];

const completos = clientes.filter((c) => c.correo).length / clientes.length;
const validos = clientes.filter(
	(c) => Number.isInteger(c.edad) && c.edad >= 0 && c.edad <= 120,
).length;
const correosPresentes = clientes.map((c) => c.correo).filter(Boolean);
const correosDistintos = new Set(correosPresentes).size;

console.log(completos); // 0.75
console.log(validos); // 3
console.log(correosDistintos); // 2
```

Un cuarto de las filas no tiene correo; tres cumplen la regla de edad. Hay tres correos presentes y dos valores distintos: uno se repite. Eso no demuestra por sí solo que se haya duplicado una persona, porque dos personas podrían compartir una dirección. Tampoco se ha comprobado que los correos sean utilizables ni que las edades reflejen la realidad.

## Mejor prevenir

Corregir datos después es caro. Es más eficaz impedir que entren mal:

- **Restricciones** en la base de datos: tipos, campos obligatorios, unicidad, [claves foráneas](/articulos/que-es-una-clave-foranea/).
- **Validación** en los formularios y en las [API](/articulos/que-es-una-api/).
- **Una sola fuente de verdad** para cada dato, en lugar de copias que se desincronizan.
- **Comprobaciones automáticas** en los [procesos ETL](/articulos/procesos-etl/), que detengan la carga si algo no cuadra.
- **Responsables**: alguien a cargo de cada conjunto de datos.

La [deriva de datos y de concepto](/articulos/deriva-de-datos-y-de-concepto/) obliga a distinguir cambios del entorno, fallos de preparación y pérdida de calidad predictiva.

## Errores comunes

- **Confundir validez y exactitud.** Un precio bien formado puede ser incorrecto; contrastarlo exige una fuente fiable.
- **Contar valores ausentes como identificadores distintos.** Un `null` en un conjunto no representa una persona única.
- **Eliminar duplicados solo por coincidencia de un campo.** Antes hay que decidir qué identifica a la entidad y qué coincidencias son legítimas.

## Lo esencial

- Unos datos tienen calidad si sirven para el uso previsto.
- Se valora en dimensiones: completitud, exactitud, unicidad, coherencia, actualidad y validez.
- Las reglas automáticas detectan ciertos defectos; la exactitud también requiere contrastar con la realidad.
- Prevenir con restricciones y validación es más barato que corregir después.
