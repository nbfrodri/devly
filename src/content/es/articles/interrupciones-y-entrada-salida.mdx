La **entrada y salida**, E/S, permite que el [procesador](/articulos/como-funciona-un-procesador/) intercambie datos con dispositivos como un [teclado](/articulos/perifericos-de-entrada/), un disco o una [tarjeta de red](/articulos/tarjeta-de-red/). Una **interrupción externa** es un aviso que solicita atención del procesador sin exigir que el programa pregunte continuamente si ocurrió algo.

Transferir datos y avisar de que una operación terminó son responsabilidades diferentes. Una interrupción puede notificar una transferencia, pero no transporta por sí misma todo el contenido recibido.

## La interfaz del dispositivo

Un controlador de hardware puede exponer registros para que el software consulte y cambie su estado:

| Registro | Ejemplo de información |
| --- | --- |
| Estado | Operación pendiente, completada o con error |
| Órdenes | Iniciar una lectura |
| Datos o descriptores | Datos transferidos o ubicación y tamaño del búfer |

En **E/S mapeada en memoria**, esos registros ocupan direcciones del espacio físico y se accede mediante instrucciones de lectura o escritura. No se comportan necesariamente como RAM ordinaria: leer puede retirar un dato o escribir puede iniciar una operación. El software debe seguir el contrato del dispositivo.

El **controlador de software**, o *driver*, conoce ese contrato. No es lo mismo que el circuito controlador: uno es software y el otro hardware. El driver ofrece operaciones al sistema operativo y prepara los accesos y recursos necesarios.

## Seguir una operación mediante sondeo

Supongamos que se ordena una lectura y el dispositivo pasa a «completado» en el instante 50 de un modelo discreto. Si consultamos cada unidad de tiempo desde cero:

```js
const listoEnElInstante = 50;
let consultas = 0;

for (let instante = 0; ; instante++) {
	consultas++;
	if (instante >= listoEnElInstante) break;
}

console.log(consultas); // 51
```

Hay cincuenta consultas sin finalización y una que la detecta. Los instantes son unidades del ejemplo; el código no mide un dispositivo ni simula instrucciones de CPU. Consultar repetidamente se llama **sondeo**, o *polling*.

Si el software espera activamente, consume CPU durante la espera. También puede consultar periódicamente y hacer otro trabajo entre consultas, aumentando potencialmente el tiempo hasta detectar el evento.

## Seguir la misma operación con un aviso

Con interrupciones habilitadas y configuradas, el driver puede iniciar la lectura y dejar que el procesador ejecute otra tarea. Cuando el dispositivo termina, solicita atención mediante el mecanismo de interrupciones de la plataforma.

Un recorrido típico es:

1. El controlador de interrupciones entrega una petición atendible al núcleo correspondiente.
2. El procesador conserva el estado de retorno necesario en un punto definido por la arquitectura; el software guarda los registros adicionales que requiera.
3. Se ejecuta un **manejador de interrupción**, que identifica y atiende el motivo del aviso.
4. El manejador registra el resultado y reconoce o despeja el evento según el dispositivo; puede dejar trabajo para después.
5. El sistema restaura un contexto de ejecución. Puede retomar la tarea anterior o decidir ejecutar otra.

La atención no es instantánea: prioridades, enmascaramiento temporal y carga del sistema pueden retrasarla. Tampoco hay una regla universal de «terminar toda la instrucción actual»: lo exigible es conservar un estado de retorno válido para esa arquitectura.

Aunque la aplicación no atienda directamente el aviso, puede observar su coste temporal o el resultado de la operación. Entrar y salir del manejador también consume recursos.

## Cuándo conviene cada mecanismo

| Criterio | Sondeo | Interrupciones |
| --- | --- | --- |
| Inicia la comprobación | El software consulta estado | Un evento solicita atención |
| Con pocos eventos | Puede hacer muchas consultas vacías | Permite dedicar tiempo a otras tareas |
| Con muchos eventos | Puede procesar grupos de completados | Un aviso por evento puede ser costoso |
| Latencia | Depende del ritmo de consulta | Depende de entrega y atención |

Si consultas una vez por segundo, un evento recién llegado puede esperar casi un segundo. Consultar sin pausa reduce esa espera a costa de ocupar CPU. Una espera activa puede tener sentido en un contexto dedicado con requisitos de latencia muy cortos.

Un diseño **híbrido** recibe un aviso de actividad y después sondea una cola para procesar varios elementos. Al agotarse el trabajo, vuelve a depender de avisos. Debe coordinar el último sondeo con la reactivación de interrupciones para no perder un evento en esa transición.

## DMA: transferir es otra tarea

El **[acceso directo a memoria, DMA](/articulos/acceso-directo-a-memoria-dma/)** permite mover datos entre dispositivo y memoria sin que la CPU copie cada unidad mediante instrucciones. El driver prepara búferes, direcciones y descriptores válidos, y coordina cuándo pueden utilizarse los datos.

La finalización puede notificarse con una interrupción o descubrirse mediante sondeo. DMA no impone una de esas opciones y no elimina la necesidad de comprobar errores, longitudes y sincronización.

## Interrupciones, excepciones y llamadas al sistema

Estos mecanismos pueden compartir parte de la infraestructura, pero su origen importa:

- Una **interrupción externa**, como la de un temporizador, llega de forma asíncrona respecto de las instrucciones del programa. Puede permitir que el [planificador](/articulos/planificador-de-procesos/) vuelva a evaluar qué tarea ejecutar.
- Una **excepción** está relacionada con la ejecución de una instrucción: por ejemplo, un acceso que provoca un [fallo de página](/articulos/memoria-virtual/). El sistema examina su causa; no siempre necesita leer del disco ni terminar el proceso.
- Una **[llamada al sistema](/articulos/llamadas-al-sistema/)** solicita deliberadamente un servicio del núcleo mediante el mecanismo definido por la plataforma. No tiene por qué utilizar la misma instrucción ni la misma entrada que una interrupción externa.

El modelo concreto de privilegios y drivers depende del sistema; no todos los controladores de software se ejecutan obligatoriamente dentro del núcleo.

Las [promesas](/articulos/promesas-y-async-await/) y el bucle de eventos de JavaScript trabajan en otro nivel. Una finalización de E/S puede acabar despertando trabajo de aplicación, pero una promesa también puede resolverse sin E/S física. No existe una interrupción de dispositivo por cada promesa.

## Lo esencial

- El driver utiliza la interfaz del controlador de hardware para ordenar y consultar operaciones.
- Sondeo e interrupciones permiten descubrir eventos con costes y latencias distintos.
- DMA mueve datos; la notificación de finalización es una decisión separada.
- Interrupciones externas, excepciones y llamadas al sistema tienen orígenes y contratos diferentes.
