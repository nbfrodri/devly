En esta comparación, **SQL** se usa como abreviatura habitual de base **relacional**: organiza datos en tablas y relaciones. **NoSQL** agrupa modelos diferentes, como documentos, clave-valor y grafos. SQL es un lenguaje, no una garantía de arquitectura: la distinción no clasifica por sí sola todas las capacidades de un producto.

NoSQL no significa datos sin estructura. Un documento tiene campos y tipos; lo que cambia es cómo se modelan, consultan y hacen cumplir sus reglas.

Este artículo las compara. Cada una tiene su explicación completa en [qué es una base de datos](/articulos/que-es-una-base-de-datos/) y [qué es una base de datos NoSQL](/articulos/bases-de-datos-nosql/).

## La diferencia de fondo

En una base relacional **defines la estructura antes de guardar nada**: qué tablas hay, qué columnas tiene cada una y de qué tipo. El motor aplica las restricciones declaradas según sus reglas de tipos y configuración.

En una base de documentos se pueden admitir formas distintas dentro de una colección. Eso no impide declarar validación: MongoDB, por ejemplo, puede rechazar documentos que incumplan el esquema configurado. Otras familias NoSQL tienen reglas diferentes.

## El mismo dato en los dos modelos

Un cliente con dos pedidos, en una base relacional, se reparte en dos tablas unidas por una clave:

| id | nombre |
| --- | --- |
| 1 | Ana |

| id | cliente_id | total |
| --- | --- | --- |
| 10 | 1 | 25 |
| 11 | 1 | 40 |

Una opción en una base de documentos es guardar juntos el cliente y un conjunto acotado de pedidos:

```js
const cliente = {
	nombre: "Ana",
	pedidos: [
		{ id: 10, total: 25 },
		{ id: 11, total: 40 },
	],
};

console.log(cliente.pedidos.length); // 2
```

En el primer caso, para ver a Ana con sus pedidos hay que combinar las dos tablas. En el segundo se lee un solo documento. En este ejemplo ninguno duplica los pedidos. Si en el modelo documental se decide copiarlos en otra colección para otras consultas, habrá que mantener ambas versiones; también se pueden referenciar. Si la lista crece sin límite, incrustarla deja de ser adecuada.

## Comparación

| | SQL (relacional) | NoSQL |
| --- | --- | --- |
| Forma de los datos | Tablas de filas y columnas | Documentos, clave-valor, columnas anchas o grafos |
| Estructura | Esquema declarado; también puede almacenar JSON | Depende del modelo; documentos pueden variar y tener validación |
| Relaciones | Claves y uniones de tablas | Dependen de la familia; en grafos son centrales |
| Lenguaje de consulta | [SQL](/articulos/que-es-sql/), común a todas | Propio de cada sistema |
| Transacciones | Habituales; alcance y aislamiento dependen del motor | Disponibilidad, alcance y aislamiento dependen del motor |
| Distribución | Hay motores locales y distribuidos | Hay motores locales y distribuidos |
| Quién valida | Motor y aplicación, según las reglas | Motor y aplicación, según sus capacidades y configuración |

Son tendencias generales. Hay bases relacionales que se reparten entre máquinas y bases NoSQL con transacciones completas.

## Qué se gana y qué se pierde

### Con una base relacional

- **Restricciones explícitas.** Una clave foránea activa puede impedir un pedido huérfano; no demuestra que todos sus datos reflejen la realidad.
- **Consultas combinables.** Como los datos están separados y relacionados, puedes combinarlos de formas que no habías previsto al diseñar.
- **Cambiar la estructura cuesta.** Añadir una columna a una tabla con millones de filas hay que planificarlo.

### Con una base NoSQL

- **Flexibilidad de escritura.** Se pueden admitir documentos con campos nuevos sin alterar una tabla, pero el código, la validación y los datos antiguos pueden necesitar migración.
- **Las lecturas previstas son muy eficientes**, porque los datos se guardan con la forma en que se van a pedir.
- **Las preguntas imprevistas son difíciles.** Si necesitas los datos de una forma que no anticipaste, puede hacer falta reorganizarlos.
- **Reglas según el motor.** Hay que comprobar validación, unicidad, relaciones y transacciones; no se deducen de la palabra NoSQL.

## Cómo elegir

Elige **relacional** cuando:

- los datos tienen una estructura clara y relaciones entre sí;
- la corrección es prioritaria: dinero, inventario, reservas;
- no sabes aún qué consultas vas a necesitar.

Elige **NoSQL** cuando:

- la forma de los datos varía mucho de un elemento a otro;
- lees casi siempre bloques completos por un identificador;
- el volumen exige repartir los datos entre muchas máquinas;
- lo importante son las conexiones entre elementos, caso en el que encaja una base de grafos.

Si predominan relaciones, restricciones y consultas cambiantes, una base relacional suele ser un buen punto de partida. Compara productos concretos con tus consultas, volumen y requisitos de recuperación; migrar entre modelos también tiene coste.

## No hay que elegir solo una

Muchas aplicaciones combinan las dos: una base relacional para los datos principales y una clave-valor como caché o para las sesiones. Cada dato va a donde mejor se maneja.

## Confusiones frecuentes

- **"NoSQL es más moderno, luego es mejor."** Resuelve problemas distintos. Las bases relacionales siguen siendo las más usadas.
- **"NoSQL no tiene estructura."** La tiene y, según el motor, puede imponer reglas de validación.
- **"SQL no escala."** Escala hasta volúmenes muy grandes; lo que resulta más difícil es repartirla entre muchas máquinas, como explica [replicación y particionado](/articulos/replicacion-y-particionado/).

## Lo esencial

- Relacional y NoSQL describen familias de modelos; las garantías dependen del motor, de la configuración y del uso.
- La relacional responde bien a preguntas imprevistas; la NoSQL, a las lecturas para las que se diseñó.
- La elección depende de la forma de los datos y de cómo se van a consultar.
- Es habitual usar las dos en la misma aplicación.
