Una **condición de carrera** aparece cuando la corrección depende de un orden entre tareas que el programa no asegura. Un **bloqueo mutuo** ocurre cuando varias tareas esperan recursos o acciones unas de otras y ninguna puede avanzar sin romper esa dependencia.

Son los dos problemas clásicos de la [concurrencia](/articulos/hilos-y-concurrencia/).

## La condición de carrera

En el modelo que usaremos, restar una cantidad de un saldo compartido requiere tres pasos:

1. Leer el saldo actual.
2. Calcular el nuevo.
3. Guardar el resultado.

Si dos tareas hacen esto a la vez, sus pasos pueden mezclarse. Con un saldo de 100, una retirada de 30 y otra de 50:

| Paso | Tarea A (retira 30) | Tarea B (retira 50) | Saldo guardado |
| --- | --- | --- | --- |
| 1 | Lee 100 | | 100 |
| 2 | | Lee 100 | 100 |
| 3 | Guarda 70 | | 70 |
| 4 | | Guarda 50 | 50 |

El saldo final es 50, cuando debería ser 20. La retirada de A se ha perdido: B calculó a partir de un valor que ya no era el actual. Se llama **actualización perdida**.

Este JavaScript reproduce esa intercalación en un solo hilo. `await` suspende la función y permite que otra tarea lea el saldo antes de la escritura. No hace falta que dos instrucciones se ejecuten físicamente a la vez:

```js
let saldo = 100;

function esperar() {
	return Promise.resolve();
}

async function retirar(cantidad) {
	const actual = saldo;
	await esperar();
	saldo = actual - cantidad;
}

await Promise.all([retirar(30), retirar(50)]);

console.log(saldo); // 50
```

Los dos `retirar` leen 100 antes de que se reanuden sus continuaciones. Después A escribe 70 y B escribe 50. La [promesa](/articulos/promesas-y-async-await/) ya resuelta permite mostrar la cesión sin depender de tiempos de red. Es un ejemplo en memoria, no un sistema de cobros.

### Por qué es tan difícil de encontrar

En este caso, leer ambas veces antes de guardar produce el error; completar una retirada antes de empezar la otra da 20. En otros programas puede haber muchas intercalaciones incorrectas. Un programa así puede pasar todas las pruebas, ir bien durante meses y fallar un día con mucha carga. Al intentar reproducirlo, no aparece.

## La sección crítica

El fragmento de código que accede a un dato compartido y no debe ejecutarse a la vez en dos tareas se llama **sección crítica**. Aquí son los tres pasos de la retirada.

Una solución para esta actualización es garantizar la **exclusión mutua**: que solo una tarea esté dentro de la sección crítica en cada momento. También existen operaciones atómicas y otras formas de coordinación; elegirlas depende del estado y de la propiedad que quieras preservar.

## Cerrojos

La herramienta básica es el **cerrojo**, o *lock*; también se le llama *mutex*.

- Antes de entrar en la sección crítica, la tarea **adquiere** el cerrojo.
- Si otra lo tiene, espera.
- Al salir, lo **libera**.

Funciona como la llave del baño de un bar: solo hay una. Quien quiere entrar la pide; si alguien la tiene, espera a que la devuelva.

En un único bucle de eventos podemos **serializar** las operaciones, es decir, ejecutarlas completas una tras otra, encadenando promesas. Cada bloque de código del artículo se ejecuta por separado. Aquí aceptamos cantidades enteras positivas y rechazamos una retirada mayor que el saldo:

```js
let saldo = 100;
let turno = Promise.resolve();

function esperar() {
	return Promise.resolve();
}

function retirar(cantidad) {
	const operacion = turno.then(async () => {
		if (!Number.isSafeInteger(cantidad) || cantidad <= 0) {
			throw new RangeError("Se requiere una cantidad entera positiva");
		}
		const actual = saldo;
		if (cantidad > actual) throw new Error("Saldo insuficiente");
		await esperar();
		saldo = actual - cantidad;
	});

	turno = operacion.catch(() => {});
	return operacion;
}

const resultados = await Promise.allSettled([
	retirar(30), retirar(150), retirar(50),
]);

console.log(saldo); // 20
console.log(resultados.map((r) => r.status).join(" ")); // "fulfilled rejected fulfilled"
```

La primera retirada deja 70. La de 150 falla sin modificar el saldo. La de 50 sigue después y deja 20. `operacion` conserva el rechazo para quien la pidió; `turno` recupera la cadena para permitir la siguiente tarea. Si encadenáramos únicamente `turno = turno.then(...)`, el rechazo impediría ejecutar las funciones posteriores.

Esta cola no es un mutex entre hilos ni protege otras instancias del programa. Todos los accesos relevantes al saldo tendrían que usar la misma coordinación. Además, recuperar la cola no deshace cambios parciales: este ejemplo valida y espera antes de su única escritura. Un recurso real exige definir qué ocurre si falla a mitad.

Un cerrojo entre hilos debe usar las primitivas adecuadas del entorno, liberar el recurso también en las salidas por error y proteger toda la operación necesaria. Reducir la sección crítica ayuda al rendimiento, pero sacar de ella la lectura o la escritura puede reintroducir la carrera.

## El bloqueo mutuo

Los cerrojos traen un problema nuevo. Imagina dos tareas que necesitan dos cerrojos, y los piden en orden distinto:

| Paso | Tarea A | Tarea B |
| --- | --- | --- |
| 1 | Adquiere el cerrojo 1 | |
| 2 | | Adquiere el cerrojo 2 |
| 3 | Pide el cerrojo 2 y espera | |
| 4 | | Pide el cerrojo 1 y espera |

A tiene el 1 y espera el 2. B tiene el 2 y espera el 1. Ninguna soltará lo que tiene hasta conseguir lo que le falta. Sin cancelación, recuperación u otra intervención, ninguna puede continuar: es un **bloqueo mutuo**, o *deadlock*.

Es como dos coches frente a frente en un puente de un solo carril, cada uno esperando a que retroceda el otro.

### Las cuatro condiciones

En este modelo de tareas que adquieren recursos, el bloqueo mutuo requiere cuatro circunstancias a la vez:

1. **Exclusión mutua**: el recurso solo lo puede tener una tarea.
2. **Retener y esperar**: una tarea conserva lo que tiene mientras pide más.
3. **Sin expropiación**: no se le puede quitar a la fuerza.
4. **Espera circular**: hay un ciclo de tareas, cada una esperando a la siguiente.

Romper una de esas condiciones previene el bloqueo de este modelo. No demuestra que el programa esté libre de otros problemas de progreso.

### Romper el ciclo con un orden común

Si todas las tareas necesitan adquirir primero 1 y después 2, ocurre algo distinto:

1. A adquiere 1.
2. B intenta adquirir 1 y espera, sin conservar 2.
3. A puede adquirir 2, terminar y liberar ambos.
4. B puede obtenerlos después.

El orden debe identificar los mismos recursos en todo el programa: llamar «primero» al primer argumento de cada función no basta si otra llamada invierte los argumentos. Con un orden estricto común no puede aparecer un ciclo de adquisición entre esos cerrojos.

Un tiempo máximo de espera puede permitir abandonar y liberar recursos, si la operación y su recuperación están diseñadas para ello. No basta con dejar de esperar el resultado mientras la operación sigue viva. Reintentar todos al mismo ritmo puede producir bloqueo activo, y reintentar sin límite no garantiza progreso.

Mantener cerrojos poco tiempo y evitar llamadas desconocidas mientras se tienen reduce riesgos. No es una prueba de ausencia de bloqueos. Un único cerrojo también puede bloquear si una tarea intenta readquirirlo sin que su contrato lo permita, o espera un evento cuya producción requiere ese cerrojo.

## Otros problemas parecidos

- **Inanición**: una tarea nunca consigue el recurso porque otras siempre se le adelantan. No hay bloqueo, pero para ella el efecto es el mismo.
- **Bloqueo activo** (*livelock*): las tareas no están detenidas, pero tampoco avanzan. Como dos personas que se cruzan en un pasillo y se apartan hacia el mismo lado una y otra vez.

## Evitar el problema de raíz

Reducir el estado mutable compartido simplifica la coordinación, pero no elimina cualquier problema de orden:

- **Datos inmutables.** Tras publicarlos de forma segura, varias tareas pueden leerlos sin competir por modificaciones. Es una idea útil en [programación funcional](/articulos/programacion-funcional/).
- **Paso de mensajes.** Cada tarea administra su estado y recibe solicitudes. Todavía hay que definir el orden, los duplicados y las respuestas.
- **Base de datos.** Las [transacciones](/articulos/transacciones-y-acid/) ofrecen mecanismos de coordinación; la operación y el nivel de aislamiento deben proteger la propiedad que necesitas. Abrir cualquier transacción no basta para evitar toda actualización perdida.

La investigación del [Therac-25](/articulos/therac-25-y-la-seguridad-del-sistema/) muestra cómo la concurrencia interactúa con interfaz, dispositivos y barreras de seguridad.

## Errores comunes

- **Pensar que un solo hilo excluye las carreras.** Una operación puede leer un estado, ceder con `await` y continuar después de que otra lo cambie.
- **Proteger únicamente la escritura.** Si el cálculo depende de una lectura anterior, también debe estar dentro del protocolo de coordinación.
- **Confundir recuperación de cola con deshacer una operación.** Permitir la siguiente tarea no repara un estado que la anterior dejó a medias.

## Lo esencial

- Una condición de carrera deja un orden necesario sin asegurar; no exige ejecución física simultánea.
- La coordinación debe abarcar todos los accesos necesarios para preservar la propiedad compartida.
- El bloqueo mutuo impide avanzar por dependencias entre tareas; un orden común de adquisición rompe los ciclos entre esos recursos.
- Gestionar errores, cancelación y liberación forma parte del mecanismo; una espera corta no garantiza progreso.
