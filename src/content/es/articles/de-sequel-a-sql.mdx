Antes de llamarse **SQL**, el lenguaje desarrollado por Donald Chamberlin y Raymond Boyce en IBM durante los años setenta se llamó **SEQUEL**, *Structured English Query Language*. La denominación posterior conserva la idea de lenguaje estructurado de consultas, *Structured Query Language*.

El nombre ayuda a entender una decisión del diseño: acercar la consulta a una descripción de lo que se quiere obtener, en lugar de exigir que la persona programe cada recorrido de almacenamiento.

## Por qué desaparecieron las vocales

En su historia oral para el Computer History Museum, Chamberlin recuerda que SEQUEL resultó ser una marca registrada ajena. La solución fue quitar las vocales y conservar SQL. Las nuevas iniciales seguían encajando con *Structured Query Language*. El cambio no significaba que hubieran abandonado el enfoque declarativo ni diseñado de repente un lenguaje sin relación con el anterior.

El testimonio también atribuye el trabajo conjuntamente a Chamberlin y Boyce. Contar la evolución solo como una sucesión de siglas puede ocultar tanto esa colaboración como la investigación de System R que convirtió las consultas en un sistema ejecutable.

## Pedir un resultado

En [SQL](/articulos/que-es-sql/), una consulta que selecciona nombres de clientes de una ciudad expresa el conjunto que interesa. No especifica si el motor debe leer toda la tabla, consultar un índice o combinar accesos.

Esa separación permite que el motor mejore el plan sin cambiar la intención de la sentencia. Puedes añadir un índice y conservar el mismo SQL; el [plan de ejecución](/articulos/planes-de-ejecucion-sql/) puede cambiar.

## De la idea relacional a una consulta ejecutable

El contexto era hacer utilizables las ideas de Codd en sistemas reales como System R. Una descripción lógica de los datos necesitaba un lenguaje con el que pedir selecciones, combinaciones y resúmenes. Las palabras cercanas al inglés facilitaban leer esas operaciones, aunque seguía haciendo falta aprender su significado formal.

### La misma consulta antes y después de un índice

Este ejemplo funciona en SQLite:

```sql
CREATE TABLE clientes_sql (id INTEGER PRIMARY KEY, nombre TEXT, ciudad TEXT);
INSERT INTO clientes_sql VALUES (1, 'Ana', 'Lima'), (2, 'Luis', 'Quito');
SELECT nombre FROM clientes_sql WHERE ciudad = 'Lima';
CREATE INDEX idx_clientes_sql_ciudad ON clientes_sql(ciudad);
SELECT nombre FROM clientes_sql WHERE ciudad = 'Lima';
```

Las dos consultas devuelven Ana. Entre ambas se ha añadido una estructura física que el motor podría utilizar, pero no se ha reescrito la pregunta. Con tan pocas filas, incluso puede preferir no usarla. La separación declarativa permite esa elección.

El cambio de SEQUEL a SQL no debe ocultar otra diferencia: el modelo relacional proporciona una base conceptual; el lenguaje concreto incorpora decisiones de sintaxis y comportamiento. Saber de dónde salen las siglas ayuda a recordar su intención, pero entender una consulta exige conocer cómo trata duplicados, ausencias y agrupaciones.

## Un nombre no define todo el lenguaje

Aunque «consulta» forme parte de sus siglas, SQL también permite definir tablas y modificar datos. Y aunque sus palabras recuerden al inglés, no es lenguaje natural: tiene una sintaxis formal y reglas precisas.

Tampoco implica que todos los motores implementen exactamente las mismas funciones. Comparten un lenguaje estandarizado, pero conservan diferencias de dialecto y comportamiento que debes comprobar cuando trasladas una aplicación.

La curiosidad del nombre sirve así para recordar la característica relevante: describes resultados y operaciones sobre datos, mientras el motor decide buena parte del trabajo físico necesario para obtenerlos.

## Lo esencial

- SEQUEL significaba Structured English Query Language.
- Chamberlin recuerda que retiraron las vocales porque el nombre era una marca ajena.
- El enfoque declarativo conserva la pregunta mientras el motor decide cómo obtener el resultado.
