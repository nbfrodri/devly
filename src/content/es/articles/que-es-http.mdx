**HTTP** (*Hypertext Transfer Protocol*) es el protocolo que usan los navegadores y los servidores web para comunicarse. Define cómo se pide un recurso, como una página o una imagen, y cómo se contesta.

Un **protocolo** es un conjunto de reglas que dos programas acuerdan seguir para entenderse. HTTP/1.1 y HTTP/2 utilizan [TCP](/articulos/tcp-y-udp/) como transporte fiable; HTTP/3 utiliza QUIC, construido sobre UDP. La fiabilidad permite detectar y recuperar pérdidas durante la conexión, pero una avería todavía puede impedir completar una petición.

## Qué problema resuelve

Un navegador y un servidor son programas distintos, hechos por personas distintas, que se ejecutan en máquinas distintas. Para que cualquier navegador pueda hablar con cualquier servidor hace falta un idioma común. HTTP es ese idioma en la web.

## Petición y respuesta

HTTP funciona siempre igual: una parte pregunta y la otra contesta.

- El **cliente**, normalmente el navegador, envía una **petición**.
- El **servidor** devuelve una **respuesta**.

El cliente inicia el intercambio. Para recibir novedades puede abrir una respuesta que permanezca activa, como un flujo de eventos, o establecer un canal [WebSocket](/articulos/websockets/) en el que ambas partes envíen mensajes.

Cargar una página suele requerir varias peticiones. El navegador pide el documento y descubre estilos, imágenes y programas; los solicita según los necesita, salvo que ya disponga de una copia reutilizable en caché o estén incluidos en el propio documento.

## Cómo es una petición

En HTTP/1.1, la línea inicial y las cabeceras tienen una representación textual como esta. HTTP/2 y HTTP/3 transmiten información equivalente mediante estructuras binarias:

```
GET /articulos/ HTTP/1.1
Host: ejemplo.com
Accept-Language: es
```

- La primera línea indica el **método** (`GET`), la **ruta** del recurso (`/articulos/`) y la versión del protocolo.
- Las líneas siguientes son **cabeceras**: datos adicionales en forma de nombre y valor. `Host` dice a qué sitio va dirigida; `Accept-Language`, en qué idioma prefiere la respuesta.
- Algunas peticiones llevan además un **cuerpo** con datos, por ejemplo lo que has escrito en un formulario.

### Métodos

El método expresa la intención de la petición:

| Método | Intención |
| --- | --- |
| `GET` | Obtener un recurso |
| `POST` | Enviar datos para que el servidor los procese |
| `PUT` | Sustituir un recurso |
| `DELETE` | Borrar un recurso |

## Cómo es una respuesta

```
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8

<!doctype html>
<html>...</html>
```

- La primera línea lleva el **código de estado**, que resume el resultado.
- Después van las cabeceras. `Content-Type` indica de qué tipo es el contenido, para que el navegador sepa cómo tratarlo.
- Tras una línea en blanco viene el cuerpo: la página, la imagen o los datos pedidos.

### Códigos de estado

La primera cifra indica la familia:

| Códigos | Significado | Ejemplo |
| --- | --- | --- |
| `2xx` | La petición ha ido bien | `200 OK` |
| `3xx` | Hace falta otra acción para completar o reutilizar el resultado | `301 Moved Permanently`, `304 Not Modified` |
| `4xx` | La petición tiene un problema | `404 Not Found` |
| `5xx` | El servidor ha fallado | `500 Internal Server Error` |

Un `304` no indica una dirección nueva: responde a una petición condicional y permite reutilizar una representación guardada en [caché](/articulos/que-es-una-cache/). No todas las respuestas llevan cuerpo; por ejemplo, `204 No Content` no lo tiene.

## No tiene memoria

HTTP es un protocolo **sin estado**, o [stateless](/articulos/stateful-y-stateless/): cada petición tiene una semántica independiente. Esto no prohíbe que la aplicación guarde sesiones y relacione varias peticiones; debe aportar un mecanismo para reconocer esa continuidad.

Un mecanismo habitual son las **cookies**: datos que el navegador guarda y envía en las peticiones que cumplen sus reglas de ámbito. Una cookie puede contener un identificador que el servidor comprueba para recuperar una sesión; tener cualquier cookie no demuestra la identidad de una persona.

## HTTPS

Sin cifrado, los mensajes quedan expuestos a quien pueda observar o alterar el tráfico. Que una versión use un formato binario no proporciona confidencialidad.

**HTTPS** es HTTP enviado a través de una conexión cifrada. El mecanismo se explica en [cómo funcionan HTTPS y TLS](/articulos/https-y-tls/). Añade tres garantías:

- **Confidencialidad**: nadie en el camino puede leer el contenido.
- **Integridad**: nadie puede alterarlo sin que se note.
- **Autenticación del servidor**: la validación del certificado vincula la conexión con el nombre solicitado; no demuestra que el negocio sea honrado.

La interfaz del navegador permite consultar la seguridad de la conexión. HTTPS no evita por sí solo errores de autorización ni vulnerabilidades en la aplicación.

## Errores comunes

- **Confundir `200` con datos correctos.** El estado describe el resultado HTTP declarado por el servidor; una aplicación puede devolver contenido equivocado.
- **Suponer que cada petición abre una conexión nueva.** Una conexión puede reutilizarse y, según la versión, transportar varios intercambios a la vez.
- **Creer que stateless impide las sesiones.** La aplicación puede conservarlas y relacionar peticiones mediante un identificador validado.

## Lo esencial

- HTTP es el protocolo de la web: el cliente pide y el servidor responde.
- Una petición lleva método, destino y cabeceras; una respuesta, código de estado y cabeceras. El cuerpo depende del mensaje.
- La semántica de cada petición es independiente; la aplicación puede añadir sesiones.
- HTTPS es HTTP sobre una conexión cifrada.

Los programas también usan HTTP para intercambiar datos entre sí, mediante una [API](/articulos/que-es-una-api/).
