La **revisión de código** consiste en que otra persona examine una propuesta de cambio, contraste su comportamiento y comunique qué necesita corregirse antes de integrarla. Puede incluir código, configuración, pruebas y documentación.

## Qué problema resuelve

Quien escribe un cambio conoce su intención y puede dar por supuesto algo que el programa no hace. Otra persona aporta una perspectiva distinta: lee lo que existe y busca qué ocurriría con entradas, usuarios o situaciones no considerados.

La revisión también comparte conocimiento. Si solo quien hizo una modificación entiende sus decisiones, mantenerla después será más difícil. Una explicación que queda en la conversación ayuda a entender el motivo; la información necesaria para usar el código debe quedar además en el propio proyecto.

## De una propuesta a una decisión

Una [**solicitud de cambios**, o PR](/articulos/git-y-github/), reúne una propuesta de una rama para integrarla en otra. El recorrido habitual es:

1. El autor describe el problema, el comportamiento esperado y cómo lo comprobó.
2. El revisor lee esa descripción y el contexto de los archivos afectados.
3. Examina el **diff**, la comparación que muestra lo añadido y eliminado, y comprueba los casos relevantes.
4. Deja observaciones concretas; el autor responde y actualiza la propuesta.
5. El revisor comprueba la versión corregida y comunica si queda algún impedimento.

En GitHub se puede comentar sin decidir, aprobar o solicitar cambios. Que una aprobación sea obligatoria antes de fusionar depende de las reglas del repositorio. Aprobar una versión tampoco garantiza que las modificaciones añadidas después sigan siendo correctas.

## Un ejemplo: el límite del envío gratuito

Una tienda acuerda esta regla: «Envío gratuito desde 50 euros, inclusive; por debajo, 4 euros». Para la práctica, los importes llegan como números enteros de céntimos y son mayores o iguales a cero.

La aplicación lee `envios.json`. El [formato **JSON**](/articulos/formatos-de-datos-json-csv-xml/) agrupa valores entre llaves: cada nombre entre comillas se relaciona mediante `:` con su valor. `gratisDesdeCentimos` indica el importe mínimo incluido para obtener envío gratuito; `costeCentimos`, el coste por debajo de ese mínimo.

La propuesta cambia el archivo a esto:

```json
{
	"gratisDesdeCentimos": 4999,
	"costeCentimos": 400
}
```

El archivo tiene una estructura válida, pero no representa la regla acordada: 4999 céntimos son 49,99 euros. La aplicación concedería envío gratuito un céntimo antes de lo debido.

| Total de la compra | Resultado con la propuesta | Resultado acordado |
| --- | --- | --- |
| 49,98 € | 4 € | 4 € |
| 49,99 € | 0 € | 4 € |
| 50,00 € | 0 € | 0 € |
| 50,01 € | 0 € | 0 € |

Probar solo 49,98 y 50 euros no descubriría el error. El **caso límite**, una entrada junto a la frontera entre dos comportamientos, lo hace visible.

Un comentario útil sería: «Bloqueante: con 49,99 euros se aplica envío gratuito, pero el requisito empieza en 50. Ajusta el mínimo a 5000 y añade ese caso a las pruebas». Indica la entrada, el resultado observado, el esperado y el motivo para detener la integración.

La corrección es:

```json
{
	"gratisDesdeCentimos": 5000,
	"costeCentimos": 400
}
```

Después se vuelven a comprobar los cuatro casos. El de 49,99 pasa a costar 4 euros; los demás conservan sus resultados. El revisor también comprueba que la prueba nueva fallaba con 4999: una prueba que acepta las dos versiones no protege esta regla.

## Qué revisar además de las líneas cambiadas

El diff sirve para orientarse, pero una modificación puede afectar a código que no aparece en él. En el ejemplo interesa saber quién lee la configuración, si interpreta el mínimo como inclusivo y si la interfaz anuncia la misma regla.

| Aspecto | Pregunta concreta |
| --- | --- |
| Comportamiento | ¿Cumple el requisito y conserva los casos que ya funcionaban? |
| Integración | ¿Quienes usan este dato o esta función aceptan el cambio? |
| Diseño y claridad | ¿Se entiende sin añadir mecanismos innecesarios? |
| Pruebas | ¿Fallan ante el error que pretenden detectar? |
| Documentación | ¿Explica el comportamiento que queda realmente? |

Las [pruebas](/articulos/pruebas-de-software/) ejercitan comportamientos; un [linter](/articulos/que-es-un-linter/) puede detectar problemas de estilo o ciertas construcciones. Ninguno conoce automáticamente la promesa de envío gratis que recibió el equipo. La [integración continua](/articulos/integracion-y-despliegue-continuos/) ejecuta las comprobaciones configuradas, no demuestra que cubran todos los requisitos.

## Comentarios que permiten avanzar

Distingue un **bloqueo**, un problema que debe resolverse para integrar, de una sugerencia opcional. «Se cobra una cantidad equivocada» necesita solución. «Prefiero otro nombre igualmente claro» puede ser una preferencia; las convenciones existentes ayudan a decidir.

Explica el efecto y su causa, comenta el trabajo y evita juzgar a la persona. Si falta información, formula una pregunta concreta. Si hay desacuerdo, contrasta el requisito o una prueba y deja registrada la decisión.

La guía de Google propone favorecer mejoras sin exigir perfección. Eso no convierte en aceptables los errores conocidos que incumplen requisitos ni elimina las comprobaciones exigidas por el proyecto.

## Errores comunes y límites

- **Pedir revisión sin contexto.** Una descripción de «arreglos» obliga a adivinar el objetivo y dificulta detectar regresiones, fallos en algo que antes funcionaba.
- **Mezclar tareas sin relación.** Separarlas permite revisar cada decisión y sus pruebas. No existe un número de líneas que garantice una revisión buena.
- **Dar por revisados cambios nuevos.** Una corrección puede afectar a otro caso; hay que comprobar la versión que se integrará.
- **Tomar la aprobación como garantía absoluta.** La revisión reduce riesgos, pero no sustituye pruebas, evaluación de [seguridad](/articulos/que-es-la-ciberseguridad/) ni observación del sistema en funcionamiento.

## Lo esencial

- Revisar es contrastar un cambio con su propósito y sus consecuencias.
- Un ejemplo con entrada y resultados esperado y observado convierte una sospecha en algo comprobable.
- Los bloqueos se justifican por efectos y requisitos; las preferencias se identifican como tales.
- La decisión debe corresponder a la versión que se va a integrar.
